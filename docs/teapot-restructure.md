## 一、定位：一个仓库里有两个东西，它们**不是**一回事

| | **Teapot Engine**（Teapot） | **Bronana** |
| --- | --- | --- |
| 是什么 | **引擎** —— 一台用来做 2D 游戏的机器 | **游戏内容** —— 用这台机器做出来的那个游戏 |
| 住哪 | **仓库根**（`src/` · `tools/` · `test/` · `docs/`…） | **`workspace/Bronana/`** |
| 谁改它 | 引擎开发者（本阶段**只有这一件事**） | 未来；**必须通过操作引擎来改** |
| 前缀 | `teapot*` | `bronana*` |
| 当前状态 | 从"一个游戏"里**剥离**出来的引擎（剥离中） | 引擎的**第一个工作区**（也是验收用例） |

### ⚠ 三条不许混的判据

1. **内容名不许出现在引擎代码里**（`bronana` 在 `src/` 引擎模块内出现 **0 处**）—— 机器判据。
2. **引擎前缀与内容前缀严格分开** —— 引擎侧的标识符（包名 / 存储键 / 环境变量 / CI 名）
   一律 `teapot*`；内容侧的标识符一律 `bronana*`。
3. **本阶段不新增游戏内容** —— 内容只在"为了验证引擎能力"时被动用，
   而且**动的是引擎、不是玩法**。

## 二、术语（这一个阶段先定死，后面所有文档都用它）

用户给的那句话——**"模块是引擎原生所有的全部内容，而插件是提供给开发者开发的自定义模块"**
——在业界**确实有对应区分**，而且不同引擎用不同词。Teapot 采用**三名制**：

| 术语 | 定义 | 谁写 | 住哪 | 对应行业做法 |
| --- | --- | --- | --- | --- |
| **模块**（Module） | 引擎**原生**的一个功能单元。引擎自己就是**一堆模块**。 | 引擎作者 | `src/modules/<id>/` | Godot 的 `module/` 编译期模块 · Unreal 的 `Module`（`Build.cs`） |
| **插件**（Plugin） | **开发者**写的自定义模块，**用与原生模块同一套机制**加载。 | 引擎使用者 | `plugins/<id>/` | Bevy 的 `Plugin` trait · Unreal 的 `.uplugin` · Godot 的 `addons/` · VS Code 的 extension |
| **工作区**（Workspace） | 引擎所管理的一个**项目**（内容是它的输入与产物）。 | 引擎使用者 | `workspace/<Name>/` | Unity 的 `Assets/` 所在项目根 · Godot 的 `project.godot` · Cargo/npm 的 workspace |

**关键设计决定（要写进代码注释与门的注释里）**：

> **原生模块与插件走同一套注册机制。** 唯一的差别是**来源目录**（`src/modules` vs `plugins`）
> 与**随引擎发行与否**。用户那句"模块是原生、插件是自定义"因此**不是两套系统**，
> 而是**同一套系统的两个来源**。

### ⚠ 这条写法经过一次**联网核证**（2026-10-01），结论没变但理由更硬

调研对照了 **11 家**引擎的官方文档，逐条核证如下：

| 机制 | 内置也走它吗 | 官方原文 |
| --- | --- | --- |
| **Bevy `Plugin`** | ✅ **全部**（含 renderer） | 「**All Bevy engine features are implemented as plugins**… This includes internal features like the renderer, but games themselves are also implemented as plugins!」 |
| **PixiJS `extensions`** | ✅ **全部** | 「PixiJS is built as a set of **swappable parts called extensions**. Renderers, asset loaders, event systems, and application plugins are all extensions.」 |
| **Unreal `Plugin`** | ✅ 部分（Epic 自家功能就装在 `Engine/Plugins/`） | 「The Plugins category contains **built-in plugin modules**」 |
| **Phaser `Plugin`** | ✅ 内置由 `DefaultPlugins` 注册表安装 | `CoreScene` / `DefaultScene` 两张表 |
| **Defold native extension** | ✅ 自家 AdMob / Spine 同称 extension | 手册标题即 *Native extensions* |
| **VS Code extension** | ✅ | 「many core features of VS Code are **built as extensions**」 |

**⇒ 业界主流是"一套机制 + 一个来源字段"。** 所以 Teapot 采用**三名制**：

| 词 | 定义 | 一句话 |
| --- | --- | --- |
| **模块** | 引擎**唯一可装载单元** = 清单（id/依赖/阶段/配置/来源）+ 生命周期 | 引擎自带的一切**也是模块** |
| **插件** | **`origin !== 'core'` 的模块** | **插件不是第二种机制**，它只是来源不同 |
| **扩展** | 对宿主**某一个能力点**的可替换实现（渲染后端 / 资源加载器 / 输入后端） | 注册进**有类型、有优先级**的表（与 PixiJS `ExtensionType` 同构） |
| **包** | **分发单位**（有清单、有版本、能被 pnpm 解析） | 一个包可含 0..n 个模块 |

> 🔴 **调研推翻了一条我本来会写错的判断**：**Unreal 的 Module vs Plugin 不是"官方 vs 第三方"** ——
> 它的轴是「**编译单位 vs 分发单位**」，与谁写的无关（Epic 自家 Enhanced Input / GAS 就装在
> `Engine/Plugins/` 下）。**能抄的是 libGDX 的"同一机制 + 归属标签"法**（官方支持 / 非官方维护者），
> **不能抄 Godot 的"两套机制"法**（C++ module 要重编引擎 vs addon 不用 —— 代价是两套 API、两套构建、两套文档）。
>
> ⚠ **还有一条要你拍板**（调研列为"最该先定的一条"）：**"模块"这个词在引擎侧与 Bronana 侧会撞名** ——
> 家法里现在的定义是"**模块** = 用户定义玩法的方式（战斗/经营/养成）"，而引擎侧的**模块**是装配单元。
> **同一个词在同一个仓库里指两个东西，而门 `name` 抓不到语义冲突。**

## 三、目标目录（**不可逆的那一步**，动手前必须先把判据立住）

```
<repo root>                      ← **这就是 Teapot 引擎的仓库**
├─ src/                          ← 引擎：所有原生模块
│  ├─ core/                      ← 内核（原 L0：utils / registry / selfcheck / fold / rhi / text…）
│  ├─ modules/                   ← **一切皆是模块**（E6 之后引擎能力的落点）
│  └─ ...
├─ plugins/                      ← **插件**（开发者自定义模块）—— 引擎给机制、不给内容
├─ workspace/                    ← **工作区**：引擎管理的项目
│  └─ Bronana/                   ← 游戏内容（**从引擎根搬出去**）
│     ├─ teapot.workspace.json   ← 工作区清单（引擎读它来"运行/打包/预览"）
│     └─ src/                    ← 内容模块（原 `src/` 里属于 Bronana 的那些）
├─ tools/                        ← 引擎的开发工具（门、普查、dev-edit…）
├─ test/                         ← 引擎的测试 + 工作区的测试
├─ docs/                         ← 引擎的文档
├─ desktop/  server/             ← 引擎的宿主外壳
└─ index.html  styles.css  vite.config.ts
```

### ⚠ 为什么工作区是 `workspace/` 而不是 `games/`（用户已选）

- `workspace/` 表达"**引擎在管理它**"（用户可以往里放多个项目）；
- `games/` 表达"它们是游戏"，而引擎不该预设工作区一定是游戏 ——
  将来可能有**素材工作区 / 测试工作区 / 模板工作区**。

用户点名要支持的八项。Teapot 是 **Web + Node 双形态、无构建步（Node 直跑 `.ts`）**，
所以每一项都必须落到**一个真实命令或一个真实产物**上：

| # | 能力 | 在 Teapot 里**具体是什么** | 命令 / 产物 |
| --- | --- | --- | --- |
| 1 | **运行**（run） | 引擎跑一个工作区。三种宿主：web（Vite 开发服务器）/ cli（无头 `sim`）/ desktop（Electron） | `teapot run <ws>` → 起宿主；`teapot run <ws> --headless --frames N` |
| 2 | **调试**（debug） | ① 断点与逐帧：无头单步 + 状态导出；② **诊断面板**（`diag`）；③ 崩溃卡；④ 行为指纹（**回放式调试**：同一盘带子放两遍必须一样） | `teapot debug <ws>` · `?diag=1` · 门 `fingerprint` / `repro` |
| 3 | **预览**（preview） | ① 开发服务器热更（Vite）；② **离屏逐屏出图**（`ui-shot`，Electron offscreen）；③ 素材清单（`art-manifest`） | `teapot preview <ws>` · `teapot shot <ws>` |
| 4 | **打包**（build/package） | ① **Web 产物**：Vite 打成静态站点；② **Desktop 产物**：Electron 外壳；③ **CLI 产物**：无头二进制/脚本。体积必须有**预算门** | `teapot build <ws> --target web\|desktop\|cli` |
| 5 | **编译**（compile） | ⚠ **JS/TS 引擎没有"编译成机器码"这一步** —— 所以这一项在 Teapot 里落成**三件真实的事**：<br>① **类型检查**（`tsc --noEmit` ×2：浏览器侧 `types: []` + Node 侧）；<br>② **模块图与依赖校验**（静态解析 import 图：无环、分层、边界）；<br>③ **产物生成**（把工作区编译成引擎能加载的模块包）。<br>引擎**不假装**有 C 那样的编译步 —— 这是诚实。 | `teapot check <ws>`（= 类型 + 图 + 边界）· `teapot compile <ws>` |
| 6 | **调优**（profile/optimize） | ① **帧预算**（`perf.mjs`：中位/尾部/P99）；② **绘制调用普查**（`draw-census`）；③ **音频普查**；④ **颜色/硬编码审计**；⑤ 预算门（体积、贴图 KB、gzip）。**调优 = 拿读数对着预算改**，不是凭感觉 | `teapot profile <ws>` · 门 `perf` / `budget` |
| 7 | **编排**（orchestration） | ⚠ **这个词业界没有统一定义**，所以 Teapot 把它**说死**成一句话：<br>**"编排 = 把多个模块/任务按声明的顺序与依赖跑起来"**，落成两件真实的事：<br>① **模块编排**：模块的注册顺序由**依赖拓扑排序**决定（不是 import 顺序）；<br>② **任务编排**：有依赖的作业图（E1 普查的 P5 作业系统 + 依赖汇合）。 | `ModuleGraph`（E6）· `Jobs.submit/wait`（E8） |
| 8 | **管理**（management） | ① **工作区管理**：列出 / 新建 / 打开 / 删除工作区，读 `teapot.workspace.json`；<br>② **模块与插件管理**：启用/禁用、看每个模块的贡献（`Registry` 家族已经是一半）；<br>③ **版本与迁移**：存档信封（`envelope.ts` 已有）。 | `teapot ws list\|new\|open` · `teapot module list\|enable\|disable` |

> ⚠ **"编排"这条要提前跟你确认口径** —— 我把它落成"模块编排 + 任务编排"，
> 如果你指的是**场景编排**（像 Unity 的 Timeline/Sequencer 那样在时间轴上摆内容），

## 五、模块系统与插件系统的最小契约（E6 / E7）

**四步齐全**（本仓库的家法）不适用于模块本身 —— 模块比那更基础。用这份契约：

| 件 | 内容 | 判据（机器可查） |
| --- | --- | --- |
| **声明** | 每个模块导出一个 `TeapotModule` 描述符：`id` / `requires`（依赖的模块 id）/ `provides`（它注册进总账哪些家族）/ `setup(ctx)` / `teardown?()` | `id` 唯一、`requires` 都存在、无环 |
| **依赖** | 加载顺序由**拓扑排序**决定，不由 import 顺序 | 环 ⇒ 启动期报错并指出环在哪 |
| **生命周期** | `setup` 只在全部 `requires` 就绪后调一次；`teardown` 用于热重载 | 每个 `setup` 恰好一次 |
| **隔离** | 模块之间**只通过 `ctx`**（引擎给的接口）与总账协作，不直接 import 别的模块的内部 | "模块 A import 模块 B 的内部文件"要能被门抓 |
| **配置** | 模块自带默认配置与 schema，工作区可覆盖 | 覆盖的键必须在 schema 里 |
| **来源** | `src/modules/*`（原生）与 `plugins/*`（第三方）**同一套加载器** | 加载器只有一份 |

#### C. ⚠ 两类东西必须分清（**这是 E3 的判据，不是措辞**）

"把 `bronana` 全改成 `teapot`"**是错的** —— 同一个字符串在两类位置上含义正好相反：

| | **引擎身份** | **内容命名空间** |
| --- | --- | --- |
| 例子 | `BRONANA_HOME` · `~/.bronana`（引擎给的默认目录）· 工具横幅 · CLI 自称 · 崩溃 / 自检文案 | `bronana.settings/run/records/profile`（存档键）· `bronana-daily-` / `bronana-week-`（种子前缀）· 标题字形 `S.EMBLEMS`（玩家看到的游戏名） |
| 谁的名字 | **引擎**的（这台机器） | **内容**的（这台机器做出来的那个游戏） |
| 处置 | → `teapot*`，**旧名双读**（E2 已为环境变量立过这条规矩） | **值保持 `bronana*`**，但**出处**从引擎硬编改成**由工作区清单注入** |
| 为什么 | 引擎改名了，它自称的东西要跟着改 | 它是**玩家的存档数据、对局种子、屏幕上的游戏名** —— 改了就是孤立旧档、换掉每日 / 周常、把游戏改名 |

**用户已拍板（2026-10-01）**：种子前缀**按工作区注入**（Bronana 工作区自带前缀）。

> 🔑 **这条决定的技术价值：它让 E3 成为纯重构。** 引擎只提供"问工作区要命名空间"的机制，
> 而 Bronana 工作区声明的命名空间**就是 `bronana`** ⇒ `bronana.settings`、`bronana-daily-<日期>`
> 这些**值一个字节都不变** ⇒ **行为指纹逐位不变**。
> 反过来，若图省事把这 6 个值直接改成 `teapot.*`，那 4 个存档键会孤立旧档、2 个种子前缀会换掉
> 每日 / 周常 —— 那是**行为变更**，要动 `test/smoke.mjs` 基线 + 写 CHANGELOG，**不是 E3 的默认做法**。

#### D. E3 动手前的三条硬约束

1. **判据先改，代码后改**：B1 / B2 有三处被测试断言钉死（`test/modes.mjs` · `test/audio.mjs`），
   这正是 E2 已经栽过一次的"**改名只改一半**"（那次是 `BRONANA_SOURCEMAP` 被断言写死）。
   改字符串时**连判据一起改**，否则门会红在你想不到的地方。
2. **不许改历史叙述**：`tools/rename-bronana.cjs` / `rename-doudou.cjs`（"土豆 → 豆豆 → Bronana"那段历史）、
   `CHANGELOG.md`、`docs/history/**` 里的旧名**保持原样** —— 改了就是篡改历史。
3. **不许把内容名写进引擎模块**：门的判据是**双向的** —— 新增一处红、**还清了不删表也红**。
   所以 E3 收尾必须把 `tools/naming.mjs` 的 `DEBT` 表**删到空**，
   而不是留着"已经还清的欠条"。
