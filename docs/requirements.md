## 一、怎么用这个文件（工作流）

一条需求要走完这五步，缺一步都不算完：

| 步 | 谁做 | 产出 | 落在哪 |
| --- | --- | --- | --- |
| 1 提出 | 用户 | 一句话说清"哪里不对 / 要什么" | 本文「六、待讨论」 |
| 2 复述 | AGENT | 用自己的话重述一遍，并**指认它属于哪个模块、跟已有的谁是同一类** | 该条需求的「AGENT 的理解」栏 |
| 3 讨论 | 用户 + AGENT | 方案、代价、影响面、要不要做成设置项 | 该条的「讨论」栏 |
| 4 动手 | AGENT | 代码 + 测试 + 四步（声明 · 注册 · 自检 · 测试）（声明表 / `BY_ID` / 自检 / 注册） | 该条状态改为「已同意 → 进行中」 |
| 5 验证 | AGENT | `pnpm verify` 17 道门全绿 + 行为指纹 | 该条「证据」栏 + `CHANGELOG.md` |

**称呼约定**：这份文件由用户与 AGENT **共读**，所以**不使用第一 / 第二人称代词**
（任何形式的指代都不写）—— 一律写「用户」与「AGENT」。
理由：代词在共读文档里指向谁，取决于谁正在读；角色名不会。

**状态图例**

| 标记 | 含义 |
| --- | --- |
| ✅ | 已完成，有证据（有测试或门守着） |
| 🟡 | 部分完成 / 进行中，写清了**剩下的那一半是什么** |
| ⏸️ | 卡在**用户**身上（要素材、要拍板、要玩过才知道） |
| ⭕ | 谈完了、用户也点头了，等 AGENT 动手 |
| 🔵 | 待讨论（新提的，还没谈） |
| ❌ | 刻意不做，**写明了理由**（免得下次又被当成"漏了"） |

> ⚠ **一条贯穿全项目的纪律**（不写在每条里，但它管着每一条）：
> **会改行为的东西必须显式选择。** 默认档永远保持可复现（行为指纹逐位不变），
> 新特性做成设置项或新入口。这样"用户想要的手感"与"测试能复现的基线"
> 可以同时存在。命中定帧（`hitStop` 默认 0）、技能构筑（空构筑 = 0 槽位）
> 都是这么落地的。

**③ 早期 42% 死亡的根因（实机因果，不是猜测）**

### R44 · 阶段性收尾（**目标与全部需求完成之后**才做）

> 用户原话：「最后一定要记得，目标和我的需求全部完成以后分步骤做阶段性收尾工作
> 1.先跑全套测试（包括冒烟+回归）
> 2.推送到远端仓库（保证CI回馈正常）」

**它不是"顺手做一下"，是一条有顺序的收尾流程。** 两步的次序不能换：
先证明本地是绿的，再推 —— 反过来就是让 CI 代劳去发现红的。

#### 第一步 · 全套测试（冒烟 + 回归）

| 命令 | 覆盖 | 期望 |
| --- | --- | --- |
| `pnpm typecheck` | tsc ×2（浏览器侧 + Node 侧） | 0 错误 |
| `pnpm test` | **57 套**无头套件（含冒烟 `test/smoke.mjs`） | 全过 |
| `pnpm verify` | **17 道门**（含上面两项 + 指纹 / 分层 / 漂移 / 曲线 / 循环 …） | 全绿 |
| `pnpm run build` | Vite 生产构建 | 成功（**CI 会跑这一条**） |

⚠ `pnpm verify --quick` **不算**：它跳过 49 套测试，
而跳过的那条恰好是"行为与数值的唯一真相"。

#### 第二步 · 推送到远端

远端 `origin` = `https://github.com/Sean-CodingForLife/Bronana.git`，上游 `origin/main`。
CI（`.github/workflows/ci.yml`）在 **push 到 `main`** 与 PR 时触发，步骤与本地一一对应：
装依赖（`--frozen-lockfile`）→ `pnpm run build` → `pnpm typecheck` → `pnpm test` → 其余各门。

⚠ **`pnpm run build` 是 CI 独有的一步**（本地 `verify` 不跑它）。它专抓一类问题：
**只有打包器才看得见的依赖** —— 例如某个模块 import 了 `node:fs`，而它又在浏览器的
依赖链上。`src/storage_fs.ts` 就是为这件事单独成模块的（见 R42 的存储那一节）。

#### M2 第一刀：接上 `capacity` 的产出点与消费点（2026-09）

v3 §8-2 要求"接上 `capacity` 代币的真实产出点与消费点（**现在 0/0**）"。
复查确认了那个 0/0：`capacity` 在 `eco_manage.ts` 里**声明得完整**，
而在全仓**一处读写都没有** —— **账本上有一笔钱，游戏里没有**。

| 点 | 实现 |
| --- | --- |
| **产出** | `Stronghold.produce(owned)` = 基础运转 + 设施产出，每波由 `startWave` 入账 |
| **消费** | `Stronghold.capacityFor(step)`：**建造子模块**盖设施要花产能 |

⚠ **产出必须有一个不依赖设施的底数**：只由设施产的话，开局 0 设施 → 0 产能 →
建不了设施，是个**把自己锁死的循环**。v3 §5.3-9 的"撞墙不卡死"要求的正是这一条 ——
**经营模块自己会运转**，设施是让它转得更快，不是让它开始转。

⚠ 盖设施现在付两笔钱，各有各的身份：`material`（**全局货币** = 行动成本）与
`capacity`（**经营代币** = 经营自己的资源）。三样钱（材料 / 产能 / 核心材料）
**缺哪一样都要在按钮之前讲清楚**。

⚠ **只写不读**：产能进 `<code>buildSummary</code>` 之后 `flow` 门报了两条 ——
"进度漂移"与"**存档不幂等**" —— 起因是只加了写入、忘了 `importRun` 的读取。
门把这半件事抓出来了；否则它会以"读档之后那笔钱莫名没了"落到玩家身上。

**新守卫 · 每个模块代币都必须同时有产出点与消费点**（判据 J 里）：
`capacity` 的 0/0 不是意外，是一整类"声明了却没人读写"。用**登记表**而不是
命名约定 —— 战斗代币 `scrap` 散着写（`S.player.scrap += m` 在好几处），
不走 `addScrap` 那样的出口，约定会漏掉它。**已反证**：把 `spendCapacity` 改名，
守卫当场报"产得出来但花不掉，它就不是一笔钱而是一个计数器"。

#### M2 第二刀：拆出建造子模块与经营子模块（2026-09）

**v3 §三-2 的原文是把刀**：

> 建造子模块：布局、设施、升级、解锁、空间规划。
> 经营子模块：资源、生产、供需、效率、市场、人员、时间。
> 经营模块内部子模块**可共享经营代币**，但**不得让建造机制承载战斗或养成的成长**。

| 改动 | 说明 |
| --- | --- |
| 产出搬到经营侧 | `Stronghold.produce` **删掉**，`Craft.capacityYield(owned, bonus)` **新增** |
| 建造只留消费 | `Stronghold.capacityFor` —— 一产一花，钱才转得起来 |
| 子模块声明 | `eco_manage.ts` 的 `Manage.SUBMODULES`：`scope` 逐条抄自 §三-2 原文 |
| 子模块自检 | 子领域与原文**逐条对账**；两个子模块必须**一产一花**（都花是死水，都产是印钞机） |

⚠ **修掉一处真实的越界（上一轮自己造的）**：据点「档案馆」的 `bonusPoints`
上一轮被改指到「训练产出」上，当时的说法是"影响的是**动作的效率**"。
**那个说法是错的** —— §三-2 禁止的是"让**建造机制**承载**养成**的成长"，
换一个动作并不改变它仍然是建造在承载养成的成长。
当时只盯着 §5.4-错误4（"直接花另一个模块的资源买本模块的能力"），
漏了 §三-2 这一条**更直接**的禁令。

现在它指到**产能产出**上（`capacityBonus`）：建造 → 经营，而这两个是
**同一个模块的两个子模块** —— 那正是 §三-2 明确允许的那条路。

**新守卫 · 建造的边界**（判据 J 里）：`stronghold.ts` 里不许出现
