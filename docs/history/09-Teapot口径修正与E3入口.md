# 09 · Teapot 口径修正与 E3 入口

> 起因：接手 Teapot 战略重构。交接材料里说 E3 是"**门 naming 那 13 处欠账 / 2 个文件**"，
> 而工程里的实测是 **17 处 / 4 个文件**。顺着这条差异查下去，**查出了更要紧的一件事**：
> 门只覆盖 `src/` 的 **23 个模块**，而 `src/` 有 **97 个** `.ts` —— **"门绿"不等于"改名做完了"**。
>
> 本卷**只做口径，不碰代码**（用户已选"先修口径，再动代码"）。
> E3 的实际动手记在下一卷。

---

## 一、那个数错了多久

| 位置 | 曾经写的 | 事实 | 怎么查 |
| --- | --- | --- | --- |
| `tools/naming.mjs` 头注释 | "改造前实测：…出现 **13 处**…真代码 9 处、注释 4 处" | `DEBT` 表 **17**（1+6+7+3） | `git show 36a96fc:tools/naming.mjs` |
| `docs/teapot-restructure.md` §六 E3 行 | "实测只有 **13 处，2 个文件**" | **17 处 / 4 个文件** | `node tools/naming.mjs` |

⚠ **两处的"13"都不是历史值，而是从第一次提交起就写错了**：

```
$ git log --oneline -- tools/naming.mjs
36a96fc feat: Teapot 战略重构 · E1 —— 文档整理 + 命名边界门 + 引擎能力总表收成一份

$ git show 36a96fc:tools/naming.mjs | grep -A5 'const DEBT'
const DEBT = {
  'comp.ts': 1, 'draw2d.ts': 6, 'storage.ts': 7, 'utils.ts': 3
};
```

—— 建表那一刻就是 **17**，而旁边的注释写 13。**两个数从来没有对上过**，而门**照常全绿**
（门判的是"实测 != 表"，注释不在判据里）。这与门 `doc-num` 记录的**同一个坑**：
手写的统计数字一定会漂，而**漂了的统计比没有统计更糟 —— 它看起来是量过的**。

**处置**：两处**都不再写总数**，改成"唯一出处是 `DEBT` 表 / 跑门得"。

## 二、量出的真问题：**门只覆盖 23 / 97**

```
$ node tools/naming.mjs --json
{"engineModules":23,"hits":17,"debtTotal":17,"mismatch":[],"fresh":[],"badNames":[], ...}
```

`engineModules` 来自门 `engine-boundary` 的 `ENGINE` + `ENGINE_MIXED` **两张分类表** ——
也就是说：**哪些模块算"引擎"是人的决定，门只扫被登记的那 23 个**。
`cli.ts` / `main.ts` / `crash.ts` / `storage_fs.ts` **都不在表里**，于是：

| 门外的六类 | 实测位置 | 今天的状态 |
| --- | --- | --- |
| CLI 身份 | `src/cli.ts` 的 `'Bronana 命令行'` · `'=== Bronana 无头跑局 ==='` | ⚠ 前者被 `test/modes.mjs` **断言钉死** |
| 崩溃卡 / 自检框 | `src/crash.ts` 的 `'Bronana 出了点意外…'` · `'[Bronana] 运行时错误'` · `src/main.ts` 的 `'Bronana 启动自检未通过…'` | ⚠ 前者被 `test/audio.mjs` **断言钉死** |
| 工具横幅 | `tools/verify.mjs`（**全门验证**的横幅）· `registry-drift.mjs` · `name-audit.mjs`（3 处）· `solid-audit.cjs` | 全绿 —— 但跑门第一眼看到的就是"Bronana" |
| git hook 标记 | `tools/install-hooks.mjs` 的 `# >>> bronana pre-commit >>>` | 已装的 hook 里留着旧标记 |
| 第三只环境变量 | `src/storage_fs.ts` 的 **`BRONANA_HOME`** | 全仓 `TEAPOT_*` **只有** `TEAPOT_SOURCEMAP` 与 `TEAPOT_DESKTOP_GPU` ⇒ E2 的"双读"规则**漏了这只** |
| 盘上的存档目录 | `src/storage_fs.ts` 的 `~/.bronana` | 在**文件系统**上 ⇒ 只能"旧目录回退读 + 迁移" |

**为什么这是"真问题"而不是"措辞问题"**：E2 的交付结论是"引擎改名完成、门上全绿"，
而**跑门的横幅、CLI 的自称、崩溃卡的文案仍然是 Bronana** —— 用户那句
「**包括文件，文件名，会话，等等，全部都要检查，不要漏了，我没提到的也要检查下**」，
指的正是这一类。

## 三、定下的判据：**引擎身份 vs 内容命名空间**

"把 `bronana` 全改成 `teapot`"**是错的** —— 同一个字符串在两类位置上含义正好相反：

| | **引擎身份** | **内容命名空间** |
| --- | --- | --- |
| 例子 | `BRONANA_HOME` · `~/.bronana` · 工具横幅 · CLI 自称 · 崩溃 / 自检文案 | 4 个存档键 · `bronana-daily-` / `bronana-week-` 种子前缀 · 标题字形 `S.EMBLEMS` |
| 处置 | → `teapot*` + **旧名双读**（环境变量）/ **旧目录回退读**（文件系统） | **值保持 `bronana*`**，**出处**改成**由工作区清单注入** |
| 为什么 | 引擎改名了，它**自称**的东西要跟着改 | 它是**玩家的存档、对局种子、屏幕上的游戏名** |

**用户拍板（2026-10-01）**：种子前缀与存储键 **按工作区注入**。

> 🔑 **这条决定让 E3 成为纯重构**：引擎只给"问工作区要命名空间"的机制，
> 而 Bronana 工作区声明的就是 `bronana` ⇒ `bronana.settings`、`bronana-daily-<日期>`
> **一个字节都不变** ⇒ **行为指纹逐位不变**。
> 若图省事直接改成 `teapot.*`：4 个存档键孤立旧档、2 个种子前缀换掉每日 / 周常 ——
> 那是**行为变更**，要动 `test/smoke.mjs` 基线 + 写 CHANGELOG。

🔴 **顺带查出一条没结清的账**：**内容侧仍然叫 Bronana**，所以账本 **R53-D**
（与 Steam 已上线的《香蕉兄弟》Bronana 撞名）**一个字都没消** ——
"内容命名空间保持 `bronana*`"正是它的代价。要么单独拍板给内容改名，要么明确接受风险；
**不许把它当成"已经改过名了"**。已写进 R53-D 的处置栏。
