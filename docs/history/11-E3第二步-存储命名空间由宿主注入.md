# 11 · E3 第 2 小步 —— 存储键的命名空间由宿主 / 工作区注入

> 上一卷（`10`）还清了门内 10 处内容名；本卷还清**最后 7 处**（`storage.ts`）——
> 于是门 `naming` 的 `DEBT` 表**第一次变成空表**。
>
> 用户 2026-10-01 的决定是「**Bronana 只指游戏内容**……**不要混了**」＋
> 「**内容命名空间由工作区注入**」。所以这一步改的不是"键叫什么"，
> 而是"**键的前缀归谁管**"：**值一个字节不变**，**旧档照读**，**指纹逐位不变**。

---

## 一、改了什么

| | 改造前 | 现在 |
| --- | --- | --- |
| `src/storage.ts`（引擎） | `settings: 'bronana.settings'` 等 **4 个带前缀的字面量** | **逻辑键名** `settings/run/records/profile` ＋ `buildKeys()`；前缀由 `Storage.setNamespace(ns)` 决定 |
| 谁给前缀 | 引擎自己（**耦合**） | **宿主**：`main.ts`（浏览器）· `cli.ts`（命令行）· `test/_load.mjs`（测试）各说清自己跑哪个工作区 |
| 忘注入会怎样 | —— | **启动期自检报红**（`SelfCheck.register('storageNamespace', …)`） |
| 3 处注释 | 拿 `bronana.profile` 当例子 | 改成 `<命名空间>.profile`（**叙述一字未改**，只换了那个字面量） |

**为什么"忘注入"必须拦**：不注入时键是**裸名**（`profile`），而读写会落到另一处 ——
表现是"**读不到旧档、像新玩家一样**"。这条**不报错**，是本仓库最怕的那一类静默退化。
所以按家法配了一条自检，并且**证明它会红**（见下）。

## 二、连带的静默 bug：`slots.ts` 在模块顶层快照了键

```
slots.ts:164  var CARRIED = [Storage.KEYS.profile, Storage.KEYS.records, Storage.KEYS.run];
```

模块顶层 —— 也就是 **import 期**。键名以前是常量，这没问题；**一旦键名能在启动期变化**，
这个快照就冻住**裸键名**，而导出 / 搬运 / 重置里的读写用的是带前缀的键 ⇒
**操作到另一批键上**（"搬运了但什么都没搬"，不报错）。已改成 `carried()` 按需算。

> 教训：**键名既然是启动期可变的，任何模块级快照都会过期。**
> 这与家法里"**改名字段要连读点一起搜**"是同一类 —— 而这次是"**改的那件事让旧的读点失效**"。
> 另外：`Slots.audit()` 在模块顶层跑，但它只验"槽位 = 键重定向"的**结构**性质
> （`slotKey(k,0) === k`），对任何前缀都成立，所以它不受影响。

## 三、证据（跑出来的）

```
$ node tools/naming.mjs
  实测命中 0 处 · 欠账表记 0 处        ← 原 17 处 / 4 个文件；DEBT 表第一次是空的
  ✔ 没有新增 · 没有引擎模块的文件名带内容名
EXIT=0

$ node test/naming-gate.mjs
  全部通过 ✔（20 条断言）              ← 空表下两个方向**仍然**会红（合成欠账探针）
```

一次性探针（`tools/tmp-ns-probe.mjs`，**验完已删**）实测两条关键性质：

```
[1] 注入之前
     KEYS = {settings:"settings", run:"run", records:"records", profile:"profile"}
  PASS 不注入时键是裸名 —— 这正是要拦住的静默危险
  PASS 启动期自检**会红**（不是装饰）      ← 家法：一条不会失败的审计等于装饰
[2] 注入之后
     KEYS = {settings:"bronana.settings", run:"bronana.run", …}
  PASS 4 个键与改造前逐字节相同            ← 所以旧档照读、指纹不变
```

```
$ pnpm verify
  通过 25 / 25 条门（含 67 套测试）
  ✔ fingerprint / repro 全绿 —— **逐位不变**（出处：node tools/fingerprint.mjs；不抄值，家法）
```

⚠ 这一步**碰了存档**（三小步里唯一的一步），所以"指纹逐位不变"不是礼节，
它是**唯一的验收**：它证明键名与写入路径一个字节都没变。

## 四、顺手修掉的一个**报告口径**错（同一类坑的又一例）

跑门时 `drift` 的报告里 `make-migration-fixture.mjs` 一直印 **✘ 没有入口**，
而门其实是**绿的** —— 判据那边写着 `ok: … || locked`（版本锁定 = 合法状态），
**报告**那条 if 链却漏了 `locked`，于是显式允许的状态被印成错误。
我照着那行去查了两轮才发现门是绿的。已补上那一档。

> 这正是本仓库记过的「**报告口径错了，判据本身没错**」—— 门没坏，是**它在说谎**。

## 五、有意留给 E5 的（不是漏的）

| 项 | 为什么留 |
| --- | --- |
| **2 个种子前缀**（`<工作区>-daily-` / `-week-`） | 同属"内容命名空间"，但它们的**值**同样"一个字节都不能变"（改了就是换掉每日 / 周常的种子）。既然机制已经就位，值与机制一起交给工作区清单最省事 |
| **`~/.bronana` 目录**（`storage_fs.ts`） | 它其实是"**工作区的数据住哪**"—— 比"引擎的默认目录"更该由 E5 的 `teapot.workspace.json` 回答（多工作区还要分目录） |
| **门外六类里的引擎身份字符串**（CLI / 崩溃卡 / 自检框 / 工具横幅 / `BRONANA_HOME`） | 那是 E3 的**第 3 小步**：与键无关，且其中 3 处被测试断言钉死（要先改判据） |
