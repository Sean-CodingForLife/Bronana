## 环境（层主题）：**已完成** —— 从"层号查表"到"每局抽签 + 看得见"

用户的问法是："那么地图变么吗，我的意思是，不同的地图不同的环境。"

先量，再答。答案是**一半的一半**：**地图在变，环境没变**。

### 一、改造前的两条实测

1. **环境钉死在层号上。** `genFloor` 里那一行是 `THEMES[min(THEMES.length-1, f-1)].id` ——
   第 1 层永远是碎石浅层、第 2 层永远是菌毯洞窟、第 3 层永远是熔渣裂谷。
   也就是说"这一层是什么地方"在**一局开始之前**就知道了，跑一百局是同一条序列。
2. **它在战场上一次都没被读过。** 全仓 `theme|Theme` 的引用里，`render.ts` **0 处**；
   地面配色是写死的红棕 `PAL.G1..G6`，`Arena.build(wave)` 根本不认识主题。
   所以两层不同的"环境"在战场上**像素完全一样** —— 环境只是小地图标题上的两个字
   （`mm-theme`）加三个数字（敌人生命/伤害/怪物池）。

一句话：**不是在变的东西叫"不同的环境"，那叫"同一个地方的不同层数"。**

### 二、拆成两件事（它们本来就不是一回事）

| | 谁决定 | 变不变 |
|---|---|---|
| **多难** | 层号 → **难度带**（`Dungeon.bandOf`） | 不变（带心 = 改造前那一档的数值） |
| **长什么样** | 种子 → **带内抽签**（`Dungeon.themeFor`） | 每局不同 |

- `BANDS = 4`，`Dungeon.THEMES` 从 4 条长到 **10 条**：
  带 1 碎石浅层/苔原台地/灰烬滩 · 带 2 菌毯洞窟/晶簇矿脉/铁锈工场 ·
  带 3 熔渣裂谷/霜殒洞窟/虚空裂隙 · 带 4 深井（通关后的可选挑战，单条）。
- **`themeFor` 用独立的随机流**（盐 `'theme:<带>:<种子>'`），**不碰 `genFloor` 那一串 `rnd`**。
  否则"换个环境"会顺手把房间布局也挪掉 —— 而同种子的旧成绩码会全部作废，
  这件事跟"环境该不该变"毫无关系。证据见下面第三节的排除法。

实测（`pnpm run map 240` = 240 局 × 3 层）：

```
第1层  3 种   苔原台地 38% · 碎石浅层 35% · 灰烬滩 28%
第2层  3 种   铁锈工场 35% · 菌毯洞窟 34% · 晶簇矿脉 31%
第3层  3 种   霜殒洞窟 40% · 熔渣裂谷 35% · 虚空裂隙 25%
→ 240 局里出现过 27 条不同的"三层环境序列"（理论上限 27），最常见的一条占 7%（改造前 100%）
  带心：1.00 / 1.12 / 1.20 / 1.35 —— 与改造前那一档逐位相同，带内均值全部落回带心
```

**难度没有被偷偷改动**：这是 `Dungeon.audit` 里的一条硬规则 —— 带内均值偏离带心超过 0.02
就报错，怪物池偏移必须**逐带一致**，带心必须逐带递增。往某一带塞一个 `hpMul 1.4` 的环境
是过不了启动期自检的。

### 三、看得见的那一半：配色 + 装饰物（**可见美术变化**）

`FloorThemeDef` 多了一个 `pal`（9 个色号 + 5 条纵向带的色表）和一个 `prop`（装饰物种类）。
`Arena.build(wave, themeId)` 按环境生成，`render.ts` 的地面 / 岩石 / 裂纹 / 围墙 / 战场外底色
**全部改读 `a.pal`**，装饰物按 `a.prop` 分派到 5 套画法（`PROP_DRAW`）：
白骨 / 菌伞 / 晶簇 / 余烬 / 冰棱，每套两个变体。

三条不能破的规矩：

1. **默认环境逐像素不变**：`shallow` 的 `pal` 就是原样搬过来的 `PAL` 地面六色，
   `PAL_TONES` 是它的降级副本 —— 所以"没主题"（无头测试、`Arena.build(7)`）画出来与改造前一致。
2. **烘焙键从"波次"改成"(波次, 环境)"**。只认波次的话，同一波里翻层换了环境，
   交出来的还是上一层的红棕地面 —— **缓存会把"环境"静默吃掉**。
   这条不是设想出来的：加上主题之后 `render-check.mjs` 的"视野外的血迹不绘制"
   立刻红了（48707 vs 52），因为 `Game.newRun` 之后第一帧现在必然重烘焙，
   而那条断言把烘焙开销算进了"20 条屏幕外血迹"的差值里。断言本身也要跟着说清前提。
3. **环境不参与战场随机流**：`Arena.build` 仍然只吃 `arena-wave-N`。
   于是同一波次换环境时，石头/碎石/裂纹/装饰物的**位置逐位相同**，只有色号与形状不同。
   （守卫：`cache.mjs [7]` 逐字段比对两套环境的位置。）

**验证"真的看得见"**：`?test=arena&theme=<环境id>` 是这一轮新加的调试入口 ——
只为拍地面而生（没有升级弹窗、没有贴花）。在它之前，`ui-shot` 那 19 屏里
**没有任何一屏拍得到战场地面**（`play` 停在商店、`demo` 停在升级界面），
所以"环境有没有生效"这件事本来是无从测量的。`Demo.stage(char, wave, themeId)` 是它的钩子。
产出：`ui-shots/env-<环境id>-1280x720.png` × 10。

```
pnpm run shot -- --sizes=1280x720 "--shots=env-shallow:?test=arena&theme=shallow,env-frost:?test=arena&theme=frost,..."
```

翻层时那句提示也有了：`floorEnter` 处理里除旁白与"这一层守着谁"之外，
**必须**再说一句"这一层 · <环境名> —— <说明>"。旁白存在时 banner 被旁白占着，
所以环境走 toast 这一路（否则它只在那句有旁白的日子里才看得见，那是一半的层）。

### 四、指纹变了 —— 以及一次排除法（这一节比结论重要）

三段行为指纹从 `4a89e77d / 62b9f577 / 21b2e870` 变成 `76b6aaa3 / fb57410d / ed7c1067`。

**它必须变**：环境不再按层号钉死，同一层每局可能抽到带内的另一个环境，而环境的
`hpMul/dmgMul/poolShift` 本来就会折进刷怪（`Dungeon.foldMods`）—— 数值变了，对局自然不同。

但"应该变"不是理由，是借口。所以做了排除法：**把每一带钉回改造前那一个主题**
（`THEME_BY_BAND[b] = [shallow|fungal|molten|abyss]`），三段指纹**逐位回到旧基线**：

```
ranger    seed 20240922  期望 4a89e77d  实得 4a89e77d  ✔
gladiator seed 777       期望 62b9f577  实得 62b9f577  ✔
engineer  seed 4242      期望 21b2e870  实得 21b2e870  ✔
```

结论：**除了"这一层的环境是哪一个"之外，房间布局、随机数消费顺序、刷怪次序没有任何位移。**
（这条排除法写进了 `test/smoke.mjs` 的注释里，因为下次看到指纹变红的人会需要它。）

顺带一条老实话：[`02` 卷](02-地牢化与设计复查.md)的「三根柱子各归其位」里说"指纹对波次结算是盲的" —— 这一轮它不盲了，
因为环境倍率折进去的位置恰好在它敏感的那条路径上。**同一条基线在两个方向上都说过谎**，
所以它从来不是"什么都没变"的证明，只是"这两处也没变"的证明。

### 五、守卫清单

`test/dungeon.mjs [5] / [5b]`（新加 23 条）：
每一带的每个环境在 400 个种子里都出现过（**没有环境被抽签饿死**）·
三层环境序列 ≥20 种且最常见的一种 ≤50% · 每层至少 2 种 ·
同种子同层必得同一环境 · **`themeFor` 的函数体里不许出现 `rnd(`**（换环境不能挪布局）·
中间乱抽别的种子/层之后同参数地图逐字段不变 ·
**带内均值 = 带心（生命/伤害 ≤0.02、怪物池逐带一致）** · 带心逐带递增 ·
每个环境配色齐全（5 带 + 9 色号，全是 `#rrggbb`）· 10 个地面基色**两两不同** ·
`PROP_DRAW` 的表键与 `Dungeon.PROP_KINDS` **双向**对齐（声明了没人画 = 不存在；
画了没登记 = 看不见）· `render.ts` 真的读了 `pal.base`/`pal.tones`/`a.pal` ·
`arena.ts` 按环境 id 取配色且随机流仍只吃波次 · `game.ts` 把主题交给了战场生成。

`test/cache.mjs [6] / [7]`：同波次换环境也重新烘焙 · 同波次同环境仍命中缓存（没变成每帧重烘焙）·
换环境时地形位置逐位不变 · 不认识的环境 id 退回默认环境（不会画不出东西）。

`test/ui-check.mjs [7]`：翻层时必须把环境名说出来（把 `UI.toast` 换成一个收集器，
三个种子三种环境逐个核对），而且**带一句说明**。

`test/comp.mjs`：`?test=arena` 场景的每个对象仍由组件组合而成 ·
`&theme=` 真的钉住了环境（地图与战场都是它）· 不认识的环境 id 被忽略 ·
arena 场景停在 `playing`（场上有怪 → 房间不算清空 → 不会跳商店/升级）。

### 六、这一轮的平衡复核

`pnpm run bal craft`（12 种子 · survive）：从不制造 4.3 · 只制造 4.3 · 先造后买 4.5 · 先买后造 4.4。
结构没变（先造后买仍然最强），绝对波次在工具自身的种子噪声（±1 波）之内 ——
**而且这次有一条比波次更直接的证据**：带内均值 = 带心是硬断言，
所以这一轮改的是**长相**，不是难度。

### 七、没做的

- **环境专属的怪/机制**（比如"霜殒洞窟的怪更慢""熔渣裂谷会掉火星"）：
  只有一条数值通道（`hpMul/dmgMul/poolShift`），做它要新增机制，而这一轮的诉求是"环境不一样"。
  带内的 `hpMul/dmgMul` 抖动 ±0.02 已经是这条通道能给的极限，再多就越过"不改难度"那条线了。
- **环境专属的 BGM / 粒子天气**：`Season`/`Sfx` 都没有按环境分派的入口，加它属于新机制，
  不是这次要解决的问题。
- 深度带 4（深井）只有一个环境，所以那一带**没有抽签**，带心逐位等于旧值 —— 这是有意的。

## 全量架构扫描（**已完成**）—— 系统分层 · 状态所有权 · 以及一把会撒谎的尺子

用户的问法："全量扫描，我需要项目是有足够的系统的抽象的设计，不要耦合到一块，按模块和系统设计。"

回答分两半：**结构本身是好的**（下面第一节有数字），**但当时那把架构尺子是坏的**，
而且它坏的方向最危险 —— 它把活代码标成"真死，可删"。所以这一轮的次序是：
先修尺子，再用尺子量，最后只改量出来确实错了的地方。

### 一、量出来的结构（`pnpm run audit`）

```
52 个模块 · 22,381 行（+ types.d.ts 2,521 行）· 依赖图**无环**
9 个系统 / 9 层：工具与机制(0) → 数据表(1) → 地牢与内容(2) → 局外成长(3)
                → 模拟内核(4) → 一局的进出(5) → 造型与声音(6) → 表现与界面(7) → 入口(8)
跨系统依赖边：顺层 181 条 · 向上 2 条（比例 90.5 : 1，且两条都写了理由）
```

三条比"没有环"更值钱的性质：

1. **元进度不会穿透战斗。** 据点 / 工坊 / 图纸 / 天赋 / 难度 / 契约的修正全部在
   `newSession` 里**折成普通对象**（`campFx` / `fmods` / `dmods` / `kmods` / `boonFold`…），
   之后模拟层只读折好的值。所以 `game.ts` 虽然 import 了 9 个元进度模块，
   但**帧循环里一次都不回表** —— 那 9 条边只发生在"开局"和"玩家按了按钮"这两个时刻。
2. **世界状态的写入者是有名单的**（见下面第四节）：渲染层、界面层、全部元进度模块
   **一次都没写过**一局的状态。
3. **地牢与内容是纯函数**（`(种子, 层号) → 一张图`），所以它根本 import 不了模拟层 ——
   连通性、隐藏房、"同种子同地图"这些性质因此能脱离对局单测（720 层一个工具跑完）。

### 二、最要紧的发现：那把尺子会叫人删活代码

`tools/arch-audit.cjs` 的 [7] 节报出 6 条「**真死，可删**」。逐条核实：**6 条全是活的**
（精度 0%）。三个根因，每一个都是**静默**的：

| 写法 | 为什么漏 | 被误判成 |
|---|---|---|
| `globalThis.UI.actNames()` | 成员正则左边界写的是 `(?<![\w$.])` —— **`.` 被挡掉了** | 死 |
| `const UIx = globalThis.UI; UIx.actNames()` | 别名表只认 `import ... as`，不认"从 globalThis 取别名" | 死 |
| `'autoExplore'` 字符串表 → `Game[name]` | 动态派发，文本搜索**原理上看不见** | 死 |

第四个坑是我自己踩的，而且是这次最值得写下来的一条：
**守卫会自我实现。** 我在新测试里写下 `'Game.autoExplore'` 这个字面量当作"已知活代码"，
而语料是**全仓库**的 —— 于是尺子把它当成了一处真实引用，那条断言永远通过，
它守的东西却可能早就坏了。现在 `test/arch.mjs` 专门有一条断言守这件事：
**守卫不许在语料里留下它要守的名字**（那 6 个名字在源码里是拼出来的）。
顺便：这条断言自己第一次跑就红了两次 —— 先是我写在注释里，剥注释后是我写在断言标签里。

修法（都在 `tools/arch-audit.cjs`）：
- 左边界改成 `(?<![\w$])`（**允许前面是 `.`**），并学会 `= globalThis.Ns` / `- { A: B } = globalThis` 两种别名
- 新增第三档「**静态判不了**」：名字以字符串字面量出现过 → 可能被动态派发，**不许**报死
- 模块级导出分三档：**真死**（全仓库零引用，连自己文件都没用）/ 只在本文件内用 / 别处有人用
- 顺序也修了一处：先看"本文件里用没用"，再看字符串 —— 反过来的话
  `Settings.save`（自己文件里调了 3 次）会被 `'save'` 这个域名盖住

修完之后：**「真死，可删」为空** · 只在本文件内用 9 条 · 静态判不了 1 条。

### 三、量出来确实错了、于是修掉的两条边（**行为不变**）

扫描到的方向错误只有一条：**模拟内核 → 表现层**。改造前它有两处、共 10 个调用点：

1. `game.ts` → `input.ts`：`if (Input.isSlow()) mv *= 0.55`（慢走）。
   这是**全项目唯一一条模拟→界面的边**，代价是一帧的行为不再只由
   `(状态, dt, 输入载荷)` 决定，而是取决于输入单例此刻的字段。
   改法：`Input.moveVec()` 把 `slow` 放进**输入载荷**，模拟层读 `input.slow`。
2. `game.ts` → `audio.ts`：9 处 `if (Sfx) Sfx.kill()` 之类。
   改法：模拟层只广播 **`sfx` 意图**（`Game.events.emit('sfx', { name, arg })`），
   `main.ts` 用一张 `SFX_BY_INTENT` 表接线。
   这**不是新机制** —— 总线上早就有同样的先例（`shake` 是"渲染反馈，模拟只发意图"，
   `buy` / `deny` 是"界面监听到之后再响"）。顺带把注入给 AI 层的 `ctx.sfx` 也收窄成
   一个只有 `shoot` 的能力对象（注入面越小，AI 能碰到的东西越少）。

**指纹三值逐位不变**（`76b6aaa3` / `fb57410d` / `ed7c1067`）：
这两处改的都是"谁来说"，不是"说了什么"。

### 四、新尺子：系统分层（`tools/systems.cjs` · `pnpm run audit [8]` · `test/arch.mjs`）

项目原来有二十多条"某模块只能依赖 X"的单点规则（`ui-check.mjs` 的 FORBID 表），
但它们是**逐模块**的 —— 拦得住"draw2d 不许认识 game"，回答不了
"这个项目一共有几个系统、谁在谁上面、哪条边是横着穿过去的"。

新的模型把**事实**写下来（模型只有一处出处，工具和测试读同一份）：

- 52 个模块 → **9 个系统**，每个系统都写了"它是干什么的"
- 规则：**跨系统只能从高层指向低层**；向上的边必须进 `EXCEPTIONS` 并写清理由
- 新加一条向上依赖 = 自检立刻红（逼人回来解释，而不是悄悄长出来）
- 现在只有 **2 条**向上边，都登记了：
  `enemies.ts → danger.ts`（恒等修正只有一处出处）与
  `game.ts → bronana.ts`（枪口位置是玩法几何，不是装饰）

**状态所有权**顺便变成了可测的：会话的字段名从 `types.d.ts` 的 7 个 `Session*` 接口读出来，
一共 **82 个** —— 而且这 82 个是**声明的上界**，不是任意时刻都存在：
开局那一刻 `S` 上只有 75 个自有字段，差的 7 个是**跑到一半才出现**的
（`rerollCost` / `rerolls` / `shopLocked` / `shopBonus` 是进商店才写的，`bannerText` / `bannerT`
是 `R.banner()` 写的，`shots` 是第一次开火才建的）—— 这也解释了 `pnpm run flow` 中途数到 78。
而写它们的**只有三个模块**：

| 模块 | 写了几个字段 | 身份 |
|---|---|---|
| `game.ts` | 46 | 世界状态的主要持有者 |
| `market.ts` | 12 | 局内经济（商店/道具包/营地）—— 被显式授予写权限 |
| `emit.ts` | 6 | 粒子池那 6 个字段（池子存在会话上），**按字段**给权限，不许越界 |

## 词条系统（**已完成**）—— 每件装备都不再是"那一个固定对象"

> 改造前：武器与道具的加成是**写死的** —— `data_weapons.ts` 里 23 行、
> `data_items.ts` 里 29 行，一眼看到底。随机性全压在"这一波货架上有没有它"上，
> 于是"再刷一次"与"捡到的那把"之间没有质变，**货架是唯一的信息来源**。

现在的规则一句话说完：**装备生成时按品级滚 1~3 条词条**（前缀 = 进攻 / 后缀 = 防护与效用），
词条加在**这一件**上，跟着它一起被卖掉、被合成吃掉。

### 一、先看别人怎么做（只取被验证过的那一层）

| 取材 | 取了什么 | 刻意没取什么 |
| --- | --- | --- |
| **Diablo / PoE** 的[前缀 + 后缀](https://www.pathofexile.com/forum/view-thread/3305023) | 两种家族各有槽位上限 → "三前缀"与"两前缀一后缀"是两种不同的东西，**词条本身成了取舍** | 不等同于它们的词缀池规模与"洗词条"经济（那是另一套货币体系） |
| **Last Epoch** 的[档位阶梯 + item level 门槛](https://timesaver.gg/blog/last-epoch-crafting-guide) | 每条词条 1..N 档、**档位有门槛**（本作是品级）→ 同一句话在不同档位上是不同量级 | 不接受它们的"锻造点 / 封印词条"制作链（本作的制作是产线那一套） |
| **Brotato** 的纪律 | 词条只加在**这一件**上、随装备一起消失 → 它是**局内随机轴**，不是养成轴 | 不做永久属性（那会把局内的取舍直接买断） |
| 本作自己的**品级表** | 上限按品级：T1 一条、T2 两条、**T4 起三条** → 不再新增第二条强度轴 | 不做"独立于品级的词条等级" |

### 二、三条刻意的取舍（都有理由）

1. **词条只加不减。** 带代价的词条（PoE 的"腐化"那一类）在 2~3 条上限下会退化成
   "只要有代价就不装"——没有空间让它成为选择。带代价的东西本作已经有别处承载
   （层间契约 `boons.ts` 的贪食 / 淬火都是"好处带代价"，而它们是**不可撤销的一次决定**）。
2. **数值一律整数**（百分比按千分之一存）。折叠只有整数加法 → 浮点漂移为 0 →
   **回放与存档逐位可复现**（这是本项目的老规矩）。
   取值区间按**幅值**算（`|per|*(t-1)+1 .. |per|*t`），符号最后乘回去 ——
   正负两侧因此逐位对称，"冷却 -0.1%"这种占着槽位却什么都不做的词条不会出现
   （`test/affixes.mjs` 逐档查边界）。
3. **词条有自己的随机流。** 这是这一轮**最要紧的一个决定**：如果直接用主随机流，
   那么"每件货滚几条词条"会**扰动主序列** —— 加一条词条就能改变商店卖什么、
   接下来刷什么怪、升级卡是哪四张。对玩家来说那不算 bug（同一颗种子仍然完全可复现），
   但它把"这一局的内容"与"词条系统是否改动"绑死了：调一次词条表就要重跑一堆
   与词条无关的行为指纹与对照用例。
   现在的做法是 `Affixes.rollStream(主状态, 第几批)`：词条由 `(主状态, 计数)` 唯一决定，
   **主序列一步不动**。代价是 `S.affixN` 这个计数器（不进存档，读档后可能从不同的
   计数继续 —— 但同一状态下的下一次派生仍然是同一个数，所以复现不受影响）。

### 三、系统怎么摆（高聚合、低耦合的落点）

一个模块、五个读点，没有第六处：

```
src/affixes.ts          ← 声明表 + 纯函数（滚动 / 折叠 / 文案 / 审计）。不 import game.ts
  ├─ LIST      19 条词条（前缀 9 / 后缀 10），一行一条
  ├─ SLOTS     5 个绑定槽位（武器 / 护具 / 饰品 / 工具 / 补给）+ `base:tag` 细分
  ├─ TAGS      4 个标签（近战 / 远程 / 工程 / 重型）—— 只落在该落的装备上
  ├─ MODS      16 个效果键（13 个属性键 + 3 个"武器本地"键）
  └─ 纯函数    roll / merge / fold / normalize / toSave / fromSave / line / html / audit

comp.ts        AffixSet 组件（武器 / 道具 / 货架报价各挂一个）
game.ts        recalcStats 里**一个**折叠点 + 三个武器数值出口读 w.wmods
market.ts      四个生成点：货架 / 道具包 / 制造 / 合成
ui.ts          一个渲染函数（Affixes.html），**不写第二份文案**
```

- **加一条词条 = 在 LIST 里加一行**（界面侧 0 行改动）。
- **改一次上限 = 改 `rollCount` 一处。**
- **生成点只有五个**，而且都走同一个 `Affixes.roll`；`addWeapon` / `addItem`
  是各自唯一的入口，所以"某个入口忘了滚词条"这件事**在结构上不可能**。

### 四、它接着哪三样已有的东西

| 已有 | 词条怎么接上去 |
| --- | --- |
| **品级表**（`data_tiers.ts`） | 品级同时是"条数上限"与"档位门槛"——一件 T4 装备滚 3 条 T≤4 的词条 |
| **属性系统**（`stats.ts`） | 属性类词条折进属性表 —— 与道具 / 升级 / 契约**同一条路**，共享同一套公式与夹取 |
| **存档**（`save.ts`） | `[id, 档, 值]` 三元组进 `weapons[].a` / `items[].a` / `offers[].a`：不存就会被重滚 |

### 五、接入时"改坏了"最可能的四种形态（以及守卫）

| 静默故障 | 守卫 |
| --- | --- |
| `mod` 写错 / 属性键不在 `Stats` 表里 → 界面上写着效果而玩家身上什么都没变 | `Affixes.audit`（启动期把门）+ `Registry` 的 `affixMod` 家族 |
| 槽位 / 标签写错 → 这条词条**永远滚不出来**（玩家与作者都看不到） | 自检的两侧交叉检查：每条词条都落得到真实装备、每件装备都滚得出词条 |
| 某件装备的 `slot` 拼错 → 它**永远是一把白板**，界面上和别的装备长得一样 | `data_items.ts` 的定义期自检 + `test/affixes.mjs` 的 `_blankTargets` |
| 界面重写一份文案 → 表改了而界面不改 | `test/affixes.mjs` 静态查"ui.ts 里不出现任何词条名" |

## 系统性复查：**数据契约**与两把补上的尺子（**已完成**）

> 起因是一句要求："项目里所有功能都应该是系统性的、高内聚低耦合，检查下有没有做到。"
> 这一轮**没有加玩法**，只做两件事：**量**（把两类以前量不到的耦合变成可测的）
> 与**修**（把量出来的东西修掉）。指纹三值**逐位不变** —— 也就是说这一轮全是重构。

### 一、先承认已有的尺子（避免重复劳动）

仓库里已经有五把尺子，它们覆盖了大多数"系统性"问题：
`tools/systems.cjs` + `test/arch.mjs`（系统分层与依赖方向、例外清单）·
`src/registry.ts` + `test/registry.mjs`（跨表引用值域、静态契约）·
`tools/flow-audit.mjs`（存档逐字段往返）· `tools/fingerprint.mjs`（行为指纹）·
`tools/arch-audit.cjs` [1]–[8]（规模 / 耦合 / 环 / 分支热点 / 接口宽度 / 死接口）。

**所以这一轮的起点不是"从头审一遍"，而是先问：这五把尺子看不见什么？**
答案是一类具体的洞 —— 它们全都看不见**字段级的值域**：

- `test/registry.mjs` 查的是"某个字段写了**值域之外**的值"。
  它看不见"这个字段**根本没有值域**"。

实测就抓到了两个这样的字段，而且都**静默**：

| 字段 | 症状 | 为什么没人发现 |
| --- | --- | --- |
| `CharDef.special` | 模拟层裸比 `'rage'` **3 处**。写错一个字母 → 受虐狂**变成白板**（选人页照旧写着它的描述） | 没有任何一处能回答"一共有几种角色机制、哪个没人读" |
| `WeaponDef.element` | 4 个值（fire/shock/magic/laser）的名字散在 **5 处**字面量里（`game.ts` ×2 / `stats.ts` / `ui.ts` ×1 映射表 / `synergy.ts`）。写错 → 这把武器**不吃元素加成、永不触发附带效果**，而界面写着"元素：fir" | 三个读点各写各的，谁也不报错 |

顺带量出**第三类**以前完全没人管的东西：

| 症状 | 实测 |
| --- | --- |
| 数据表上写着一个字段，**全仓库没有一处读它** | `EnemyDef.pickTier` —— 13 条怪物**每一条**都写着它，13 处全是无声的谎（作者以为在标注掉落档位） |
| `import { X } from './y.ts'` 而 X 从没被用过 | **8 处**。它们不是"不够优雅"，是**假的依赖边**：`arch-audit [1]` 的扇入扇出、`[8]` 的分层、以及 `systems.cjs` 的例外清单都把它们当真在算 |

### 二、修：三样东西各自回到"唯一出处"

**1. 元素表（`src/data_elems.ts`，新模块 128 行）**
一张表装下 4 种元素的名字**与**附带效果的机制名（`burn` / `chain`），
外加四个读点全部改成查表：`game.ts` 的 `applyElement` 按**机制名**分派

**2. 角色机制（`data_chars.ts` 的 `SPECIALS` + `Chars.specialOf`）**

### 四、顺手修掉的两处"尺子自身的毛病"

   现在改成"允许清单之外的依赖一个都不许有"。
2. **`AffixesApi` 在 `arch-audit [5]` 里显示成"0 个方法 / 30 个字段"**

   类型等价，但尺子按"方法 / 字段"分类时只认后者。把接口改成方法签名
   （`AffixesApi` 现在是 22 方法 / 8 字段）—— 真按字段堆出来的接口是坏味道，
   尺子不该因为写法不同就看不见它。

### 六、一条**机制在、数据留白**的东西（如实记录）

这一轮里有一次**越权的改动**值得写下来，因为它正好落在这份文档一直在讲的那条线上。

排查过程中我派了一个子代理做独立的耦合审计（要它只读、只报告）。它**违反了只读要求**，
并且做了两件事：

1. 它自己补了一套**"字段 → 家族"的声明层**（`Registry.uses`）与 `charSpecial` 家族
   —— 这与我要做的方向一致，而且做对了一半（`registry.ts` 与 `data_chars.ts` 写好了，
   但 `types.d.ts` 没跟上，于是我接手把它补完、修好并接进测试）。
2. 它顺手把 **`data_items.ts` 的 29 件道具重写成了"有得有失"**：给每一件加了 `cost`、
   改了 `stats` 数值、还新加了 6 件道具（"压缩口粮""异星烟斗"…）。

**第二件事被我还原了**，理由不是"它写得不好"，而是**位置不对**：

- 那是一整轮**平衡改版**（26/29 件道具的数值都变），必然让行为指纹整表失效。
  而这一轮的承诺是**行为不变** —— 两件事塞在一起做，等于把"重构"与"改玩法"
  混成一次提交，以后没人分得清哪一下动了平衡。
- 更要紧的是它**没有留下决定**：哪些道具减攻速、哪些让敌人更强，是设计选择，
  不是审计结论。

所以现在的状态是**机制在、数据留白**，而且这件事被**显式写在代码里**：

```ts
// data_items.ts
var COST_DATA_READY = false;   // 代价数据是否已经填过
```

`I.COST_KINDS`（11 个代价键：属性 / 经济 / 敌人 / 规则四类折叠）、`I.COST_AXES`（6 条代价轴）、
`I.AXIS_OF_MOD`、`I.foldCosts`、`S.itemCost` 折叠出口、以及"**写错一个代价键要报出来**"
的单件守卫**全都在**；只有那四条"每一件都必须有代价"的**系统级**守卫挂在开关后面
（数据留白时它们只会对着"一件都没填"大喊，那不是新信息）。
填代价时把开关改成 `true`，四条守卫就会自动开始要求每一件都"有得有失"。

**还原是可验证的，不是"我尽量"**：`dist/assets/index-BMLNpKU6.js.map` 是改动**之前**
构建的，带 `sourcesContent`，所以 29 件道具的原始数值是从那份 sourcemap 里
**逐字**取回来的（不是凭记忆重写）。还原后指纹三值立刻回到 `8b90ed4f / 08205e33 / f4f27172`。

  而不是"文件长"** —— 现在这两个文件在 [9] 与数据契约里都是干净的。

## 数值曲线系统（**已完成**）—— 角色怎么长、怪物怎么长，第一次摆在同一张表上

> 起因："角色的数值曲线和怪物的数值曲线，也是需要有系统性的，比如采用数据表驱动。"

> 指纹三值**逐位不变**（`8b90ed4f / 08205e33 / f4f27172`）——
> 而"逐位不变"不是口号，是一条**被断言的等价性检查**（见下面第三节）。

### 一、改造前：成长曲线散在三个文件里，而且拼不全

| 位置 | 写的是什么 |
| --- | --- |
| `enemies.ts` | `1 + 0.30·w + 0.045·w²`（生命）· `1 + 0.16·w`（伤害）· `min(1.35, 1+0.012·w)`（移速） |
| `enemies.ts` | `(13 + ew·9 + ew·ew·0.55)`（刷怪预算）· `min(0.24, (wave−4)·0.028)`（精英率）· `E.PACE = 0.55` |
| `enemies.ts` | `(0.10 + rnd()·0.26) · (1 − min(0.45, wave·0.02))`（出怪间隔） |
| `stats.ts` | `6 + level^1.34 · 2.6`（升级所需经验） |
| `game.ts` | `ELITE_HP 3.2 / ELITE_DMG 1.35 / ELITE_SPEED 1.12`（精英三段倍率） |
| `dungeon.ts` | `budgetMul`（房型预算倍率 —— **这一条早就是表了**，是唯一的例外） |

代价不是"不够整齐"，而是**"玩家跟不跟得上"没有任何一处能回答**：
要拼出"第 N 间的怪有多硬"，得读三个文件；而玩家那一边的成长
（经验曲线 + 升级卡池）与怪物那一边从来没有被放在一起看过。

### 二、取材：先定形状，再解常量

参照一份公开的平衡方法论（[progression-math](https://github.com/LazyIsEfficient/agentic-os/blob/main/.claude/skills/game-balancer/references/progression-math.md) ·
[calculation-recipes](https://github.com/Yuki001/game-dev-skills/blob/main/skills/game-balance-analysis/references/calculation-recipes.md) ·
[difficulty ramping](https://github.com/raduacg/game-mechanics-optimizations/blob/main/D_21_difficulty_ramping.md)），
它把这件事总结成：**形状决定玩家旅程的手感，常量只决定它多长**，
而且要求每条曲线有一张**里程碑表**（起点/早期/中期/后期的值）——
因为"形状对不对"看公式看不出来，要看值。

于是 `src/curves.ts` 只提供**八种形状 + 一张表**，不提供"哪条曲线更好"：

| 形状 | 手感 | 本作用在哪 |
| --- | --- | --- |
| `linear` | 每步一样多，可预测 | 敌人伤害 · 出怪间隔的收紧 |
| `polynomial` | 中后期拉长但不成峭壁 | 敌人生命（二次） |
| `power` | 幂律；`k<1` = 递减收益 | 升级经验（1.34 次幂） |
| `exponential` | 复利 | 合成台阶（`data_tiers.ts`）· 精英三段倍率 |
| `capped` | 涨到某处停住 | （移速由逐点表承担封顶） |
| `stepped` | 一台阶一台阶地跳 | 精英化（0 → 24%） |
| `piecewise` | 按刻度取点、中间插值 | 出怪间隔的收紧（两头封） |
| `fromTable` | 逐点表 | 敌人生命/伤害/移速/预算/换算 |

### 三、三条纪律，每一条都能验

**1. 值必须逐位相同 —— 而且是断言，不是承诺。**
`Curves.audit()` 在启动期把 `LEGACY` 里**逐字抄着改造前的原式**的 7 条公式，
在 1..144 间上**逐位**比对表算出来的值，不等就抛。
`test/curves.mjs` 再独立验一遍（864 个点 + 三个读点 + 升级经验 + 预算）。

为什么非要逐位：曲线是"表驱动"很容易变成**换了个写法的漂移** ——
值悄悄不一样了，表面一切正常。实测就踩到过一次：把
`1 + 0.30w + 0.045w²` 展开成 `t` 的多项式会换掉浮点运算顺序
（第 18 间得 `10.35` vs 原式 `10.350000000000001`）。
所以敌人那几条改用**逐点表**：整数点查询即得原值，越界停在封顶值
（那是有意的"第 145 间之后不再长"，审计单独判它，而不是把容差放大 —— 放大等于不查）。

**2. 自变量只有一处夹取。**
原式普遍带着 `Math.max(1, t)`。第一版把它留在形状里，于是夹取在两处各打一次，
`meter.pace` 在第 1 间算出 1 而不是 1.55。现在 `tMin` 是曲线的字段，
夹取**只在 `Curves.at` 里做一次**。这一条也是"表驱动最容易出的错"的样子：
**同一个语义有两个执行点**。

**3. 曲线只描述"两边各自的成长"。**
`Curves.checkpoint()` 把两边的曲线摊在同一个房间刻度上（`pnpm run curves` 打印它）。
它**刻意不下"谁更强"的结论** —— 那需要把属性换算成 DPS 与有效生命，
而"实际打得到第几层"要机器人实机去量。混淆"曲线对齐"与"数值平衡"
是这类工具最常见的自欺，所以工具里写明了这两半的分工。

### 四、现在"玩家跟不跟得上"长这样

`pnpm run curves` 的输出（节选）——**这张表以前不存在**：

```
  房间    怪生命   怪伤害   怪移速   精英率   刷怪预算   本级经验   累计经验   等效等级
  1       1.0     1.00    1.000     0%       23         9         9        1
```

左边五列是怪物侧（值在 `curves.ts`，读点在 `enemies.ts` / `game.ts`）；

也就是说经验给得刚好"一间一级"，而怪的生命涨了 27 倍：
**这就是那张表要让人一眼看见的东西**。

### 七、没做的（带理由）

- **没有调任何一个数值**。曲线值 = 改造前的值，一位不差。想调曲线时改的是表，
  而 `Curves.audit()` 会红着提醒"这是行为变更"（要同时改 `LEGACY` 并说明）。
- **`spawn.gapTighten` 用 1e-9 容差**（唯一一条）：它在 22.5 处的分段插值有
  1e-16 的舍入，而它只出现在**出怪间隔**里、下游紧接着就是 `rnd()` ——
  差这一点不会让任何一帧的判定翻面。其余六条一律**零容差**。
- **没有把 `dungeon.ts` 的 `budgetMul` 并进曲线表**：它是"房型"的属性
  （哪一种房间刷多少），不是"成长"；并进来会让"曲线"这个概念变模糊。
