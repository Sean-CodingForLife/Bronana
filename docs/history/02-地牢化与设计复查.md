## G3：随机 Boss 池（**已完成**）

原来全游戏只有 **1 个 Boss**（`giant`，id 还硬编码在 `E.buildWave` 里）。
现在是一池四只，而且"随机"落在**层**上，不是落在波上。

| Boss | 机制 | 玩家要做什么 |
| --- | --- | --- |
| 荒原暴君 `warden` | 缓慢压上 + 扇形 7 发 | 侧移绕开扇形，别被逼到墙角 |
| 掘地者 `digger` | **钻地**（免伤、不可选中、直线冲向你）→ 破土放一整圈 | 它钻下去时不要浪费输出，冒出来那一刻拉开 |
| 母巢 `brood` | 保持中距，按节拍**召唤**小怪 + 环形酸弹 | 先清小怪还是先集火本体，是个真选择 |
| 钟摆 `pendulum` | 按节拍沿一条弧线**扫射** | 考横移时机，不是考躲弹密度 |

### 三个设计决定

1. **随机落在层上**：`Enemies.bossFor(seed, floor)` 是纯函数 ——
   同一层永远同一只。这样地图、Boss、剧情碎片（`boss:warden|digger|brood|pendulum`）
   三者才不会各说各话；同种子 = 同一串 Boss，成绩码与每日挑战仍然成立。
   难度 9 的"双王"给的是**同一只来两份**，不是两只不同的（两条规则叠在一起会把
   "更硬"悄悄变成"更随机"）。
2. **四只的"应对方式"必须两两不同**：自检直接比较 `behavior/pattern` 组合，
   重复就报错。只改数值的"新 Boss"在数据上过不了这一关。
3. **界面不认具体 Boss**：关底血条按 `def.boss` 找，按名字显示；土堆渲染按 `burrowed` 标志。
   加第五只 Boss 不需要改界面。

### 一处必须写清楚的取舍

**掘地者钻地期间完全免伤**，而且这个判定挡在**随机数之前**
（`damageEnemy` 的第一行）。理由不只是手感：如果改成"打中了但伤害为 0"，
玩家对着土堆开火就会消耗暴击判定，**随机序列会随玩家行为漂移，回放当场分叉**。
子弹在候选扫描里也直接跳过它（连"命中"都不算）。

### 验证（`test/boss.mjs`，33 条）

- 池子规模 / 每只都标了 boss / 第一层就可能遇到 / 应对方式两两不同 / 引用都在 AI 注册表里
- 200 个种子后四只都出现过；同种子同层同一只；三层的 Boss 不会永远是同一只
- 进 Boss 房刷出来的**就是这一层那只**，普通房不记 Boss id
- 三条机制各自"真的存在"：掘地真的免伤且打不死、冒出来又能打；母巢真的召唤且只召唤声明表里的小怪；钟摆相位真的在推进且是一串弹
- 打倒之后 `S.bossesDown` + `bossDown` 事件都在；存档往返只收真有的 Boss
- 四只各自都能在真实对局里跑 12 秒、被武器打到、被打死

**行为指纹没有变**（`4a89e77d` / `62b9f577` / `21b2e870`）—— 三段固定对局都没走到
Boss 房，而 Boss 池只影响 Boss 房。这不是巧合，是"改动的范围 = 指纹变化的范围"这条关系的又一次验证。

## N2：剧情接线（**已完成**）

`story.ts` 原来只是"表和纯函数"，一局打下来它一个字都不会变。这一批把它接上了：

| 接的东西 | 怎么接的 | 在哪 |
| --- | --- | --- |
| **枢纽**（新屏幕） | 新状态 `hub` + 场景表 + `index.html` 区块 + `ui.ts` 渲染 + CSS 两栏；左边站人（有"!"=有新话），右边是他现在要说的话 | `game.ts` / `scene.ts` / `index.html` / `ui.ts` / `styles.css` |
| **台词推进** | 条件是**档案里的计数**（runs / wins / floor / fragments / bosses / secrets / endings + 4 个 flag）；说过的话记账（`said`），所以不是"越堆越长"而是"每次回来头几个人有新东西说" | `profile.ts` 的 `storyCtx/linesFor/say` |
| **碎片收藏** | 一局的**来源**换碎片：四个 Boss 各给一片、密室逐片给、事件首次见给一片、深井给一片；同一来源**一片只能拿一次** | `profile.ts` 的 `foldRunIntoStory` |
| **结局** | 条件达成即收藏（4 个，含隐藏的「回信」= 通关 + 12 片 + 下过深井） | `Profile.endingsSeen` |
| **层间旁白** | 翻层时打一句环境音（**不带条件**，所以不剧透任何东西） | `story.ts` 的 `NARRATION` + `ui.ts` 的 `floorEnter` |
| **图鉴剧情页** | 图鉴新增一栏：碎片 X/12、结局 X/4、遇到过的遭遇。**没找到的碎片只说"第几片"**；**隐藏结局连名字都不给**（显示"？？？"） | `ui.ts` 的 `renderStoryBlock` |
| **模拟层只报事实** | `RunSummary` 多四个字段（`floor` / `bossesDown` / `secrets` / `events`）：模拟层只报"碰到了什么来源"，不解释它通向哪片记录 | `game.ts` 的 `buildSummary` |

### 五个真 bug / 真坑（都是跑出来的）

1. **`storyCtx` 与 `endingsSeen` 互相递归** → 界面第一次刷新就 `Maximum call stack size exceeded`。
   修法：ctx 里的 `endings` 读**已经落账的**那几个，而不是现场重算的列表。
2. **`game.ts` 的一句注释里写了 `story.ts`** → 剧情那套测试的"模拟层不认识剧情"当场变红。
   修法：改掉注释（这条守卫是**故意的**，它连注释一起查 —— 因为"提到"就是耦合的开始）。
3. **12 片一局拿不满**（4 Boss + 4 密室 + 1 事件 + 1 深井 = 10）。这不是 bug，是设计：
   剩下两片要**再来一局**（第二条遭遇 + 第二次深井）。测试现在把这条写成了断言
   （"一局最多 10 片"），免得以后有人以为一次就能集齐。
4. **`levelups > 0` 是一条会时红时绿的断言**：机器人是"直线远离最近的怪"，
   材料掉落要靠走过去捡 —— 它捡到多少纯看运气（实测换一个种子就从 4 次变成 0 次）。
   现在升级链路**摆好条件直接验**（拨回战斗 → 经验给足 → 升级 → 卡被选掉 → 回战斗）。
5. **标题页的"!"不刷新**：枢纽里的新话是在**局外**产生的，标题页得跟着更新 ——
   挂在 `refreshContinueButton` 上（两个都是"从档案读出来的标题页状态"，放一处就不会漏）。

### 一局的"来源"能换到多少（从表里算，不是估的）

| 来源 | 一局能给几片 | 为什么 |
| --- | --- | --- |
| 四位器官（Boss） | 4 | 一层一只；下到深井那一层就是第 4 只 |
| 密室 | 最多 4 | 每层 1 间（二层起有概率 2 间），破墙才算 |
| 事件房 | 最多 3 | 一层一间（四层就是 4 间），**每条遭遇只给一次** |
| 深井 | 1 | 一局只给一片 → 集齐要**下两次深井** |
| **合计** | **一局最多 10** | 集齐 12 片需要两局（这是"真结局"的时间成本） |

### 验证（`test/hub.mjs`，48 条）

档案 ⇄ 剧情表的 id 对照与坏档防线（拼错的台词 id 会让那句永远"说过了"）· ctx 的每个数字
都能从档案算出来（含 `clocktower` 这条**据点 → 剧情**的边）· 来源换碎片（一片一次、给完为止、
第二局补齐）· **不剧透**（深层台词取不到、记录官要第一片才出现、隐藏结局连名字都不给）·
台词记账（说过的不再出现、`!` 会熄）· 四个结局的达成顺序（含真结局的前置）· 层间旁白
每层都有且不含剧透词 · 模拟层仍然一个字都不认识剧情 · 新屏幕接齐的五处契约
（状态机 / HTML / ui / CSS / 场景表 + 从暂停进能沿原路回那一局）。

构建：49 个源码文件 / `vite build` **49 模块 · 328.64 kB（gzip 121.81 kB）**；**33/33 套测试通过**；
**行为指纹依旧逐位一致**（N2 全在局外档案与界面层，模拟层只多了四个"报事实"的字段）。

## G5：深度（**已完成**）—— 限时房 · 层间契约 · 隐藏要素

G1–G4 把地牢立起来了，但它们都是"直的"：每间房按同样的规矩打、每层按同样的顺序走。
这一批加的是**三种弯**。

### 一、限时房（`⧗`，每层恰好一间）

一间**时限砍半**的普通房（`waveTime ×0.5`，怪还多 25%）。它把"时钟"从背景音变成主角：

| | 普通房 | 限时房 |
| --- | --- | --- |
| 时限 | 基准 | **半**（实测 17.7s → 8.8s） |
| 按时清完 | 材料 ×1.2 | 材料 **×1.8** |
| 超时 | 材料 ×0.8 | 材料 **×0.45**（剩下的怪照样狂暴） |

实测两档之比：普通房 **×1.52**、限时房 **×4.00** —— 也就是说在限时房里，
"打得快"这一件事的价值是别处的 2.6 倍。**保证每层一间**（而不是按概率）：
它是一种玩法，概率会让某些层完全没有它，玩家就学不会"这一间要抢"。

### 二、层间契约（`boons.ts`，新模块）

打完一层 Boss，在层间商店里抽 **2 条**、挑 **1 条**（不可撤销），它管下一层。
11 条契约，三组效果各有真实读点（**都不新增机制**）：

| 组 | 折进哪 | 例子 |
| --- | --- | --- |
| `enemy` | `S.wmods`（与难度/房型同一套键名与折法） | 猎场：精英 +10%、每间奖励 +50% |
| `econ` | 四个读点各读一次（材料收集 / 每间奖励 / 商店货架 / 折扣） | 矿脉：材料 +35% · 军械库：货架 +2、九折 |
| `stats` | `recalcStats`（与营地设施同一条路） | 淬火：护甲 +3、生命 +6、**移速 −8%** |

**实测（12 种子 survive，相对"不挑"）**：

| 契约 | 波次 | 材料 | 孢子 | 读法 |
| --- | --- | --- | --- | --- |
| 军械库 | +0.7 | +21 | +2 | 商店型：货架多了，间接变强 |
| 淬火 | +0.6 | +26 | +2 | 防御型：活得更久（代价是慢） |
| 壁垒 | +0.4 | +20 | +2 | 敌人的血少了 |
| 丰饶 | +0.3 | **+43** | +2 | 经济型：材料最多 |
| 猎场 | **−0.4** | **+36** | −1 | **风险型：用波次换材料**（这才是取舍） |
| 灵巧 / 钻机 | ±0 | +13 / −3 | +1 / 0 | **专精型**：对"没有任何闪避/工程学"的机器人等于没有 |

两条检查（与营地/天赋同一套容差）：
**✔ 没有支配性契约**（改前 ⚠ 淬火是纯增益，支配了所有其他条 —— 给它加了"更沉"的代价）；
**✔ 没有死选项**（改前 ⚠ 贪食、赌徒在三个指标上都不如"不挑" —— 代价压过了好处，两条都重调了）。

**诚实的部分**：灵巧/钻机这类"专精型"契约在**这个机器人身上量不出价值**，
因为它的装备是随机喂的、不会去堆闪避或工程学。它们对真人是有意义的
（契约的意义本来就是"对现在这套装备值不值"），但这一条**没有实测支撑**，只能算设计意图。

### 三、隐藏要素的跨局那一半

`secretsFound` 原来只是**这一局**里的一个计数。现在它进了档案，并挂在三条**隐藏挑战**上：

| 隐藏挑战 | 条件 | 解锁 |
| --- | --- | --- |
| 墙里有什么 | 累计发现 **6 间密室** | **隐藏角色「掘进者」** |
| 四个器官 | 打倒过全部 4 只 Boss | 武器「解剖刀」 |
| 收信人 | 解锁真结局「回信」 | 道具「开箱狂」 |

两条设计：
- **隐藏挑战没完成之前不列在图鉴里**（完成了才现身 —— "图鉴里突然多一条"本身就是一个发现信号）
- **隐藏角色没解锁之前连卡都不出现**（不是"锁着"，而是"不在"）；它有自己的起始武器（裂地锤）、
  属性方向（厚血/慢）、本职天赋子树（破墙者 / 【基石】地脉）与一段"过去"

跨局指标的接法：`Challenges.context(..., story)` 多收一份**探索进度**
（密室数 / 碎片数 / 结局数 / 器官数 / 最深层），由 `Profile.applyRun` 喂进去。
顺序也有讲究：**先并剧情、再评挑战** —— 否则"这一局刚好凑够 6 间密室"要等下一局才发奖。

### 四、改出来的一个真 bug（`undefined + 0.1 = NaN`）

`Boons.fold` 里每条契约只写自己用到的键，于是第一次 `out[key] + v` 是
`undefined + 0.1` = **NaN**。表现是"抽到猎场之后一只精英都不出"（`eliteChance` 成了 NaN，
`rnd() < NaN` 恒假），而界面上完全看不出问题。修法：第一次碰到某个键时先摆上恒等值。
测试里也钉了一条：折出来的敌人组键必须能对上 `danger` 的同名键。

### 五、收尾：道具套装（F 的后半）

F 那一批只做了**武器**的联动，"道具套装"一直缺着。这一轮补上，而且刻意**复用同一份表结构**：
`Synergy.ITEM_SETS`（不是新模块）+ `ofItems()`（与 `of()` 同构：数件数 → 取最高档 → 不叠档）。
区别只在"分组从哪来"：武器按 kind/type/element **天生**分组，道具没有天生分类，
所以成员是**显式声明**的 —— 也因此多一条守卫：**29 件道具必须件件有归属，且不能同时进两套**。

| 套装 | 主题 | 成员 | 最高档 |
| --- | --- | --- | --- |
| 拾荒 | 捡、运气、材料滚雪球 | 7 件 | ×4：收获 +22、每波材料 +14（走天赋 econ 那条路） |
| 装甲 | 厚起来，代价是慢 | 6 件 | ×4：护甲 +10、生命 +20、移速 −10% |
| 兴奋剂 | 快、疼、回得快 | 6 件 | ×4：攻速 +20%、伤害 +12%、生命窃取 +4%、护甲 −2 |
| 工具 | 工程与精度 | 10 件 | ×6：伤害 +20%、暴击 +8%、工程学 +14 |

**实测（12 种子 survive）**。第一张表看"每套的形状"，第二张是最干净的一对：

| 配置 | 波次 | 材料 | 孢子 |
| --- | --- | --- | --- |
| 四件不同套（对照） | 7.2 | 287 | 26 |
| 装甲 ×4 | **8.3** | **409** | **33** |
| 兴奋剂 ×4 | 7.9 | 354 | 31 |
| 工具 ×4 | 7.3 | 218 | 24 |
| 拾荒 ×4 | 6.7 | 383 | 26 |

| 同样三件，第 4 件… | 波次 | 材料 |
| --- | --- | --- |
| 在套里（凑成第 4 档） | **8.3** | **409** |
| 不在套里（停在第 3 档） | 7.7 | 362 |

结论：**凑成一套值 +0.7 波 / +47 材料**；四套的"形状"各不相同（装甲最能活、拾荒最有钱、
工具对随机配装最无用）—— 没有哪一套在所有指标上都赢。
**诚实的两条**：① 那个"最干净的一对"里两件道具本身的属性也不同（`charm` vs `coffee`），
所以 +0.7 波里含一点原始属性差；② 机器人是随机喂装备的，它**不会为了凑套装去挑货**，
所以这里量的是"凑成之后值多少"，不是"值不值得为它改购物车"。

### 六、验证

- `tsc`（web + node）**0 错**；**34/34 套通过**（G5 新增 `test/g5.mjs` 43 条；
  `test/synergy.mjs` 增到 6 节 49 条，含道具套装那一节）
- **行为指纹逐位一致**（`4a89e77d` / `62b9f577` / `21b2e870`）—— 三段固定对局既没走进
  限时房、也没走到 Boss 房，而这两样正是 G5 唯一动到模拟层的地方；道具套装在
  "0 件 / 1 件"时恒等，也满足指纹前提
- 平衡实测：限时房两档比值 ×4.00 vs ×1.52 · 层间契约（无支配性、无死选项）· 道具套装两张表
- 测试里顺手修掉的两处**测量错误**（都在 `test/g5.mjs` 里写了注释）：
  ① 用不同波号比时限（比出来的是基础时限的差，不是限时房的折扣）；
  ② `Game.step` 只作用在**当前会话**上，先建两个会话再回头量 → 量到的永远是第二个。
  这两条和"预建营地跳掉第 1 波"是同一类错误：**先怀疑测量**。

## 界面比例与"装得下"（**已完成**）—— 从"靠眼睛调"改成"量得出来"

> 触发这一轮的是枢纽那一屏：状态被塞进 232px 的窄列里，`.set-label{flex:1}`
> 被右边的值挤到只剩一两个字宽，"走过的局数"竖着排成一列。
> 修的时候发现**这不是孤例** —— 于是先把"界面到底装不装得下"变成可测量的东西：
> 新增 `tools/ui-shot.mjs`（Electron **离屏**渲染，窗口不显示）逐屏截图，
> 同时回收每个元素的 `getBoundingClientRect / scrollHeight`。

### 一、量出来的问题（1280×720，改动前）

| 症状 | 实测 | 根因 |
| --- | --- | --- |
| 角色页"起始武器"那一行看不见 | `char-detail` 内容 136 / 框 112 | 屏幕是 flex 列，面板默认 `flex-shrink:1`：装不下时被压扁，**下一个面板的背景正好把它盖住** |
| 图鉴三张长列表只剩一条缝 | 每个 `.codex-list` ≈ 28px | 五块内容抢一屏，`flex:1 1 auto` 只好平分 |
| 商店武器列压住"下一波" | `.shop-cols` 内容 588 / 框 460 | 面板不滚、`overflow:visible`：内容直接溢出到后面的元素上 |
| 暂停页菜单吃掉 420px | 8 个按钮竖排 | 按钮竖着排，高度全给了菜单（内容只剩一条） |
| 据点列表里出现 `**结构性**` | DOM 文本里真有 `**` | 数据表（stronghold.ts）的说明写了 markdown，界面原样打出来 |

### 二、装进去的四条规矩（写进 CSS 注释里）

1. **屏幕 = 顶栏 + 内容 + 底栏**：顶/底 `flex:none`（永不压扁），内容块
   `flex:0 1 auto; min-height:0` 并自己滚；整屏还装不下时整屏也能滚
   （以前 `.screen` 没有 `overflow`，设置页最后几行在矮窗口里**够不着**）
2. **不写死 `vh`**：`max-height:64vh` 忽略了标题与菜单占掉的约 330px，
   窗口矮于 ~980px 就装不下；现在内容吃"剩下的高度"，与窗口无关
3. **`hidden` 属性必须真藏得住**：作者样式里的 `display`（`.settings{display:flex}`）
   会盖过浏览器的 `[hidden]{display:none}` —— 商店的"层间契约"面板一直被这件事坑着
4. **矮窗口收空隙、不收字号**：`@media (max-height:700px)` 只收紧 `gap/padding`

## 拆掉四处"不好的设计"（**已完成**）—— 表驱动 · 拆上帝对象 · any 清零 · 启动期把门

> 起因是一句判断："**62 个扩展点、1986 条断言，但 ui.ts 不是表驱动的，game.ts 和 Session
> 是两个上帝对象，`any` 都堆在界面层**。" 这三条都对，而且都能量出来。这一轮把它们改掉，
> 每一条都配了**守卫**（不是"这次修好了"，是"下次长不回来"）。
> 改完发现还差最后一块，于是**第④条**也做了：把定义期自检从"测试期"搬回"启动期"。

### 一、先说清楚"系统化"的现状（避免自欺）

`tools/arch-audit.cjs` 是这个仓库的架构体检：模块规模、扇入扇出、依赖环、类型分支热点、
全局接口规模、`any` 用量、死接口。它给出的结论是**声明与审计做得好，执行时机不行**：

| 层 | 系统化程度 |
| --- | --- |
| 数据/玩法（怪物、AI、房型、难度、契约、天赋、据点、营地、挑战、剧情） | **表 + 折叠 + 定义期自检 + 专属测试**，62 个家族 / 645 条条目，跨表引用 0 问题 |
| 分层与依赖 | 47 个模块、依赖图无环、越层依赖由测试拦（`game.ts` 不认识渲染/界面/剧情） |
| 确定性 | 固定 dt + 种子化 RNG，三段固定对局当回归基线（指纹逐位一致） |
| **启动期校验** | 12 个模块写了 `audit()`，但**只有 scene.ts 会 throw**；其余在加载时被调用、返回值被丢掉（**§五 已关**） |
| **界面层** | 唯一还没表驱动化的大模块（85 处类型字符串分支，全在一个 switch 里） |
| **两个上帝对象** | `game.ts` 2757 行 / 扇出 22；`Session` 72 个字段平铺 |
| **类型漏洞** | `any` 45 处，其中界面层 15 处 |

### 二、① 界面层表驱动化

| | 改造前 | 改造后 |
| --- | --- | --- |
| 动作分发 | `switch (act)` **53 个 case / 380 行** | 两张表：`scene.ts` 的 `SCREEN_ACTS`（10 条"去某个界面"）+ `ui.ts` 的 **按屏分组的 10 张动作表**（44 条"要做事的"，合并成 `ACTIONS`） |
| 刷新分发 | `if/else if` 十连 | `RENDERERS` 表（10 条），对照 `scene.ts` 的 `REFRESH` 表 |
| ui.ts 类型字符串分支 | **85 处** | **20 处** |
| "按钮有没有接上"怎么查 | 各套件拿正则去 ui.ts 里找 `case 'x':`（脆：源码里出现 ≠ 真的接上） | `UI.actNames()` **运行时可枚举**，`test/_acts.mjs` 统一问它（6 个套件改用它） |

**动作处理器按屏分开**（`ACT_SHELL` / `ACT_SETTINGS` / `ACT_CHARS` / `ACT_SHOP` / `ACT_CAMP` /
`ACT_TALENTS` / `ACT_KEEP` / `ACT_HUB` / `ACT_CODEX` / `ACT_CHALLENGE`，9·14·1·6·3·4·1·3·1·2 个）。
拆开是有代价的：单张字面量里的重名是**编译错误**，拆成合并就丢了这个保护 ——
所以合并函数 `mergeActs()` 显式查重名并抛出，测试再验"每个动作恰好属于一组、没有杂物箱"。
（行数 2082 → 2154：多出来的是分组声明与合并逻辑，换的是可枚举的结构与那条查重。）

三条新守卫：
- **动作表 ⇄ 按钮**：index.html(44) + 动态生成(10) 的每个 `data-act` 都必须注册；表里每条都必须有按钮；两张表不许重名
- **重画表 ⇄ 场景表**：`scene.ts` 声明要重画的 10 个名字，`ui.ts` 必须都有渲染函数（对不上时那一屏永远停在旧内容上，且不报错）
- **分组 ⇄ 动作**：要做事的那 44 个动作每个恰好属于一组；分组不许出现"杂物箱"（单组 > 20 就拆）；`SCREEN_ACTS` 的值在 `Scene.validate()` 里定义期就查，还进了总账（family: `screenAct` → `state`）

### 三、② 拆上帝对象

**game.ts → market.ts（-239 行）**：商店 / 道具包 / 营地这一整块（价格折扣的唯一算法、
货架两个结构性解锁、刷新、锁定、两种局内货币）是**由界面驱动、只在 shop/camp 发生**的子系统，
与"每帧都在跑的模拟内核"不是一件事。切法与 `ai.ts` 同一套路：**能力由 game.ts 注入**
（`MarketCtx` 只有 8 样东西），本模块不 import game.ts，依赖图仍然无环。

**Session：72 个平铺字段 → 7 个命名组**（Core / Camp / Market / Dungeon / Wave / Ents / Debug），
`interface Session extends …` 只是个空并集。守卫 `test/persist.mjs [2b]` 抓三件事：
没有一个字段是散装的（直接写在 Session 里）、没有被两组同时声明、运行时会话的字段都在组里。

**这条守卫第一次跑就抓出了三个字段**——这就是它存在的意义：

| 字段 | 情况 | 处理 |
| --- | --- | --- |
| `S.shop` | **全仓零命中**的死字段（真正的商店状态在 `offers`/`levelCards` 里） | 删掉 |
| `S.itemSets` | 道具套装的折叠结果，一直在用，但类型里没写 | 补进 `SessionCore`（挨着 `synergy`） |
| `S.nextId` | 实体 id 计数器，一直在用，但类型里没写 | 补进 `SessionEnts` |

### 四、③ `any` 清零（并设上限）

根因是一条签名：`U.el(tag, cls?, html?): any` —— 一个 `any` 生出了界面层十几个 `any`
（`var b: any = U.el('button', …)`）。改成 `HTMLElement` 之后，那些注解全部删掉；
顺带拆开了 ui.ts 里混在一个 `Record<string, any>` 里的**三本账**（节点 / HUD 节点 / HUD 值缓存），
并把 `var b: any` 换成真正的类型（`HTMLButtonElement` 等）。

结果：**界面层 15 → 0**，全仓 45 → **31**（剩下的都是外部边界：webkit 前缀 API、组件系统的
动态字段表、效果键的两种取值形态）。`test/persist.mjs [2c]` 给了**每文件预算 + 总数上限**
（总数上限 = 预算之和，不另写魔数）——想加一个 `any`，得先改那条测试，那一步就是评审。

### 五、④ 启动期那把门（最后补的一块）

改造前：9 个模块在加载时调 `X.audit()`，然后**把返回值丢掉**。后果很具体 ——
一张表写错了（某个效果键没人读、某个 id 指向不存在的条目），程序照样能起来，
只是**某条效果悄悄不生效**；唯一的发现途径是"有人跑测试"。护栏存在，但不在必经之路上。

现在 `src/selfcheck.ts` 是这道门的唯一入口，三件事：

1. **各模块注册**（`SelfCheck.register('Dungeon', Dungeon.audit)`），不再自己算完丢掉 ——
   注册是声明，跑不跑由启动流程决定。共 **11 项**：
   `Dungeon·Boons·Story·Synergy·E·Camp·Stronghold·Scene·Talent·Season` + 内置的 `registry`（跨表引用）
2. **入口调用**：`main.ts`（浏览器）与 `cli.ts`（命令行）启动时 `run()`；
   任何一条不过就抛**一个把全部问题列全的错误**（不是只抛第一条），
   浏览器里还会画一张**能读的失败页**（白屏对谁都没用）
3. **不是表检查的那些明确排除**，而不是让正则去猜：`Comp.audit(e)` 是对单个对象、
   `Emit.audit()` 查的是运行期池、`Registry.audit()` 是内置的跨表引用 ——
   三条都写在 `test/persist.mjs [2d]` 的例外表里，新增"表自检"忘了注册就会红

**这道门当场抓到的一个真问题（值得记）**：命令行入口是"只有模拟层"的构建，
渲染层家族（怪物造型 / 道具图标 / 武器造型，由 sprites.ts 注册）根本没加载，
所以全量跨表检查会报 **147 条假警报**（实测）。于是 `scan/run` 有了
`registry: 'full' | 'partial' | 'off'`：浏览器与测试用 `full`，
命令行用 `partial`（只查"目标家族已注册但值不在里面"——那才是真的写错了）。
把这件事写进代码注释与这里，是因为**"全绿"和"报了 147 条"之间差的正是构建边界**。

### 六、顺手修掉的一处**flaky 测试**（测量错误）

`test/smoke.mjs` 的"击杀数 > 20"用 `Game.newRun('ranger')`（不传种子 → `Date.now()` 当种子），
于是每次跑的结果都不一样，实测撞到过**刚好 20**。已钉死显式种子（329 杀）。
同一类问题的教训再记一次：**先怀疑测量**。

## 流程与逻辑复查（**已完成**）—— 从 0 到 1 再到 100

> 视觉之外还有一类 bug：**流程和逻辑**。它们不报错、也不一定看得见，
> 但会让"你以为在做的事"和"实际发生的事"不一致。这一轮换了一种查法：
> 不写逐项清单（清单之外的东西丢了不会响），而是问三个**结构性**的问题。

### 一、新工具：`pnpm run flow`（`tools/flow-audit.mjs`）

1. **存档幂等**：把一局玩到有内容的位置（打过架、进过商店、买过、刷新过、建过营地、
   挑过契约），`exportRun` → `importRun` → 再 `exportRun`，两次存档必须**逐字段一致**。
   任何"读档时重掷 / 重置"都会在这里露出来。
2. **随机流接着走**：记下存档时的随机状态，另开一个 rng 放到这个状态试抽 5 个
   （那就是"继续玩会抽到的 5 个"），读档后必须抽到同样 5 个。
3. **回放保真**：录一局（含挑契约）→ 带子里必须有那几条命令 → 放回去必须真的生效。

### 二、它抓到的六条（全部已修，都有实测）

| # | 症状（玩家视角） | 实测 | 修法 |
| --- | --- | --- | --- |
| 1 | **读档后随机流从头开始** —— 商店/选卡/刷怪走的是"这一局开头那条序列"，与"没存过档接着玩"不是同一局 | 继续玩应抽到 `0.179 0.745 0.739 0.365 0.266`，读档后实抽 `0.847 0.500 0.847 0.268 0.609` | `U.rng` 暴露 `state()/setState()`；存档带上 `rndState`，读档**最后**恢复（早恢复会被"重新长地图"吃掉） |

### 五、"点下一关直接就跳关了"—— 三个叠在一起的房间流程 bug

玩家报的是这一句。查下来它是**三个**问题叠出来的，而它们全都被"每一步都看不出错"掩盖着。

| # | 根因 | 表现 |
| --- | --- | --- |
| 7 | `autoExplore`（"下一波"按钮）**只沿路径走一步**。目标在三格外时，玩家停在中间某间**已清**的空房里 | 地图上没怪、商店没开、按钮也不在那一屏了 —— 感受就是"点一下跳关了"。实测种子里程：`event → start(空房)` 之后就卡住 |
| 8 | `goRoom` 对**已清**房间也无条件 `startWave(wave+1)` | 走过走廊也算一波：波次 +1、白拿一份"每波到账"（建材 / 天赋材料 / 营火回血 / 免费刷新），还在一间地图标着"已清"的房里刷出一整波怪 → 两间已清房来回走就是**可反复刷的循环** |
| 9 | `autoExplore` 把关底房当成普通"特殊房"参与比较（`isSpecialRoom` 对它返回 true） | **距离并列时优先进关底** → 打完 Boss 直接翻层，这一层剩下的房间全没了。实测 seed 777：带着 3 间没走就进了关底 |

修法（三处，都在房间流程里）：

- **关底最后**：`autoExplore` 分两轮挑房（先非关底，实在没有才去关底）——这正是它注释里本来就写着的行为，
  代码却没做到。抽出 `pickNextRoom(cur, rooms, bossOnly)` 把规则说清楚
- **一路走到那一间**：按路径逐跳前进，直到落在一间**未清**的房间上（中间的已清房间当走廊）
- **走廊不算一波**：`goRoom` 对已清房间只挪位置 —— 不开波、不发每波收入、不刷怪、不触发进门效果
  （那些是一次性的：重复触发本身就是"来回走刷奖励"的另一个口子）
- 顺带：`nextWave` 也允许"站在已清房间里"继续走（手动走回清过的房是合法的，按钮不该因此变死）

**证据**（`pnpm run flow` 的路线表，括号是"本层还剩几间未清"）：

```
seed 12345   event(10) → fight(9) → fight(8) → camp(7) → … → shop(1) → boss(0) → 第2层 fight(13) → …
seed 777     rush(7) → fight(6) → event(5) → camp(4) → …→ boss(0) → 第2层 …
7 个种子： "没走完就被送进关底" 0 / 168 次点击 · "按下去没反应" 0 / 7
```

修之前同一条表是：`event(10) → start(9) → 按下无反应（当前不在商店界面｜本层还剩 11 间未清）` ——
每一步都"合法"，合起来就是玩家报的那个现象。

**顺带被这一轮改动炸出来的一个真 bug**：`test/comp.mjs` 报
`实战.enemies[0] 游离字段 enraged` —— 超时狂暴标记 `enraged` 由 `overrun()` 写、渲染层读，
却**没在组件表里声明**。它以前不报，只是因为那套测试跑到的那局从没超时过；
我这次让机器人多打了几间（更容易撞上超时）才露出来。已补进 `EnemyCore` 的字段声明。

**守卫**（`test/rooms.mjs [8]`）：从商店出发一路点"下一波"，
**每一步都必须落在一间未清的房间上**、**每一步波次只 +1**、而且**这条路线真的要走好几步**
（实测 11 步，从 `event` 一路到 `boss(0)`）。

**诚实的一条**：**行为指纹没有动**（`4a89e77d`/`62b9f577`/`21b2e870` 逐位一致）——
因为那三段固定对局在帧数预算内从没走进"多房间自动行军"。也就是说，
这个 bug 对项目里最强的那张回归网是**不可见**的；它能被抓住，靠的是这一轮新加的流程体检。

### 六、重构："房间由玩家自己选"（Hades / 以撒那种）

上面那条修完之后，设计上还剩一个更根本的问题：**选择权在系统手里**。
打完一间，"下一波"替你按"最近的房间"自动走 —— 玩家没有挑房间这个动作。

先说清楚现状（省得把重构做重）：**门其实早就能自己走**。
`enterRoom(dir)` 有完整的校验（有没有门 / 这一间清没清 / 暗门破没破），
玩家走到门口就会过去，小地图上相邻房间本来就是可点的按钮，这两条都有测试守着。
坏的是**那个按钮**：它把"走哪间"这件事从玩家手里拿走了，还顺便制造了上面 §五 那三个 bug。

所以这一轮的重构是**把主行动换掉，而不是新造一套系统**：

1. **模拟层开一个口**：`Game.doors()` → `[{dir, roomId, type, name, icon, open, why}]`。
   规则（有没有门 / 锁着没有 / 暗门破没破）**只在这里判一次**；房型名与图标来自
   `dungeon.ts` 的房型表。这是"自己选房间"的**唯一数据来源** ——
   界面不重复判断、也不按房型 id 分支（这条纪律本来就有测试守着）。
   走不了的门也返回（带 `why`）：藏起来玩家会以为地图画错了。
2. **界面**：商店与营地的最上面多了一行 **门**（`门：自己挑一间  ⚔战斗  ⌂营地  ⚔战斗`），
   每扇门一个按钮，走的是与"走到门口"**同一条路、同一套校验**（`data-act="enter-room"`）。
   关着的门显示为禁用 + 原因（"墙上只有一道裂纹 —— 打穿它"）。
3. **"下一波"降级**：改名为 **「自动探索」**、缩成右下角的小按钮（保留给不想手动挑的人，
   也保留给无头跑局 / 回放 / 指纹 —— 测试与 CLI 仍然调 `Game.nextWave()`）。
   它不再是商店的主出口。
4. **顺手**：普通战斗房的图标从 `·` 改成 `⚔`（`· 战斗` 看着像图标没画出来）。

**刻意没做的事**（这是设计决定，不是漏了）：**商店仍然是"清完一间就开"**，
而不是像以撒那样"商店是地图上的一间房、你自己走进去才开"。前者是本作的经济节奏
（每间都有一次买卖机会，与 Brotato 的波间商店同源），改成后者等于重做整个 pacing。
关底门也**不锁**：想速通就直接进关底（那是一个明确的风险/收益选择）——
`autoExplore` 的"关底最后"只约束自动路径，不约束玩家。

**守卫**：`test/rooms.mjs [8]` 新增三条 —— `Game.doors()` 列出的门数与房型名齐全、
**关着的门真的进不去**、**开着的门真的走得进去**（列表与校验必须一致，
否则玩家会遇到"看着能走的门走不了"）。

## 合成树（**A + B 已完成**）—— 战斗 / 养成 / 经营 的第三条边

要求原话是"我全都要"，并且先定了调子：**战斗、养成、经营是铁三角**。
所以这一轮不是"加一个合成系统"，而是**把合成放在三条边的交点上**：

| | 合成在这条边上是什么 |
|---|---|
| **战斗** | 局内变强的另一条路：不靠运气买，靠**两个格子换一档** |
| **经营** | 一个真正的取舍：两件装备 + 一次购买机会 ↔ 一件更强的；回收价与货架都围着它转 |
| **养成** | 局外"图纸工坊"：花**合金**（只由合成产出）解锁**能力**，把合成这件事本身做大 |

### 一、先去看别人怎么做（不是自己拍脑袋）

| [土豆兄弟 · 武器品级与强化机制](https://www.9game.cn/tudixiongdi/7981557.html) | 品级四档（白/蓝/紫/红）；**两个同品级的同名武器合成高一档**；**身上还有空武器槽时不自动合成**（直接装上第二把），槽位满了才并进去；武器栏里可以手动合成或"回收"（低价卖出） |

### 二、A：局内合成（战斗 × 经营）

规则照抄原作的两条细节，因为它们各自解决一个真问题：

1. **两把同名同档 → 一把高一档**（T1+T1→T2 … T4 是终点）。
2. **还有空槽位就装上，不自动合成**；**槽位满了才并进去**。
   前者保证"同一局里能拿两把同型号的枪"，后者让合成成为"装不下时的出路"。
   买不了时给的理由也分两种："已经满档"与"槽里没有同名同档的另一把"。

关键设计（也是它必须存在的原因）：**`def.tier` 与 `w.tier` 分开**。
`def.tier` 是"这把武器通常出现在哪一档"（商店门槛看它），`w.tier` 是"它**现在**是哪一档"。
分开之后，"T4 的匕首"仍然是匕首 —— 造型 / 手感 / 家族 / 弹药类型全不变，
只是更强。于是合成**不需要** 92 个"每档一把"的武器条目，也不会把
`synergy.ts` 按家族算的联动打散。

数值是**台阶**（相对武器自己那一档取比值），不是绝对表：
`T1 1.00 / T2 1.50 / T3 2.10 / T4 3.00`（冷却 0.94/0.90/0.86、击退与射程同步小涨，
**T4 额外 +1 穿透**，但"本来就打穿一切"的喷火器/磁轨炮不吃这一口）。
绝对表会让 T1 武器升到顶也追不平 T4 武器的底子；台阶保证每一级合成的收益差不多 ——
这正是"要不要花两个格子换一档"这个问题的**可作答形式**。
木桩实测（同种子、同 30 秒、站桩打不死的小怪）：T1 192 / T2 312 / T4 684 伤害，
即 **×1.63 / ×3.56**（台阶 1.5/3.0 再叠冷却收益）。

顺手修掉的一处**旧账**：`w.dup`（"身上有同名武器 → 散射武器多打一发"）删掉了。
那个位置现在归合成 —— "再打一发"是最弱的一种解释（数值上几乎看不见），
而"合成一把更高品级的"是玩家真会去规划的路。同名武器仍然有用，只是用途从"多一发"变成"燃料"。

**回收**也跟着改了：旧实现按 `priceOf(def)*0.5` 收，会把一把吃掉四把匕首的 T3 匕首
按 T1 的价钱收走（= "合成之后就再也别想反悔"）。现在价值 = `底价 × 2^抬升档数`，
所以"买两把→合成→回收"永远不产钱（有专门的套利守卫）。

### 三、B：图纸工坊（养成）—— 局外第三条腿

局外原本已经有两条腿，各自解决不同的问题：

* **据点（孢子）**：改这一局的**规则与容量**（货架格数、折扣、营地容量）
* **天赋（点数，按角色）**：只改**开局条件**（起始属性与携带）
* **工坊（合金）**：改**合成这件事本身** —— 能合什么、怎么合、回收多少、货架多宽

**合金只有两个来源**，都在合成这条链上：

1. 局内每次合成：`+结果档位`（合得越高给得越多）
2. 每次结算的基础产出：`3 + 波次/3` —— 这一条是"够得着"的保证：
   一次都没合成的局也在推进，否则工坊对新手等于不存在（Dead Cells 的细胞同理）

与孢子**互不兑换**：两条曲线一旦能互换，就只剩一条曲线了。

九张图纸三阶（`src/forge.ts`），每一条都是能力：

| 阶 | 图纸 | 效果 |
|---|---|---|
| 入门 | 废料回收 / 合金萃取 / 备料 | 回收 50%→70% · 每次合成 +1 合金 · 开局第一把武器 T2 |
| 工艺 | 质检 / 异档熔接 / 备用货架 | 35% 的货架武器高一档 · 同名不同档也能合 · 每列多 2 件 |
| 大师 | 大师锻造 / 军械库 / 熔炉 | 合成结果额外 +1 档（T1+T1→T3）· 开局第一把 T3 · 结算合金 +25% |

前置链是**刻意的**：想拿「大师锻造」必须先走「异档熔接」那条线，
于是"我要不要练合成流"这个问题在开局前就要回答。点满整棵树 ≈ 10 局（每局约 14 合金）。

**没做的一件事，以及为什么**：原本想给「武器槽 +1」（最直觉的元奖励）。
查下来做不到 —— 武器挂在骨架的 **6 个固定挂点**上（`bronana.ts` 的 `SEATS`），
第 7 把武器没有挂点，画出来会叠在第 1 把上或者变成 NaN。
硬塞一把不如换一个同等份量的能力，于是那一条改成「备用货架」：
**找到"同名的另一把"的概率跟着涨** —— 它服务的还是合成，而不是绕开这个约束。

## 三根柱子各归其位（**制造这一步已完成**）—— 出击 / 制造 / 图纸

上一节把"合成"做在了**战斗那一侧**（顺手并两把），而按产品的定义应该是：

| 柱 | 玩家动词 | 它产出什么 | 它消耗什么 |
|---|---|---|---|
| **出击** | 探索、收集 | **材料 / 建材 / 旧装备** | 装备与道具（从制造来） |
| **制造** | 造 | **装备与道具**（现成的 24 武器 / 29 道具） | 材料 + 一张够档的图纸 + **一条产线的一波** |
| **图纸** | 解锁 | **能造什么**（档位）、产能、质量、回收 | 合金 |

三条接口全是**单向**的，而且是这次重构的全部内容：
`出击 → 制造`（材料/建材/旧装备）、`制造 → 出击`（装备与道具）、`制造 → 图纸 → 两边`（能造什么）。

### 一、删掉的耦合（这是实质）

| 原来的线 | 现在 |
|---|---|
| 营火每波回血 / 哨塔给炮塔 / 祭坛送刷新 → **经营给战斗加数值** | **删**。工坊的效果键只剩五个，**全部作用于制造**（省料 / 质量 / 多给一件 / 回收加成） |
| 工作台给商店打折 → 经营改战斗经济 | **删**。想让商店便宜就去点天赋 |
| 拾荒堆给 `harvesting` 属性 | **删**。工坊不进 `recalcStats` |
| 图纸「备料」开局第一把武器免费 T2/T3 | **删**。图纸给的是"能造什么"，强度由玩家自己造 |
| 合金由**合成**产出 | 改成由**回收旧装备**产出（合成只是加工已有装备，不产新东西） |
| 货架是购物中心 | 货架 = **应急成品（×1.6 溢价）+ 回收站 + 刷新/锁定**。造得起的比买便宜（×1.4） |

`camp.ts` 的自检里有一条**回归守卫**：往工坊里塞 `waveHeal` / `turretBonus` / `shopDiscount` / `stats`
里的任何一个，`Camp.audit()` 立刻报错（"耦合会从这里长回来"）—— `test/camp.mjs [9]` 会真的塞一次验证它抓得住。

### 二、制造是什么（用已有的东西，没有新元素）

- **配方不是手写的第三张表**：每一件已存在的武器/道具就是一条配方（`weapon:knife` / `item:coffee`），
  费用 = 它自己的原价 × 1.4 × 工坊省料（封顶 45%）。产物就是现成的 24 + 29 件。
- **工坊的 5 座设施 = 5 条产线**（位子只有 3 个）：熔炉（造武器省料）/ 配药台（造道具省料）/
  锻台（武器有机会高一档）/ 检验台（道具有机会多给一件）/ 回收炉（回收加成）。
  相邻组合（5 个成环）全部是制造向的：淬火 / 流水线 / 回炉 / 熬炼 / 釜底。
- **每波每条产线只能造一件** —— 这是经营**自己的回合**，也是"这一波投产线还是投自己"这个
  取舍的来源（空着的产线就是浪费，不需要额外的惩罚机制）。
- **档位门槛由图纸给**：默认只能造 T1；「基础图纸 / 工艺图纸 / 大师图纸」把上限开到 T2/T3/T4。
- 合金：`回收 + 结算基础产出(3 + 波次/3)`，熔炉再 +25%；点满整棵树 ≈ 10 局。

### 三、这不是新系统，是**搬家**

| 文件 | 这一步做了什么 |
|---|---|
| `craft.ts`（新） | 配方表（由武器/道具两张表长出来）+ 费用 + 档位门槛 + 质量 + 产线数；定义期自检 + 启动期自检 + 总账 |
| `camp.ts`（重写） | 从"给战斗挂被动的面板"变成**局内工坊**；效果键五个全部制造向；自检新增"不许出现战斗向的键" |
| `forge.ts`（改） | 九张图纸从"能力树"改成**图纸树**：档位 ×3、质量、产线、回收、合金；合金来源改为回收 |
| `game.ts`（改） | 删掉三处营地的战斗读点；新增 `craft / craftOptions / craftLines / craftFreeLines`；回收产合金；存档带 `craftUsed / craftCount / alloy` |
| `market.ts`（改） | 货架改为**应急价**（×1.6）；回收产合金；商店折扣不再读工坊 |
| `ui.ts` + `index.html`（改） | 营地那一屏重做成**工坊**：产线状态 + 配方页签（武器/道具，53 条里只列够档的）+ 设施/相邻组合 |

### 五、出击那一侧：房间从"选下一波"变成**收集的舞台**（**已完成**）

做完制造之后，"出击"这一侧的问题就露出来了：**房间只决定"下一步去哪"，不决定"拿到什么"**。
所以这一段做的是把已有的 10 种房型变成**不同的收集点**，并且让"什么时候去打关底"真的有得失 ——
一个新元素都没加，用的全是已经存在的东西（房型表 / 材料 / 建材 / 合金 / 已有的武器与道具表 / `bonusMul`）。

| 房型 | 改造前 | 现在（独占产出） |
|---|---|---|
| 宝箱 | 又一笔材料 + 建材 + 刷新 | **一件装备**（已有的 24 武器 / 29 道具里挑一件，武器放不下就退成道具）+3 建材 |
| 精英 | **什么都不多给**（只有更硬更疼）—— 于是没人有理由进去 | **一大笔材料**（`30 + 波次×8`）+2 建材。它是"拿命换这一笔"的选择 |
| 密室 | 材料 + 建材 + 刷新 | 材料 + 建材 + **合金**（图纸树唯一的局内来源）。它是全游戏唯一"进门要付代价"的地方（先找裂纹、花时间砸墙），独占产出给它最合理 |
| 补给 | 回血 + 建材 ×2 | 回血 + **建材 ×3**（建材是工坊的本钱） |
| 商店 / 限时 / 战斗 / 关底 / 入口 | —— | 不动（它们各自的角色已经清楚了） |

**顺手抓到一个"表里有、局里没有"的死内容**：精英房原先只在"剩下的死路"里按 45% 抽，
而死路的下限是 5 个、正好被 Boss + 四间特殊房吃光 —— 所以**精英房几乎从来没有出现过**。
现在它和限时房一样是**每层保证一间**（挑一间深的普通战斗房改掉）。

### 六、深度的回报：关底时机第一次成为"选择"而不是"顺序"

打 Boss 就结束这一层，没打的房间连同它们的东西全丢 —— 这个机制一直在，
可**"走光这一层"永远最优**（多打一间只会更多），所以那个"时机"从来不是选择。
现在每次收集的倍率随层数上涨（用已有的 `bonusMul`，事件房也在用同一个字段）：

```
第 1 层 ×1.00  →  第 2 层 ×1.46  →  第 3 层 ×1.92
（层号 × 层主题的 hpMul —— 主题的文案"菌毯洞窟：敌人更硬，孢子更多"以前只是文案）
```

于是两条路各自成立：**走光这一层** = 次数多（每一间都是一次收集 + 一次买卖 + 一个制造回合）；
**早打关底** = 单次更肥。`test/rooms.mjs` 里量了这条不等式：
早翻层的收益（×1.92）能超过多清两间（88 vs 169）。

### 七、实验台也跟着改了：机器人以前"只盖不造"

`tools/balance.mjs` 是量这三根柱子的地方，而它的机器人**只会建工坊、不会用**——
于是"工坊"在实验台上永远显示 `+0.0`（第一次跑出来就是这个数）。
现在它多了一个**制造回合**（能用空产线造得起里最贵的一件，武器优先；一件都造不起就空着），
不然"经营这一根柱子值不值"这件事在实验台上根本量不出来。

补上制造回合之后，实验台上的数字**第一次动起来**（12 种子 · survive 模式）。
再补一组**专门量"制造 vs 买"**的实验（`node tools/balance.mjs craft`）：

| 配置（同样两个设施、同样种子） | 波次 | 击杀/千帧 | 制造 | 商店件 | 孢子 |
|---|---|---|---|---|---|
| ① 从不制造（对照） | 4.1 | 8.7 | 0.0 | 3.5 | 12 |
| ② **只制造（不买货架）** | 4.3 | **12.6** | 4.6 | 0.0 | 13 |
| ③ **先造后买** | **4.9** | **13.5** | 4.5 | 1.3 | **15** |
| ④ 先买后造（机器人的旧默认） | 4.1 | 8.8 | **0.4** | 3.3 | 12 |
| ⑤ 只造道具 | 4.1 | 8.7 | 0.7 | 3.5 | 12 |

四件可读的事：

1. **制造真的能替代购买**：只制造（不买货架）波次 4.3 > 从不制造 4.1，而
   **击杀/千帧 12.6 vs 8.7（+45%）** —— 产线把材料变成了更强的装备，不是一块好看的菜单。
2. **顺序比"怎么盖"值钱**：先造后买 **+0.8 波 / 15 孢子**；而"先买后造"因为货架的
   **应急价（×1.6）先吃掉材料**，产线一整局只造出 **0.4 件**（几乎空转）。
   这既说明应急溢价在起作用，也是一条给玩家的提示：**想练制造就别先买**。
3. **摆法有价格**：同样三件设施、只是顺序不同，差 **0.3 波**；两件里最好的是
   「熔炉+锻台（淬火）」**+0.8 波**，而「检验台+回收炉」只有 +0.1。
4. **道具线现在偏弱**：只造道具 0.7 件/局（被购买挤掉），配药台/检验台单建 **+0.0**。
   这是下一步该看的地方 —— 要么道具不够重要，要么道具产线该换个定位。

（诚实标注：表里"每杀捡回"从 4.19 掉到 2.36，是**机器人在远处击杀、掉落没走过去捡**，
属于走位策略的副作用，不是设计问题。）

### 七、据点：从"数值穿透"收窄成**能力解锁**（**已完成**）

据点原来有 13 个修正键，其中三个是**把数字乘到别的柱子上**的：

| 删掉的键 | 原来做什么 | 现在 |
|---|---|---|
| `sporeMul` | 菌床给孢子产出 +35%（跨柱子的经济倍增） | 菌床改成 **`offlineLevel`**：它只回答"离线产出解锁没有、等级多高" |
| `rerollDiscount` | 钟楼让刷新价 −15% | 钟楼就是"每波免费刷新 +1/级"（README 原文里那一档"功能解锁"） |
| `campDiscount` | 工匠让工坊建造价 −15% | 工匠改成 **`refundFull`**：拆工坊设施**全额返还** → 摆法可以试错；L2 再给一条产线 |

补上的两条能力键：`refundFull`（拆了不亏）与 `offlineLevel`（离线产出的开关与等级）。
于是据点剩下的 11 个键**全部**是"能力 / 容量 / 目录 / 开局条件 / 养成层内的加减免费次数"：

```
startMaterials（开局条件）· shopSlots（每列货架）· freeRerolls（免费刷新）
campSlots（工坊产线）· refundFull（拆了全额返还）· offlineLevel（离线产出）
freeRespecs · bonusPoints（据点 → 天赋那条边）
workshop（刷新保底 T3+）· rangeItem（开局多带一件）· depot（商店必出在用的类别）
```

自检里加了一条**回归守卫**：`BLEED = ['rerollDiscount','campDiscount','sporeMul','shopDiscount','damage','maxHp']`
里的任何一个键出现在设施表里，`Stronghold.audit()` 立刻报错（"穿透会从这里长回来"）；
`test/keep.mjs` 会真的塞一次验证它抓得住。

### 八、同名合成住在哪（补一句）

它**不在战斗里**（战斗只负责探索与收集）：合成是制造那侧的一个动作，
在工坊/商店里做、不占产线的一波（因为它不消耗材料，只是把已有的两件并成一件），
而**合金只从回收来**。三根柱子的边界因此是干净的：战斗不生产，制造不探索，图纸不碰数值。

### 九、商店三栏齐了：原料 / 回收 / 应急成品

| 栏 | 做什么 | 为什么是它 |
|---|---|---|
| **原料** | **建材包**（材料 → 4 建材，越到后面越贵） | 建材是工坊的本钱，平时靠出击捡（每波 +2、宝箱/补给/密室）。这一栏是"我这一波就是要开工"的应急口，定价刻意不划算 —— 它买的是时间，不是资源 |
| **回收** | 卖装备 → 材料 + **合金** | 图纸树唯一的稳定来源（`salvageAlloy`），所以回收不是清垃圾，是"探索 → 解锁"那条链的入口 |
| **应急成品** | 货架上的武器/道具（×1.6 溢价） | 装备的主要来源是制造；货架只负责"等不了产线"的情况。"能买为什么要造"因此有答案：造得起的比买便宜（×1.4） |

### 十一、把 `S` 上类型（**已完成**）—— 一次静态检查暴露出的系统性隐患

复盘时说"快速静态检查有没有致命 BUG"，抓到的东西里最值钱的不是任何一个 bug，而是这一条：

> `src/game.ts:77` 是 `var S = null;` → **`S` 是隐式 `any`**。
> 那个 3100 行的模拟内核里，所有 `S.xxx` 的读取都不受 TypeScript 检查。

它当时**已经**放过一个真 bug：`S.fmods.bonusTier`（图纸改版时删掉的键）被
`fusedTier()` 一直读着，永远得到 `undefined`、恒等于 0 —— 行为无害，但那是一句
"读起来像有加成"的假话，而 `tsc` 全绿。

**做法**：`var S: Session = null as unknown as Session;`

- 先要**字段检查**，再谈 null 安全：代码里已经到处是 `if (!S) return` 前置守卫；
- 代价写在注释里：`null as unknown as Session` 是一次**有意为之的类型谎**，
  所以它必须配一条测试 —— `test/persist.mjs [2b-2]`：game.ts 里读的每个 `S.字段`
  都必须在 7 个分组里声明过（实测覆盖 72 个字段）。

**编译器接手之后立刻指出的三处**（都是真的、都不是崩溃型）：

| 问题 | 修法 |
|---|---|
| `newSession` 的字面量**少了 7 个必填字段**（`waveEnding`/`forceClear`/`textParticles`/`freeParticles`/`freeTextParticles`/`visCursor`/`textCursor`）—— 它们靠 `Emit.bind` 与 `startWave` 懒创建，于是"声明必填"和"初值缺席"长期不一致 | 全部在字面量里给初值（出生即齐全），`Emit.bind` 里的 `if (!S.x)` 退化成防御 |
| `UPGRADE_POOL` 的 `key` 被推断成 `string`，而下游要 `StatKey` | 声明成 `Array<{ key: StatKey; amt: number; w: number }>` |
| `Pickup.dead` **被写、被读、却没声明**（`containers` 的缺省 dead 判据读的就是它），而且不在任何组件里 | `Comp.define('PickupCore', { seed, value, dead: false })` + `Pickup.dead?: boolean` |

### 十二、这一轮还顺手修的三个真 bug（静态检查的产物）

1. **`craft()` 没有状态校验** —— 战斗中也能造装备（界面不画按钮，但接口允许）。已补 `requireStateIn(['shop','camp'])`。
2. **`craft()` 的提交不是原子的** —— 探路用配方原档位、而锻台/淬火会把结果抬一档，

3. **反馈缺口** —— `sell` 事件的提示没提合金、`craft` 事件根本没人监听：
   玩家永远看不到"回收产了多少合金""这次是不是淬火成功了"。
   而合金是图纸树唯一的稳定来源、那 25% 是锻台的全部价值。已补两个监听。

### 十三、"子弹会分叉"是怎么查出来的 —— 一次"事件只发不收"的反馈缺口

玩家报："我发现现在的子弹会分叉，怎么回事。"

**第一件事是把"分叉"变成可数的东西。** 一次扣板机产出多于一发，代码里只有两个来源：
武器自己声明的 `shots`，和道具「克隆装置」（`special: 'extraProjectile'`）。两把武器各打各的**不算**。
实测（14 把远程武器逐把钉住玩家与木桩，只取刚扣完板机那一帧的弹丸）：

| 情况 | 一次开火 | 张角（实测） |
|---|---|---|
| 手枪（未声明 spread） | 1 发 | — |
| 手枪 + 克隆装置 | **2 发** | 6.9°（未声明 spread 时的 ±0.06 弧度兜底值） |
| 变异手枪 `shots:2 spread:12` | 2 发 | 24° |
| 霰弹枪 `shots:5 spread:30` | 5 发 | 60° |
| 霰弹枪 + 克隆装置 | 6 发 | 60°（发数变多、张角不变） |

于是"分叉"= 上面这几种之一，**没有 bug**。真正的问题在下一句"怎么回事"——
玩家为什么会不知道自己身上多了这么一件东西：

> `applyRoomEntry()` 的返回值在**三处调用点都被丢掉**，而它发的 `roomEnter` 事件
> 一个监听者都没有（全仓 `.on('roomEnter')` 零命中）。
> 也就是说：**8 种"有内容"的房型给东西时，玩家一句提示都看不到。**

它的来路是这一轮出击侧的改造——宝箱房从"又一笔材料"变成了"白给一件装备"，
第 10 波起档位上限到 T4，实测 2000 次：武器 41.5% / 道具 58.5%，
其中**克隆装置 1.90%**。白拿一件"所有远程武器额外发射 1 发弹丸"，
确实看起来就是"子弹突然会分叉"。

**拍板（用户）：T4 保留在免费池里。** 免费装备就是宝箱房存在的意义，
而"看得见给了什么"这件事已经补上了——惊喜不等于莫名其妙。
（RNG 种子搅散同样拍板：**先不动**，只记在这里。）

**修法**：`ui.ts` 把 `roomEnter` 接到既有的 toast 上（普通遭遇房没有内容，`msg` 为空就不打扰）。
顺带把宝箱/密室/精英/补给那几句"我给了你什么"全都变得可见——它们以前都写在返回值里，没人看。

**守卫**（两处，都是这一轮加的）：

- `test/ui-check.mjs [7]`：8 种有内容的房型都必须报出自己给了什么 + `roomEnter` 必须有人收；
- `test/combine.mjs [10]`：14 把远程武器的"一次开火发数"、克隆装置是全游戏唯一加弹丸的道具、
  霰弹枪张角 = 2 × 声明的 30°、扇形以瞄准方向为中心（这就是上表那几行）。

**同一轮顺手量出来、但先不动的一条**（要动就得重定指纹基线，所以记在这里）：

> `U.rng` 的第一个输出对相近种子几乎恒定 —— seed 1000/1001/1002/1003 的第 1 个数
> 都是 `0.062`，200 个种子 200/200 落在 0.5 以下。也就是说"新建一局之后的第一个随机决定"
> 在相近种子上是同一个。修法是播种前先搅散（splitmix 一类），代价是全部行为指纹与
> 若干测试的期望值要一起重定 —— 它不产生错误行为，只产生"每局开头很像"。

### 十四、T5「神话」+ 一次"统一管理"的收口（**已完成**）

用户这一轮给了两句判断：**成型速度过快，加一档 T5（红色）**；以及
**"你有没有用设计表格来管武器/道具/物品？我认为需要统一管理"**。

#### 一、先回答"表格管理"这一问：哪里已经是表，哪里还散着

| 对象 | 现状 |
|---|---|
| 武器 24 把 / 道具 29 件 | **已经是"一行一件"**：数值、图标、档位、描述都在行里；`registry.ts` 的总账强制跨表引用（`icon`/`kind`/`tier` 写错当场报错） |
| **品级**（档位/名字/颜色/倍率/解锁波次） | **散在 6 处**：`Weapons.TIERS`+`TIER_MAX`、`Weapons.rollShop` 的内联阶梯、`Items.maxTierFor` 的内联阶梯、`game.ts` 宝箱房的内联阶梯 ×2、`ui.ts` 的 `tierName` 数组 ×2、`styles.css` 的 `--tier1..4` |
| 道具的 `special`（改机制的那一类） | **裸 if**：只有 `turret`/`extraProjectile` 两个，但没有任何表与总账 —— 写一个表里没有的机制名，这件道具**彻底没用**，而描述还在界面上写着效果 |
| 道具包的权重 | 数组写死 4 项、循环也写死 `i < 4`：**加一档会让新档永远开不出来，而且不报错** |

结论：**列表是表，档位不是**。档位这一层缺一张表 —— 所以"加一档要改六处，漏一处是静默的"。
这次先补这张表，再加档。

#### 二、做法

1. **`src/data_tiers.ts`（新）**：一行一档，六个读点全从它读
   （`name`→界面、`cls`→class、`wave`→`capFor()` 的解锁阶梯、`dmg/cd/knock/reach/pierce`→合成台阶）。
   `Weapons.TIERS === Tiers.LIST`（**同一份引用**，测试断言过）。
2. **道具的 special 收进表**：`Items.SPECIALS` + `Items.foldSpecials()` → `S.itemFx`（折一次，模拟层只读结果），
   外加 `itemSpecial` 家族：每件道具的 special 必须在表里，表里的每个键必须有人读。
3. **包的权重表长度跟着品级表走** + `Items.audit()`：加档时它会当场说"包种的权重表少了一项"。
4. **静态守卫**（`test/combine.mjs [1]`）：扫一遍 `src/`，档位名数组 / 内联阶梯 / 写死的上限
   **只许住在 `data_tiers.ts`**（并带一条对照样本，证明这套规则真的抓得到东西）；
   再逐档查 `styles.css` 有没有 `--tierN` 与那几条规则。

`lucky` 现在只在**档位真的被抬起来**时为真。

### 十五、地图体检：把"地图有没有选择"量出来（**已完成**）

#### 一、量出来的三条真问题

| 1 | **特殊房的落点是常量** | "四间特殊房（宝箱/商店/补给/事件）里最深的那支是宝箱"：**68~79%**；深度排名固定为 宝箱 0.90 > 商店 0.75 > 补给 0.57 > 事件 0.46。既然越深越好，**"往最深的那一簇钻"永远是最优解** —— 那是背下来就行的规则，不是选择 |
| 2 | 生成器写的"≥5 个死路"**从来没达到过** | 密室是在特殊房之后才凿的，而凿一间会把 2~4 个邻居从死路变成走廊 → 实测只剩 **3.06** 个；而死路正是"可以跳过的支线" |

1. **落点洗牌**：四间特殊房仍占**同一批最深的死路**，但"哪种房落在哪一支"由这一层的种子洗牌决定
   （Boss 仍然是最深的死路 —— 那是结构，不是偏好）。
2. **凿完密室再补一次死路**（深度封在 Boss 那一层）：把生成器写的下限真正做出来。
   顺手修掉它带出来的一个真 bug：补叶子时**不能接在密室后面** —— 密室的门全是暗门，
   接出来的叶子只有一条"要破墙"的路（900 层实测抓到 3 层"不破墙走不到的普通房"）。
3. **门牌不报身份**：未打穿的暗门显示为「? 裂纹的墙」，理由仍然是"打穿它"。
   线索只留一处（HUD 的「⚠ 右 墙上有裂纹」）：知道**这里有一处东西**，不知道**是什么**。

**一处试错（记下来，因为它证明测量比直觉可靠）**：第一版我把座位也随机了，

绕路的压力反而被抹掉了。所以改回"座位仍是那几条最深的死路，只洗牌"。

2. 第一版 A/B 比的是"旧的固定顺序"与"新的**某一次**洗牌"两个**单样本**，
   数字差很大（3.08 对 4.93）却什么也证明不了 —— 两者都是同一批座位的不同排列，
   期望值相同。正确的量法是量**规则**：宝箱的深度名次分布。

#### 五、守卫（新增 4 条，都在既有套件里）

`test/dungeon.mjs`：每层 ≥3 个死路的楼层 ≥95%（并报出实测均值与历史值）·
**反记忆断言**：宝箱在四间特殊房里最深那支的比例必须 <60%、四个名次各 ≥10%。
`test/rooms.mjs`：未打穿的暗门在门牌上必须是"裂纹的墙"，不能出现"密室"三个字。

#### 六、用户拍板之后加的三件（**已完成**）

三件都要，于是都做了。每一件都带一条**能失败的**守卫。

1. **一层之内的深度收益**（房间 `depth` 第一次进收益公式）
   以**本层的平均深度**为基准、每步 10%：实测浅端 −29% · 深端 +34% · **整层平均 0.0%**。
   第一版写的是"每深一步 +7%" —— 那等于给全局加约 20% 材料，而用户这一轮的抱怨里就有
   "成型过快"，加通胀只会更快，所以改成中心化：**这是梯度，不是通胀**
   （冲关底、跳过深处支线，真的会少拿）。
   守卫（`rooms.mjs`）：逐间取三层每一间的倍率 → 整层平均 = 该层的基准（±0.03）、
   第 3 层均值 ≥1.5、**最深那间 > 最浅那间**（三层分别 +0.2 / +0.6 / +0.6）。

2. **一局的特殊房分配**（`Dungeon.runPlan`：从"每层四类各一间"出发，层与层之间随机换 3~5 对票）
   总产出**与改造前完全相同**：每一类在本局仍然恰好 3 次。变的只是分布 ——
   实测 **71% 的层会缺四类里的某一类**（改造前恒为 0%，因为每层都是全套）。
   效果一眼可见：`pnpm run flow` 的路线表里 seed 4242 第 1 层出现**三间商店**、
   seed 20240922 第 1 层**两间补给**。
   守卫（`dungeon.mjs`）：每类恰好 3 次/局 · 分配可重复（地图要能按（种子, 层号）单独重建）·
   缺类的层占比落在 10%~60%（0% = 每层一模一样，100% = 乱套）。

3. **地图迷雾**：`Dungeon.visible` 只画 `seen` 的房间；进门看见"这一间 + 它的**非密室**邻房"
   （以撒那种：看见一格就看见下一格的门）。**可见变化：小地图不再一开局就显示整层。**
   两处必须一起改的地方：`autoExplore`（"下一波"按钮）改用**整层**选路 ——
   迷雾只决定画什么，不决定按钮能不能找到下一间；`warpTo`（测试/实验台的挪房）走同一套 `seeRoom`。
   守卫：`dungeon.mjs`（新层 0 间可见、看见一间只多出一间）+ `rooms.mjs [5b]`
   （入口 + 一圈 → 进一间长一圈 → 隔 3 间以上仍看不见 → 密室不在那一圈里）。

#### 七、这一轮的平衡复核（以及一句老实话）

`pnpm run bal craft` 重跑（12 种子 · survive），与上一轮记录的数字对照：

| 配置 | 波次（上轮 → 本轮） | 击杀/千帧 |
|---|---|---|
| 从不制造 | 4.1 → 3.8 | 8.7 → 7.9 |
| 只制造 | 4.3 → 4.3 | 12.6 → 10.7 |
| 先造后买 | 4.9 → 4.5 | 13.5 → 11.5 |
| 先买后造 | 4.1 → 4.4 | 8.8 → 10.1 |

**不能读成"变难了"**：房间布局换了，同样 12 个种子面对的是**不同的房型序列**
（这个工具自己的说明里就写着种子噪声 ±1 波）。能确认的是**结构没变**：先造后买仍然最强（4.5 波）。

**指纹三值仍然不变 —— 但这次要说清它测不到什么**：那三段指纹跑不出"波次结算"，
而这一轮改的恰好是波次结算里的倍率，所以指纹对它是**盲的**。
覆盖这一处的是 `rooms.mjs` 的那三条新断言（逐间倍率），不是指纹。

#### 八、没做的

- **地图尺寸/层数**（14.7 间/层 · 3 层）：没动 —— 一局的长度已经在 40 间上下，
  再放大会把"跑完三局"的门槛抬到不合理的程度。
- 死路补到"≥5"之后仍有约 5% 的层只有 2 个死路（生成器确实没有可长叶子的地方了）：
  没为它加特例，因为守卫现在量的是**占比**而不是"每层都必须"。
