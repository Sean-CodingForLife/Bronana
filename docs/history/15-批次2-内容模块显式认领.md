# 15 · 批次 2（前半）—— 42 个模块显式认领

## 一、为什么这件事值得单列

门 `engine-boundary` 一直在报一句话，语气是**提示级**：

> 既不是引擎、也不在数据表清单里的模块 **42 个**（它们**算内容**，但**没有显式认领**）

**那不是"分类完成"，是分类没做完。** 判据说得对（它们算内容），但**没有任何地方写下这件事** ——
于是任何人读这张表都会以为这个仓库只有 2 个内容模块。这与本项目记过的
「文档说了一道不存在的门」是同一类：**判据知道、而表不知道**。

## 二、怎么认领的（**同一组的理由写一遍**）

```
引擎 26 → 25 · 混合 4 → 4 · 显式内容 2 → 38 · 数据表 31 · 未显式认领 42 → 0
```

- **补认领为引擎 6 个**：`workspace.ts` · `rhi.ts` · `viewport.ts` · `text.ts` ·
  `storage_fs.ts`（⚠ 注明它的默认目录名 `~/.bronana` **还带着内容名**，是待修，不是干净的）· `crash.ts`
- **补认领为内容 35 个**，用**分组常量**写理由：
  `C.play`（玩法与对局 12 个）· `C.meta`（局外成长与经营 13 个）· `C.view`（表现与界面 7 个）·
  `C.host`（宿主入口 3 个：`main` / `cli` / `demo` —— 今天它们**知道这个游戏**，E4/E5 之后会变成通用入口、届时搬去 ENGINE）
- ⚠ **理由相同的东西抄 35 份，改的时候必然漏掉几份** —— 这正是本项目记过多次的"两份真相"。
  所以写法是**分组常量 + 逐文件指向它**，不是复制粘贴。

## 三、门当场纠正了我一处误判（值得记）

我先按**性质**把 `diag.ts`（诊断叠加层）划成**引擎**。门立刻报 3 处越界：

```
· diag.ts 是**引擎**，却 import 了**内容**模块 comp.ts
· diag.ts 是**引擎**，却 import 了**内容**模块 game.ts
· diag.ts 是**引擎**，却 import 了**内容**模块 sprites.ts
```

⇒ 按本仓库的规矩改判：**决定一个模块坐哪里的不是它的性质，是它的依赖**
（这句话在 `AGENTS.md` §四分层的例子里就写着：`trade.ts` / `run_save.ts` / `stats.ts` 都栽过）。
`diag.ts` 归**内容**。

**这条值得留下**：如果我当时选择"为了让门变绿而放宽判据"，这道门就等于被删掉了 ——
门自己的处置文案就写着这一句。
