## 三模块循环·落地（**已完成**）—— 营地搬出战斗场景 · 建材并入材料 · 一条"打→造→再打"

> 起因（用户拍板这一轮做什么）："剩下三块（README 已更新，按风险排序），一起做了吧"，
> 外加一句**纠正我对"局外"的理解**的话：
>
> > "我说的局外指的不是多个屏幕或者是分屏，而是说的是类似于游戏内的不同场景，
> > 局内局外只是为了区分战斗和其他两个模块的，不要看字面含义。所以实际情况是
> > 这三个模块虽然是不同场景，但都是在同一个游戏内的，能明白不，如果还是不明白，
> > 你可以看看那种类似于白天经营，晚上战斗这种类型的游戏。"
>
> 这一句话改变了整个改法的性质：不是"把营地从一屏搬到另一屏"，
> 而是**把营地从"战斗里的临时工事"变成"经营场景自己的实体"**。

### 一、我原先理解错在哪（记下来，因为它决定了很多设计）

我一开始把"局外"当成了**另一个 UI 屏幕**，于是方案是"把 `camp` 那一屏挪到据点那一屏去"。
按那个理解，设施仍然是**每局从零盖**的 —— 因为屏幕只是显示，状态还是那一局的。

正确的理解是：三个模块是**同一个游戏进程里的三个阶段**
（白天经营、夜里出战）。于是"局外"= "**战斗场景之外**"，而经营与养成
各自是**独立场景**、有自己的实体与自己的时间尺度。差别落在两处硬事实上：

| | 按"换个屏幕"理解 | 按"场景"理解（**实际采用的**） |
| --- | --- | --- |
| 设施的生命周期 | 每一局清零 | **跨局永久**（账号资产） |
| 玩家什么时候经营 | 战斗中每波顺手盖一座 | 打完一轮回到经营场景，专门花时间 |

### 二、这一轮改了什么（按风险排序的三块）

#### 第 1 块：营地搬出战斗场景（最大的一块）

`camp.ts` 的设施 / 建造顺序 / 那笔钱，原先全部住在**局内会话**里
（`game.ts` 的 `S.camp` / `S.campRow` / `S.campPoints` / `S.campFx`），
`test/camp.mjs` 有 **121 条断言**钉着它，`market.ts` 还专门为它写了一节。

现在：

| 原先 | 现在 | 落在哪 |
| --- | --- | --- |
| `S.camp`（每局清零） | `Profile.campOwned()` | `profile.ts`（跨局） |
| `S.campRow` | `Profile.campRow()` | 同上 |
| `S.campPoints`（**建材**，每波 +2） | **删掉整笔钱** | 钱变成 `Profile.material()` |
| `S.campFx`（会话里冻一份） | `Profile.campFx()`（**每次现算**） | 见下面"为什么不能缓存" |
| `market.campBuy/campSell` | `Profile.campBuy/campSell` | `market.ts` 那一节留了一条注释指路 |
| `S.craftUsed`（这一波用过哪几条产线） | **留在会话里** | 它确实是"这一局"的回合计数器 |

**"建材"这一笔钱被删掉了**，这是本轮的第二个要点。它原先的服务对象只有
"局内营地"，而营地走了。它的**六个来源**全部改发**材料**：
每波固定 +2（**这一条直接删除**，见下）、精英房、宝箱房、补给房、密室房、
商店"原料"那一栏（改造前是"废料 → 建材"，现在是**唯一一条"废料 → 材料"的兑换**）。

> 为什么把"每波 +2"**删掉**而不是改成"+2 材料"：每波白送材料会让
> "打得好不好"与"经营能做什么"脱钩 —— 那正是改造前"先攒钱盖房"越过战斗的那条捷径。

**⚠ 删掉它之后我模拟玩了一遍，发现循环是断的 —— 这一条必须记下来。**

我写了一段临时代码把整条循环走一遍（打一轮 → 进工坊 → 盖产线 → 造装备 → 再打），
结果第 1 间清完时：**材料 = 0**，而最便宜的一座设施要 2 —— **连第一座都盖不起**。
原因是删掉"每波白送"之后，材料只剩**宝箱 / 精英 / 补给 / 密室四种房间**这一个来源，
而普通战斗房一分不给。**48 套测试全都通过，因为它们直接调 `Profile.addMaterial` 发材料** ——
这是"测试绿了但游戏玩不通"的一个真实案例，只有真的跑一遍流程才会露出来。

补的产出挂在**清间**上（`endWave` 里的 `gainMaterial`）：

```
清间材料 = round((4 + 波次 × 1.5) × harvestMul())
```

它与被删掉的"每波白送"有**本质区别**，这也是它能留下的理由：

| | 被删掉的"每波 +2 建材" | 补上的"清间给材料" |
| --- | --- | --- |
| 触发 | **无条件到账**（活着就行） | **清掉这一间**才有 |
| 随进度 | 恒定 2 | 随波次增长（4 → 5.5 → 7 → …） |
| 拿不到的情况 | 没有 | 被时限逼到超时、或怪没清完 |

实测曲线（`pnpm run bal`，12 种子平均 · `survive` 模式）：一局 **5 波 ≈ 16 材料**，
7.5 波 ≈ 35 材料。工坊**全建满**（5 座设施：2/2/3/3/3，再加升级）约 20–30 材料 ——
也就是"头一局攒出一座，十局内把工坊建成型"，与《Hades》那类元进度的节奏同量级。

**为什么折叠效果不能缓存进会话**：设施现在可以在一局进行中被改建
（经营场景随时能进），缓存下来就会出现"刚盖好的熔炉，这一局却不省料"。
所以制造的费用与档位**每次现读**；只有一个派生值仍然冻在会话里 ——
**回收比例**（`S.salvageRate`），而它由 `Game.campBuy/campSell` 成交后立刻重算。

#### 第 2 块：三模块的场景化收口

- 制造现在可以在**商店 / 工坊 / 据点**三处发生（`requireStateIn(['shop','camp','keep'])`）——
  因为经营场景就是"据点那一屏"，在那儿造装备才是自然的。
- 界面不再自己算规则：`ui.ts` 原先在按钮上各自调一遍 `Camp.canBuy` / `Camp.refundOf`，
  **而且没传 opts**（据点给的位子、工匠的全额返还在按钮上都没算），
  于是按钮上的价钱与实际扣的钱可能不一致。现在统一走 `Game.campFacilities()`。
- 场景表那一层没动（`scene.ts` 的 `camp` 仍然是一屏），因为它本来就是数据驱动的。

### 三、一个必须先说清楚的账：材料是**一个池子**，有两个名字

用户原话是"材料靠战斗获得，玩家自己花材料打造"，而材料又是**跨局**那笔钱。
这两件事只有一个自洽解，**这里写死**：

```
战斗中：材料当场进钱包（Profile.addMaterial）——不让它等结算
       因为"打完一轮 → 回工坊造一件"这条循环里，中间那一环不能是"先结算一次"
结算时：入账的是 `stats_total.scrap`（**废料**口径），与材料无关 —— 不会重复发
```

于是"花材料打造"与"材料能带出去"同时成立，而且**不惩罚省钱**：

- 花掉的材料是你这一局打到的其中一部分，剩下的自然留在钱包里带出去
- `earned`（结算入账）只算**废料**，所以"多花材料造装备"**不会**减少带出去的量 ——
  这里没有"攒钱税"

`S.materialEarned` 只是一个**展示用**的计数器（"本局打到多少材料"），不参与结算计算。

**指纹为什么又不变**（这一点必须讲清楚，否则看起来像"改了但没生效"）：
三局指纹基准是**固定帧数的模拟跑**，它们**不经过建造或制造那一段交互**
（那是玩家在商店/工坊里的决定，机器人不替玩家做）。所以"钱换了归属"
对它们没有影响。这是"改动落在战斗循环之外"的**实证**，不是漏测 ——
反之，如果指纹变了，那才说明我动到了不该动的东西。

### 五、这一轮**没有**做的

- **局内两屏的物理合并**：`#scr-camp` 与 `#scr-keep` 仍然是两屏。
  按"场景"的正确理解，它们其实**是同一个经营场景**（一个在战斗中可达、
  一个在大厅可达）。合并它们会动 `scene.ts` 的场景表、`Game.TRANSITIONS`
  与 `ui-shot` 的取景清单，而且**不影响玩法**（状态与账已经都在档案里了）——
  所以留到下一轮，先把"钱与设施真的跨局了"这件事做扎实。
- **营地的平衡数值没有重调**：设施价格（2/3/4…）原先是按"每波 +2 建材"定的，
  现在改成材料，**收入结构与量级都变了**（材料来自怪与房间，不再每波白送）。
  `tools/balance.mjs` 已经跟着改了接线，但"新经济下盖一座熔炉算不算划算"
  需要重新跑一遍基准才有结论 —— 那是一件独立的事，见下一章"还没做"。


> 起因："三个模块（战斗、养成、经营）……战斗是局内，养成和经营是局外的……
> 最重要的是这三个模块都不该是相互嵌合的，每个模块都是不同的场景下游玩的，
> 应该是由局内战斗刷怪得到材料、击败 Boss 得到核心材料，然后通过各种不同的材料
> 和核心材料，经营和养成才能继续升级优化进入下阶段和有关键产出……
> 然后养成和经营通过产出反哺战斗，他们是一套严密的循环。"

### 一、先说清楚：**这一轮的产出是一张货币表**，不是新玩法

这一轮**没有改任何玩法数值**（指纹三值逐位不变），也没有重写经营 / 养成的设施表。
它做的是把"三个模块怎么互相喂"从**散文**变成**可查的数据 + 可失败的断言** ——
因为在那之前，没人能回答"这一笔资源该不该存在、该从哪来、该花在哪"。

### 二、取材：货币的四个层级

参照一份公开的货币系统设计总结（[multiple currency types](https://github.com/raduacg/game-mechanics-optimizations/blob/main/I_46_multiple_currency_types.md) ·
[temporary vs permanent resources](https://github.com/raduacg/game-mechanics-optimizations/blob/main/I_47_temporary_vs_permanent_resources.md) ·
[resource conversion](https://github.com/raduacg/game-mechanics-optimizations/blob/main/I_48_resource_conversion.md)），
它把货币按"赚多少 / 花在哪"分成四层，**每层解决一个不同的心理问题**：

| 层级 | 赚多少/局 | 花在哪 | 心理作用 | 本作 |
| --- | --- | --- | --- | --- |
| session | 100~500 | 局内立刻变强 | "现在就该花掉" | **材料** |
| bridge | 30~100 | 局外、跨局 | "死了也没白打" | **孢子 / 合金** |
| meta-rare | 1~5 | 卡住**大块内容** | "这一局值了" | **核心材料** |
| ultra-rare | 0.1~1 | 声望 / 解锁 | 长期目标 | （没有，本作不需要） |

对照外部：《Hades》六种货币（Darkness 跨局 / Obols 局内 / Titan Blood 只能靠"首次通关某个武器"）、
《Dead Cells》两种（Gold 局内全丢 / Cells 必须活着带到 Collector 才保得住）——
本作四笔钱与它们的对应关系一模一样，只少了一层 ultra-rare（那是长线运营的东西，本作不做）。

### 三、`src/economy.ts`：三模块循环的骨架

**四笔钱，各有层级、来源、去向、why（下表与 `Eco.LIST` 逐字对应）：**

| 货币 | 层级 | 来源 | 去向 | 实际扣钱的函数 |
| --- | --- | --- | --- | --- |
| 材料 | 局内（结算清零） | 战斗 | **战斗**（货架 / 制造 / 刷新） | `market.buyOffer` / `craft` / `reroll` |
| **核心材料** | 关键（带得出去） | **只有 Boss 掉**（`CORE_PER_BOSS`） | **经营 + 养成** | `Profile.keepBuy` / `Profile.forgeNode` |
| 孢子 | 跨局 | 战斗结算（按深度） | **经营**（+ 天赋洗点） | `Profile.keepBuy` / `spendSpores` / 洗点 |
| 合金 | 跨局 | 回收装备 | **养成** | `Profile.forgeNode` |

⚠ **这张表里有两处曾经写错，两处都值得记下来**（都是"文档说 A、代码做 B"）：

1. **"经营花材料"是错的**。材料是 `session` 档、结算清零，它**买不了局外设施**。
   真相是 `Profile.keepBuy(id)` 扣 **孢子 + 核心材料**。
   而"经营花材料"这个说法一旦写进注释，下一个人就会以为据点那一屏该读 `materials`。
   代码里 4 处读点已经用 `pnpm run reconcile` 逐个量过（它数的是真实读点，不是那句话）。
2. **本作没有 `ultra-rare` 那一档**。方法论是四层，本作三档 —— 少的那一层是**明确的取舍**
   （那是长线运营货币，本作不做），不是漏做；`audit()` 会拒绝"声明了但没有货币的层级"，
   所以这里是把第四档**不声明**，而不是声明了空着。

**三条被审计钉住的纪律：**

1. **只有战斗能产出**。`audit()` 会拒绝任何 `from` 里带 `manage` / `grow` 的货币 ——
   局外能印钱 = 它自己就是一条循环，战斗那一侧就变成可选的了。
2. **局内 / 跨局不许串**。局内货币必须**有**局内去向，跨局货币**不许有**局内去向
   （否则"这一局的钱能买局外的东西"，两条经济就并了）。
3. **核心材料只有 Boss 掉**。`test/economy.mjs` 会静态检查它**只**出现在
   `if (e.def.boss)` 那一支里 —— 放到普通掉落里，`meta-rare` 那一档就退化成
   "多打几把"。它同时是经营与养成的**共同门槛**：于是那两个模块争的是同一笔稀有资源。

### 四、闭环已经接上了：两条反哺边 + 两个门槛

原先登记在 `Eco.GAPS` 里的两条反哺边**已经补完**（现在是空的），
判据写在 `Eco.BACKFLOW` 里（正面声明，不是"缺口清单"）：

| 边 | 通道 | 门槛（必须指向真会被花掉的东西） |
| --- | --- | --- |
| 经营 → 战斗 | `Stronghold.modsFor → kmods`（开局折一次） | `archive` Lv.3 要 **2 个核心材料** |
| 养成 → 战斗 | `Talent.opening → opening`；`Forge.modsFor → fmods`（开局折一次） | `master` 图纸要 **2 个核心材料** |

为什么改成"正面声明"：`Eco.GAPS` 曾经把这两条边登记成缺口，
而它们其实**一直在工作**（只是以效果而不是货币的形式）——
那张表因此会**永远**报"缺 2 条"，**一把会撒谎的尺子**。
现在每条边写清"谁提供 / 什么在限制它"，而 `limit` 必须指向真的花掉核心材料的东西：
**白给的反哺不是循环的一环，是开场福利。**

**反哺为什么是"效果"而不是"货币"**：`kmods` / `fmods` / `opening` 在 `newSession` 里
折一次，之后模拟层**不再回表**。这就是"三个模块不互相穿透"的实现方式 ——
战斗那一侧永远只看到一份折好的初始条件，看不到"据点有几级"。

**全部读点都有真出口**（`pnpm run reconcile` 逐个量过，13 个据点效果键 × 全部命中）：

| `freeRerolls` | `game.ts:1494` |
| `campSlots` / `refundFull` | `market.ts:252/256`（工坊产线位） |

### 五、三个模块各自的"场景"（`Game.STATES` 里的落点）

| 模块 | 局内/局外 | 场景（`Game.STATES`） | 花什么 | 产出 |
| --- | --- | --- | --- | --- |
| 战斗 | 局内 | `playing` / `levelup` / `shop` / `camp` | 材料 | **四笔钱的唯一来源** |
| 经营 | 局外 | `hub` → `keep`（据点设施） | 孢子 + 核心材料 | 容量与产能（货架 / 产线位 / 离线产出） |
| 养成 | 局外 | `hub` → `talents`（天赋树）+ 图纸工坊 | 合金 + 核心材料 + 天赋点 | 开局条件（`opening` / `fmods`） |

三屏都有真机截图守着（`tools/ui-shot.mjs` 的 `keep:` / `talents:` / `hub:` 三张），
所以"每个模块是不同的场景下游玩的"这一条**是可以看见的**，不是只有声明。

### 六、这一章**不能**声称的一件事（诚实边界）

**"高内聚低耦合"目前只在代码依赖上成立，不在玩法边界上完全成立。** 具体两条：

1. **局内营地（`camp.ts`）是"经营"模块嵌在战斗里的一半**：
   它花的是**局内**建材（`Camp.POINTS_PER_WAVE`），产出的是这一局的产线布局，
   出了局就没了。也就是说"经营"这个模块**横跨了局内与局外两半**，
   而不是纯局外 —— 这是设计选择（一局的局内也要有"经营"的味道），
   但它确实与"经营是局外的"这句话不完全一致。
2. **经营与养成共用两笔钱**（孢子是经营的主币、养成的洗点币；核心材料是两个模块的共同门槛）。
   两者都有独立的表 / 场景 / 独立的反哺通道，但**经济是同一个池子** ——
   所以它们更像"同一张局外经济的两条支线"，而不是两个互不相关的模块。

上面两条**都还没有外部权威来源可以对照**（见第七节），所以我不把它们写成"设计对/错"，
只写清楚现状。要真正把这两条做干净，是一个**玩法决策**（要不要把营地从局内挪到局外、
要不要给经营一个独占货币），不是一次重构能替它定的。

### 七、外部参考（这一轮补的）：同类游戏怎么切这两刀

| 问题 | 外部做法 | 来源强度 |
| --- | --- | --- |
| 临时资源 vs 永久资源要不要分档 | 要分，而且**临时资源必须在局内花完**（这正是"session 档"的理论依据） | [`I_47_temporary_vs_permanent_resources`](https://github.com/raduacg/game-mechanics-optimizations/blob/main/I_47_temporary_vs_permanent_resources.md) `[摘要]` |
| 局外模块之间要不要互不相关 | **Hades 的局外有两套互不相通的花法**：`Mirror of Night` 花 Darkness/Keys 换**能力**、`House Contractor` 花 Gems/Diamonds 修**建筑与外观** —— 同一座 House of Hades、两套货币、两条不重叠的升级轴 | [House Contractor](https://hades.fandom.com/wiki/House_Contractor?printable=yes) `[摘要]` |
| 一个模块能不能横跨局内局外 | **没有找到权威来源说"不行"** `未验证`。反例：Hades 的 Charon 商店在局内、Wretched Broker 在局外，两者都花 Obols/Gems ——「同一个名字的资源在两个场景里花」是被广泛使用的 | [Wretched Broker](https://hades.fandom.com/wiki/Wretched_Broker) `[摘要]` |
| 局外成长会不会把局内变简单 | 这是同类游戏的**公认风险**（"meta 太强会让单局失去意义"），常见对策是**只解锁内容、不叠数值** —— 本作的 `Forge` 正是这条（"只解锁能力不改数值"） | 多来源讨论，无单一权威 `未验证` |

**结论**：本作在"临时/永久分档"与"只解锁能力不叠数值"两条上与外部一致；
在"局外模块互不相通"这条上**外部没有硬标准** —— 但 Hades 的两套花法给了
一个更好的参照：如果将来要把经营与养成彻底分开，
**给经营一个独占货币**（而不是与养成共用孢子）就是那条路，
代价是要么新增一笔钱（多一层认知负担），要么把孢子与合金的归属拆得更硬。
**这一步需要拍板，不是重构。**

## 美术资源体系与 TA（**已完成**）—— "没有一张图片文件"的美术管线

> 起因：把一款 2D 游戏需要的**美术资源**与**技术美术（TA）**工作都在项目里落地，
> 要求系统化、高内聚低耦合（不含人物角色相关内容）。

### 一、先说清楚约束：这个项目没有一张图片

全部视觉都是**代码画出来的**（`src/sprites.ts` 1200+ 行、`src/draw2d.ts` 的原语、
`src/render.ts` 的静态层烘焙）。所以"落地美术管线"在这里不是加一个 `assets/` 目录，
而是**把真实项目里那条管线的每一道工序，换成这个项目里对应的东西**：

| 真实项目 | 本项目 | 谁做的 |
| --- | --- | --- |
| PS/SAI 源文件 | 生成函数（画法参数写在数据表里） | `sprites.ts` / `render.ts` |
| 导出 PNG（尺寸/通道规范） | 离屏 canvas（size / anchor / 通道语义） | `sprites.ts` 的缓存 |
| **资源检查**（超限/冗余图层/多余通道） | `Art.lintAsset` 的 7 条判据 | `art_spec.ts` |
| **图集打包**（SpriteAtlas） | 贴图缓存分组 + 预算 | `art_spec.ts` + `sprites.ts` |
| 引擎导入设置（TextureImporter） | 缓存键与倍率（DPR / bake） | `sprites.ts` / `render.ts` |
| **材质 / Shader / 混合模式** | 合成步骤序列（4 个可组合 op） | `art_shaders.ts` |
| 渲染层级（Sorting Layer + Order） | `depth.ts` 的 13 个层带 + 层内 y 排序 | 已有 |
| **DrawCall 预算** | 每帧绘制数 + 静态层 + 纹理字节 | `test/render-check.mjs` + `pnpm run art` |
| 美术规范文档 | 规范本身是**可执行的数据表** | `art_spec.ts` |

**取材**：autotiling 的位掩码约定（[blob47 / Wang tiles](https://assetstore.unity.com/packages/tools/level-design/autotiler-blob47-auto-tiling-for-tilemap-407348) ·
[autotiling macros](https://fyrox-book.github.io/scene/autotiling.html)）、
图集打包（[MaxRects bin packing](https://www.glbasic.com/forum/index.php?topic=7896.0)）、
资源命名与目录规范（[Unity Style Guide](https://github.com/justinwasilenko/Unity-Style-Guide) ·
[Unreal 命名规范](https://unrealcommunity.wiki/6100e8169c9d1a89e0c34217)）。

### 二、`src/art_spec.ts`：规范是**数据**，不是文档

一张表声明了 12 类资源，每类五件事：**前缀 / 图集 / 混合 / 锚点 / 命名示例**。

```
瓦片集 TILE_  世界图集 normal   锚点 格心     场景物件 PROP_  世界图集 normal   锚点 脚底
背景层 BG_    世界图集 normal   锚点 中心     叠加装饰 DECAL_ 世界图集 multiply 锚点 脚底
图标   ICON_  界面图集 normal   锚点 中心     交互物件 OBJ_  世界图集 normal   锚点 脚底
器械   DEV_   世界图集 normal   锚点 脚底     界面素材 UI_   界面图集 normal   锚点 中心
特效   FX_    特效图集 additive 锚点 中心     粒子   PT_    特效图集 additive 锚点 中心
物件动画 ANIM_ 世界图集 normal  锚点 中心     宣传美术 PROMO_ 不进图集   normal   锚点 中心
```

规范是数据，于是**它自带一把尺子**：`Art.lintAsset(声明)` 检查
命名 / 类别 / 尺寸 / 锚点 / 图集 / 混合 / 预算七条，每一条问题都写明是哪条判据。
六道工序（画法 → 检查 → 烘焙 → 图集 → 摆放 → 合成）也逐道声明了**产物与检查** ——
"某类资源缺了检查"于是是结构性的不可能。

三条尺寸规范都是**从真实几何反推**的，不是拍的：

- `grid = 16` / `tile = 16`：战场 1680×1260，瓦片必须是网格的**整数倍**，
  否则拼接处落不到格线上（"整数倍"与"整除"在这里数值等价、含义相反 —— 这条注释留着，
  因为 `ruinFloor` 用 32px 就是靠它才没被判非法）。
- `icon = 32`：图标在商店 / 背包 / 悬浮提示三处以三种尺寸出现，
  非整数倍缩放会把 3px 描边糊成 2px 或 4px，而"唯一外轮廓色 3px"写进了美术宪法。
- 锚点必须写明，因为**深度排序按脚底**：一棵用中心锚点的树，
  在玩家从它前面走过时排序就是错的。

### 三、资源归属：**没做也是一种登记过的状态**

规范声明 12 类，但"哪几类项目真的做了"只能由**生产它的模块**自己说。
于是每个模块在加载时登记：`Art.noteOwner('prop', 'render.ts')`。
`pnpm run art` 于是能打印出这样一张表：

```
✔ 瓦片集 TILE_   art_tiles.ts + render.ts      ← 规范在一处、绘制在另一处（两个贡献者）
✔ 场景物件 PROP_ render.ts        ✔ 背景层 BG_  render.ts + art_parallax.ts
✔ 叠加装饰 DECAL_ render.ts       ✔ 图标 ICON_  sprites.ts
✔ 交互物件 OBJ_  sprites.ts       ✔ 器械装置 DEV_ sprites.ts
✔ 界面素材 UI_   ui.ts            ✔ 特效贴图 FX_  sprites.ts
✔ 粒子贴图 PT_   sprites.ts       ✔ 物件动画 ANIM_ art_parallax.ts
✔ 宣传美术 PROMO_ sprites.ts
在做 12 类 · 推迟 0 类 · 漏做 0 类
```

**"漏做 0 类"是硬断言**：`Art.missingKinds()` 列出"既没有生产模块、也没登记理由"的类别，
`test/art.mjs` 与 `pnpm run art` 都会因为非空而失败。做不了的那一类可以登记进
`Art.DEFERRED` 并写清理由（"没做"是一种**登记过的状态**，不是沉默），
而自检会**反向**检查：一旦哪个类别真被做出来了，它必须从推迟清单里拿掉，否则报错 ——
这一条在把 `anim` 做出来的那一轮真的触发了，报错原文是
"anim 已经在推迟清单里，却已经有模块在生产它（art_parallax.ts）"。
`DEFERRED` 现在是**空的**（12 类全部有主），但机制留着：
"机制在、数据空"与"数据在、机制没做"是两件完全不同的事。

### 四、`src/art_tiles.ts`：自动规则瓦片（第一处真实用途）

4 位掩码 = 上下左右四个邻居，**邻居同种地形就立起那一位**，16 种组合 → 16 块瓦片。
`autotile(set, grid)` 是**纯函数**：给一张地形网格，算出每一格该用哪块瓦片、
画在哪（返回的坐标已经是**像素**，调用方不必再乘一次 —— 乘错一次就是整层偏移半格）。

规则表逐格写出来（不是按形状自动生成）：自动生成会让"某种地形忘了做端头瓦片"
变成静默的。最要紧的一条判据是**形状必须与掩码对得上** ——
写错的唯一表现是"转角画成了直段"，它看起来**只是有点怪**，不抛错、不崩溃。

真实用途：战场的**废墟铺装**。地面原本是 70 块笔刷色斑（能给出大色调，给不出结构），
而"废墟"的本质是**格子**：整块的砖、断在中间的砖、拐角的砖、孤零零的一格。
网格从已有的 patches 派生（**不新增随机流**，同一波次仍是同一张地面），
只在色斑**叠加 ≥3 层**的地方铺 —— 阈值同时是观感与开销的旋钮。

这一步是**量出来的**，三次都记在注释里：

| 做法 | 静态层烘焙（帧） | 结果 |
| --- | --- | --- |
| 每块色斑都铺（16px 瓦片） | 74937 | ✗ 顶穿"烘焙帧上限 6 万"这条守卫 |
| 只在叠加 ≥3 层处铺（16px） | 68992 | ✗ 仍超 |
| 只在叠加 ≥3 层处 + 实心格短路 + 32px 瓦片 | **56267** | ✓ 通过（每帧中位 185 次绘制，比改造前还低 9） |

"实心格短路"是这一轮最值得记的一笔：mask 15（四面都是同种地形）占绝大多数，
而它的接缝在相邻格各画一条会**叠成双线**——所以实心格不画接缝，
只画主体与立体边。接缝于是只出现在真正有拐弯的地方，而那正是需要看见接缝的地方。

### 五、`src/art_parallax.ts`：分层视差与状态动画

两样东西放一个文件，因为它们回答同一个问题：**"这一层在动，但它不参与玩法。"**
动的方式只有两种 —— 跟着镜头动（视差），或者跟着时间动（动画）。

**视差在这里真的成立**，因为镜头真的会平移：战场 1680×1260，视口 1280×720
（`cam.zoom` 缺省 1），于是横向可平移 ±200px、纵向 ±270px。
三层：远景 `rate 0.10` / 中景 `0.22` / 近景 `0.38`。两条硬约束写在自检里：

- `rate` 必须严格落在 `(0,1)`：`0` = 贴着屏幕（一看就假）、`1` = 跟地面同速（看起来没动）。
- **相邻两层的 rate 差 ≥ 0.05**：差 0.02 的话肉眼分不出层次，那两层就是白画。
- 越远越慢（`depth` 与 `rate` **反向**）—— 这一条我写错过两次，
  两次都被那段自检当场拦住。一条挂在启动期的断言比一句注释值钱，
  因为它会在**下一次**有人改这两个数字时再拦一次。

副本份数是**算出来的**，不是"多画几份保险"：
`ceil(maxPan × rate / repeat) × 2 + 1`。少画一份的表现是
"走到某个角落背景突然断掉"，而它只在那一处发生。

**状态动画**给了一个通用、数据驱动的模型：一条 clip = 一组关键帧 `(t, 值)`，
物件的 `t` 由"进入这个状态之后过了多久"给。第一条真实用途是**开门** ——
改造前门在清完房间那一刻从"锁着"跳成"开着"，门闩凭空消失（一件可以演的事被吞掉了）。
现在门闩抬起 0.3 秒，而且播的就是那张关键帧表（含一个负值的过冲，让"抬起"有惯性）。

这一轮也修掉了一个**自己写出来的** bug，值得記：第一版把"状态变了就重置计时"
写在推进计时**之后**，于是"状态刚变的那一帧把 t 清 0、然后就早退"，
门闩永远停在 t=0 —— 动画一帧都不播，而它不报错、测试也只有真去断言"抬升量 < 1"才发现。
`test/art.mjs` 现在对此有 5 条断言（含"0.3 秒之后抬到底"与"另一间房不受影响"）。

### 六、`src/art_shaders.ts`：2D 着色器 = **可组合的合成步骤**

Canvas2D 没有 fragment shader 可写，但"逐像素替换"这件事，四个合成操作就够了：
`over`(source-over) / `in`(source-in) / `atop`(source-atop) / `add`(lighter)。
一条 shader = 一串步骤，每一步是"某个 op + 一个**声明式**动作"
（`fill` / `ring` / `border` / `mask` / `offset` / `alpha`）。

8 条效果：命中白闪、外描边、溶解、精英色、全息、色差、暗角、遮罩揭示。
**每条都写清了"为什么需要它"**（没有理由的效果不该进库），
`kind` 分成 `sprite`（作用在贴图上）与 `screen`（作用在整屏）两类，两类都必须有人。

接线的三条，每条都替换掉了原来的一份**裸写法**：

- `hitFlash` → `enemyFlash`。改造前 `source-in` + 白填充是裸写的，
  于是"把白闪改成暖白"要改两个地方，漏掉的那个只表现为"有一只怪闪的颜色不一样"。
- `elite` → 精英怪的加色金光（`atop` 让它精确落在怪物轮廓内，
  读起来是"这只怪本身在发光"而不是"套了个金圈"）。
- `vignette` → 低血暗角。它画**四条边**而不是压整屏：低血压暗的是余光，不是玩家正在看的地方。

**剩下五条登记为"备用"，每条都写清了等什么条件才用**（溶解要等"会消失的敌人"、
遮罩揭示要等"需要揭示的地图"……）。这条纪律是给维护者的：
否则"暂时用不上"的效果只有两个下场 —— 要么被删掉、要么变成没人敢碰的僵尸代码。

### 七、宣传美术：标题字是**画出来的**

`promo` 这一类在真实项目里就是一张图（封面 / Logo / 标题插画）。
在"零资源文件"的宪法下它没有落点 —— 除非**按同一套画法把它做出来**。
所以标题 **Bronana** 现在是一个**程序化的字标**（`sprites.ts` 的 `S.EMBLEMS`）：

- **逐字声明**（7 个字形 + 基线错落），不是一句文案 ——
  于是"标题多宽"是算出来的，不受平台字体与 `text-shadow` 影响；
  三台机器上一样宽。每个字画两遍：右下 4px 的纯色投影 + 7px 黑描边的本体。
- 一枚**徽记**（豆形剪影 + 硬边光环），可单独用在 Loading / 结算。
- 它走**共用**的缓存前缀（与掉落物同组）而不是新开一族 ——
  `test/cache.mjs` 守着"缓存键前缀只有五种"，多一种就是多一类没人管的条目。
  那条守卫是对的，所以这里让路。
- 界面层只负责"画到哪个节点上"（`#title-logo` 那块画布），
  CSS 里的宽度必须写**确定像素**：无头校验会核对每一张 DOM 画布的
  "属性尺寸 = 逻辑 × 倍率、CSS 尺寸 = 逻辑"，响应式宽度（`clamp`）让那条判不出来
  —— 小屏适配因此交给媒体查询，改的仍是同一批数值。

### 八、`pnpm run art`：资源体检（TA 的"资源检查"那一格）

```bash
pnpm run art
```

打印六节：规范表 · 资源归属（谁在做 / 谁推迟）· 图集分组与实测字节 ·
**两个池子分开的预算** · 着色器接线状态 · 瓦片规则表的 mask 分布。
它读的就是游戏跑起来那份数据（直接 import `src/*.ts` 并**真跑一局画几帧**），
所以"工具说没事、游戏里是另一回事"这种漂移不会发生。

两个池子必须分开报，因为**它们不是同一条预算**：贴图缓存按条目数自然有界
（每种怪物 / 武器 / 图标各一张，实测 37 条 / 1011KB）；静态层烘焙是两张整屏画布
（实测 17.99MB），它真正的约束是"总像素 ≤ `render.ts` 的 `BAKE_MAX_TOTAL_PX`"——
那条上限决定的是**烘焙倍率取 dpr 还是退回 1×**，不是让静态层去挤贴图的额度。
混在一起报会得出"18.98MB > 16MB = 超标"这种**错**的结论 —— 它差点被我写进这一节。

### 九、验证

- `tsc` 两套 **0 错** · **44 套 0 FAIL**（新增 `test/art.mjs`，131 条断言）
- **指纹三值逐位不变**（`8b90ed4f / 08205e33 / f4f27172`）——
  这一轮改的全是画面，模拟层一行没动
- 探针 **24 局不变量全部成立** · `pnpm run audit`：真死 0 · 未用 import 0 ·
  未读字段 0 · 依赖环 0 · 向上的边仍 2 条 · **60 个模块 / 27859 行**
- 渲染预算：每帧绘制中位 **353** 次（上限 900）· 烘焙帧 **56395** 笔（上限 60000）
  · 每帧新建选项对象 **0** 个
- 资源归属：**在做 12 类 · 推迟 0 类 · 漏做 0 类**
- 新增三个模块都挂在既有的层上（`art_spec.ts` → 数据表层，
  `art_tiles.ts` → 地牢层，`art_parallax.ts` / `art_shaders.ts` → 造型层），

### 十、这一轮从"量"里改出来的五件事

五条都不是设计出来的，是尺子报出来的 —— 记在这里，因为它们是这套体系**在干活**的证据：

| 尺子 | 报出的问题 | 改法 |
| --- | --- | --- |
| `render-check` 的烘焙帧上限 | 铺装把静态层从 2 万笔顶到 **7.5 万笔** | 只在色斑叠加 ≥3 层处铺 + 实心格短路 + 瓦片粗一档 → **56267** |

| `test/ui-check.mjs` 的画布尺寸契约 | 标题画布用响应式宽度（`clamp`）→ 判不出逻辑尺寸 | 固定像素 + 媒体查询，CSS 尺寸行内设 |

### 十一、没做的（带理由）

- **图集画布合并（把多条资源真的拼进一张离屏 canvas）**：现在的"图集"是
  **分组与预算**（按出现场合分组，回答"哪几类不能同批"），
  而真正的拼图收益来自"减少纹理切换"——在 Canvas2D 里同一张缓存 canvas 的就是一次 blit，
  跨 canvas 才是断点。要拿到收益得先把只画一次的贴图（怪物 / 图标）拼起来，
  而它们现在各自一张、总字节数远在预算内（实测 37 条 / 1011KB）。
  这是一笔"先量后做"的账，量出来的结论是**现在不做**。
- **物件动画的骨骼（Spine 式）**：`rig.ts` 已经通用，但本项目的"会动的物件"
  （门闩 / 箱盖 / 神龛浮环）都是**单自由度的状态变化**，用关键帧就是最优解。
  上骨骼要等第一个"多部件联动"的物件（比如会走路的机关），在那之前它只是复杂度。
- **`chroma` / `dissolve` / `hologram` / `outline` / `maskReveal` 五条 shader**：
  已在库里实现并测过，登记为**备用**并各自写清"等什么玩法才接"
  （见 `pnpm run art` 的 [5]）。
- **`anim` 的更多 clip**：现在只有门 / 箱 / 神龛 / 断柱四条，而真正使用它们的只有门
  （另外三条等对应的物件出现）。这是**内容**不是机制 ——
  机制（关键帧表 + 取样器 + 按住处计时）已经在了，加一条 clip 是加一行数据。

## 系统性复查 + 补齐"游戏该有的东西"（**已完成**）

> 起因："项目里所有功能都应该是系统性的，高内聚低耦合，检查下是否有做到，没做到就改造好……
> 还有就是游戏需要有的都补充上，可以没有素材但是不能没有至少占位是需要有的。"

### 一、复查结论：架构本身是干净的（数字说话）

`pnpm run audit` 的九节全绿，逐条回答"系统性做到了吗"：

| 尺子 | 结果 |
| --- | --- |
| 声明-注册-自检-测试 四件套 | **23 个 `SelfCheck.register`** · 90+ 个 `Registry.family` · 每张数据表都有自己的 `audit()` |
| 真死的接口 / 内部成员 | **0**（"声明了却没人用"这一类为空） |
| 未使用的具名 import | **0** |
| 声明了却没人读的数据字段 | **0** |
| 依赖环 | **0**（62 个模块） |
| 向上的依赖边 | **2 条**，两条都登记了理由（`enemies→danger`、`game→bronana`） |
| 系统分层 | 9 层，`test/arch.mjs` 守着"只能高层→低层"，新加一条向上的边会红 |
| 未登记的向上依赖 | **0** |

复查中**改掉**的几处不系统的地方：

- `test/persist.mjs` 的"模块级可变状态"盘点**只认 `var x = …`** ——
  挂在导出对象上的字段（`Music.current = ''`）既被判成"可变"，又不在"当前存在的清单"里，
  于是白名单一登记就成了"已删除的条目"。现在两种形态都认。
- **设置项只有"应用分支"没有"界面控件"**：`music` 加进设置表时，应用分支、
  测试、主循环都接上了，唯独**设置页没有那个按钮** —— 而当时的尺子只看
  "有没有应用分支"，全绿。现在 `test/registry.mjs` 多一条判据：
  **每个设置项都要有按钮 + 处理函数两样**（映射写成显式表，因为名字本来就不一致：
  `damageNumbers` 的按钮叫 `set-damage`、`volume` 有两个）。
  这是"尺子漏了一整类"的第三次 —— 记在这里，因为**加功能时先问"哪条尺子会红"** 是这里最省事的习惯。
- 同一份"像玩家那样跑一局"的实现此前有**两份**（探针 / 对局体检），
  同一个种子跑出两个结果 —— 收成 `tools/_run.mjs` 一份。
- `Profile.spendCore` 是死接口（零调用点），删掉：它正是"核心材料只涨不花"那条假边的证据。

### 二、补齐的"游戏该有的东西"

盘点的判据是：**没有素材可以，但不能没有系统与占位**。

| 项 | 之前 | 现在 |
| --- | --- | --- |
| **背景音乐** | **完全没有**（只有音效） | `src/music.ts`：5 条曲目 × 3 声部，**程序化生成**（能听的占位） |
| **运行时错误兜底** | 只有启动自检失败页（那是给开发者的） | `src/crash.ts`：`error` / `unhandledrejection` 接上，给玩家一张**可行动**的卡 |
| **标题页画面** | 一块**静态棋盘格** | 三层视差 + 抖动带 + 石板地面（复用已有的 `art_parallax.ts`） |
| **音频开关** | 只有"音效"总开关 | 设置里多了「背景音乐」（**按钮 + 处理函数 + 映射表登记**齐全） |
| 设置 | 13 项（含改键 / 减少动效 / 失焦暂停） | 14 项 |
| 存档 | 信封 + 版本 + 迁移链 + 损坏兜底 | 已完备 |
| 成就 | — | `challenges.ts` 已经承担（29 条 / 6 组 / 35 度量），**不必另起一套** |
| 教程 | "操作说明"页 + 标题页那行提示 | 已完备（不是缺失项） |
| 暂停菜单 | 继续 / 设置 / 战绩 / 放弃本局（含二次确认） | 已完备 |

**音乐为什么是"能听的占位"而不是静音**：曲目是「和弦 + 琶音 + 打击」三层，
每层 16 格（`-1` = 休止符，**休止符是数据**不是缺项）。战斗那条**按强度分层**
（0/1/2 档：只改琶音密度与打击重量，不改和弦进行）——
听起来是"同一首曲子更紧张"，而不是"突然换了首歌"。
音阶取**小调五声**：任意两音同响都不难听，所以程序化生成的琶音不会出错。
将来换真音乐时：把 `Music.play()` 里的合成器换成 `AudioBufferSourceNode`，
**曲目表与场景映射一个字都不用改** —— 它们才是这一层真正的产物。

音量走 `Sfx.master` **一个出口**：音乐自己再开一个 gain 就会出现
"调了音量音乐没变"或"静音了音乐还在响"。

### 三、**我不做的**（写给用户决定，附代价）

#### ① 本地化（i18n）—— 不做，理由是"C 选项不存在"

需求本身很直白：一张语言表 + 一个 `t(key)` + 缺键检查。**但这个项目里没有任何 key** ——
所有界面文案都是**内联字面量**（`'开始游戏'`、`'材料不足'`、`ItemDef.note`…），
粗数在 `ui.ts`(2686 行) / 各数据表(2000+ 行) 里约 **1000+ 条**。

- **全做**：机械但量极大（把 1000+ 条字面量逐条换成 key，并给每条起名），
  而且会把**数据表里本来读得很顺的文案**（`note: '收获更高（材料来得快），代价是身体被掏空'`）
  变成 `noteKey: 'item.rations.note'` —— 数据表当场变得没法读。
- **只做框架**：出中英双语，必然一半中文一半英文 ——
  这比没有 i18n 更糟，因为玩家会以为"这个游戏支持英文"。
- **第三种做法**（推荐）：**先不动**。真要出海时，
  一次性把 UI 层的字面量抽成 key（数据表的文案留中文，或另做一份文案表）。
  本项目的文案密度是它的特色，也是它的债 —— 这个取舍只有你能定。

#### ② 多存档槽位 —— 不做，理由是"它解决的不是真问题"

一款单机肉鸽只有**一局进行中 + 一份账号档案 + 一份设置**，没有"想开两个档"的真实需求；
而槽位会让 `profile` 的迁移链、离线产出结算、赛季记录都要考虑"哪一份"，
复杂度全落在最难测的地方。**收益接近零。**

#### ③ 检查点恢复（存到一半死在 Boss 房，刷新从那一波继续）—— 不做

现在的存档点是"清完一间 → 商店"，这是**刻意的**：中途恢复会让"这一局"变成可反复试探的东西，
roguelite 的张力就没了。真要放宽，该动的是"存档点放哪"这个设计决定，不是加一个恢复系统。

## 数值曲线：**角色侧那一半是补上的**（第二遍）

> 起因："角色的数值曲线和怪物的数值曲线，也是需要有系统性的，比如采用数据表驱动…"

### 一、第一遍做对了一半（如实说）

`src/curves.ts` 第一遍把**怪物侧、刷怪节奏、经验**搬进了表：14 条曲线、8 种形状、
逐点等价校验、`pnpm run curves` 的对照表。但**角色侧只有两条**：
`player.xp`（升级要多少经验）与 `player.cardGain`（每次升级给几张卡，常数 1）。

于是"玩家每级长多少"的答案落在了 `game.ts` 的 `UPGRADE_POOL` 里 ——
而它是一张**固定幅度 + 固定权重**的平表：第 1 级和第 40 级抽到的卡**强度一模一样**。
结果是：怪的生命是指数（第 39 间 ×27），玩家的成长却是
**一条平线 × 更多的级** —— 两边对不上，成长感全靠"多抽几张"。

### 二、外部怎么做（这一条是照着改的）

- **Brotato**：升级选项里弱属性（收获 / 幸运）起得小、强属性（伤害 / 生命）起得大，
  而"每次升级给多少"随波次抬 —— 固定幅度的平表是他们刻意不用的形状
  （[Brotato 升级表](https://gamers.wariichi.com/brotato/upgrades/)）。
- **Hades**：祝福有稀有度档，"每级的选项强度"是显式的设计量，而不是副产品
  （[稀有度与等级](https://steamcommunity.com/app/1145360/discussions/0/2796126653263362641/?l=tchinese)）。

### 三、补了两条角色侧曲线（都住在 `curves.ts`）

| 曲线 | 形状 | 值域 | 它在回答什么 |
| --- | --- | --- | --- |
| `player.cardAmt` | `power`（`a + m·t^k`，递减收益） | **1.0 → 1.6**（Lv1 → Lv40） | **一张升级卡值几倍** —— 这是"每级长多少"缺的那一半 |
| `player.cardPool` | `exponential` | ×1.01 → ×1.61 | 等级越高，池子越偏向**防御**（生命/护甲/闪避/回复/吸血） |

`UPGRADE_POOL` 从"平表"改成**声明**：每条只写基准幅度与基础权重，
外加一个 `guard` 标记（它是不是防御向）。真正的幅度 = `基准 × Curves.at('player.cardAmt', 等级)`，
真正的权重 = `基础 × Curves.at('player.cardPool', 等级)` —— **数值在曲线里，池子在表里**。

`a` 取 `0.9703` 是为了让**第 1 级恰好是 1.0**：开局那几张卡不能因为"引了一条曲线"
就悄悄变强（`test/curves.mjs` 用 1e-9 的容差钉着这一条）。

### 四、一个值得记的错误：第一版写成了 1.0 → 10.3

我按"怪生命 ×27，那卡也涨到 3~10 倍"去配参数，然后**量了一遍**：

```
Lv10  伤害 +18.0%   护甲 +7.2     ← 第一版
Lv30  伤害 +292%    攻速 +286%    ← 和对面的 ×17 完全脱节
```

卡幅度这条曲线**乘在"一整局的抽卡次数"上**（几十上百张），
所以它是**乘性叠乘的放大器**，不是一条独立曲线。写成 10 倍等于把
"几十张卡"的复利再乘 10 —— 曲线没错，**量级**错了一个数量级。
改成 **1.6**（卡的强度与卡的张数各出一半的成长）之后：

```
Lv1  伤害 +5.0%   护甲 +2.0   生命 +3.0
Lv10 伤害 +5.9%   护甲 +2.4   生命 +3.5
Lv40 伤害 +8.1%   护甲 +3.3   生命 +4.9      ← 温和，但对得上对面
```

**教训**：曲线要跟着"它乘在什么上"一起定价。这条 now 写在那条曲线的 `why` 里，
`test/curves.mjs` 也用"第 40 级必须落在 1.3~2.0 之间"把量级钉住 ——
下次有人想把它调到 10，测试会先红。
