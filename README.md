# Bronana

一个用 **TypeScript + 原生 ES 模块 + HTML5 Canvas** 写成的独立肉鸽游戏（Bronana）。

> **类型是 roguelite，不是 roguelike。** 战斗模块是**实时动作**（不是回合制、不是网格制），
> 有元进度与"继续这一局"的存档。术语订正写在 `docs/skill-audit.md` 的第 ⑧ 节 ——
> 那里以前把这道判据叫 `roguelike`，靠一句"按 roguelite 取适用面"打补丁。
**零运行时依赖、零素材文件** —— 全部 79 个源码模块（另有 `types.d.ts`）都是真正的 `import` / `export`，
开发时 Vite 直接跑未打包的 `.ts`，发布时 `vite build` 产出单个 JS 包。

所有美术（豆豆角色、异形小怪、24 把武器、29 个道具、外星荒漠地面、特效）都是**代码程序化绘制**的，
因此画风统一度是 100%：不存在任何风格割裂、没有一张外部贴图。
武器与道具还各自带**随机词条**（前缀 / 后缀，见 [`docs/history/03`](docs/history/03-体系化与数值曲线.md) 的「词条系统」）。

## 立刻开玩

三种运行形态，共用同一份 `src/` 与同一份 `dist/`，不各写一套。

```bash
pnpm install         # devDependency：typescript、vite、@types/node（electron 可选）

# ① web：浏览器
pnpm run dev         # → http://127.0.0.1:5180  （改源码即时热更新；不会自动开浏览器）
pnpm run build       # 产出 dist/
pnpm run preview     # Vite 自带的 dist 预览

# ② cli（服务器模式）：把 dist 用 HTTP 提供出去
pnpm run serve       # → http://127.0.0.1:5180  （默认 dist/、只回环）
pnpm run cli -- help # 看全部用法
pnpm run sim -- --seconds 120         # 无头跑一局并打印报告（平衡调参用）

# ③ desktop：Electron 外壳（窗口里加载的是内置服务器，不是 file://）
pnpm run desktop
pnpm run desktop -- --dev            # 外壳 + Vite 开发服务器
```

发布前：

```bash
pnpm run typecheck   # 两个 tsconfig：浏览器侧 + Node 侧，都 0 错误才继续
pnpm test            # 三十九套无头测试，全部通过才继续
```

### 包管理：pnpm，不是 npm

`pnpm-lock.yaml` 是唯一的锁文件，`pnpm@12.5.1`（写在 `package.json` 的 `packageManager` 里）。
迁移过来不只是换个命令，有三处实际差别：

- **`node_modules` 是链接布局**（真实文件在 `.pnpm-store/`）。所以 `node_modules/**` 里那些
  用相对路径瞎猜依赖位置的脚本会失效 —— 本项目没有这种脚本，全部依赖都走 `import`，
  测试直接 `import ../src/*.ts`。
- **依赖的安装脚本默认不执行**（pnpm 10+ 的默认行为，`.npmrc` 里显式写出来免得被误改）。
  这里唯一需要脚本的是 `electron` 的二进制下载：受限网络下它会失败
  （实测 `EPERM: mkdir C:\Users\Administrator\AppData\Local\electron`，**这跟 pnpm 无关**，
  npm 时代同样失败）。要用桌面模式就单独放行：

  ```bash
  pnpm approve-builds      # 勾选 electron，允许它跑安装脚本
  pnpm rebuild electron    # 只重跑 electron 的脚本，不重装全部依赖
  ```

- **存储与缓存放在项目内**（`.npmrc` 里的 `store-dir=.pnpm-store` / `cache-dir=.pnpm-cache`）。
  这样换机器/换用户时不必碰全局目录，`pnpm store prune` 也只影响本仓库。
  两个目录都在 `.gitignore` 里。

| 形态 | 入口 | 说明 |
| --- | --- | --- |
| **web** | `index.html` → `/src/main.ts` | Vite 打包成 `dist/`；`base: './'` 所以放任意子目录都能跑 |
| **cli** | `src/cli.ts`（Node 直接跑 TS，不经打包器） | `sim` 无头跑局出报告；`serve` 静态服务器。**不依赖渲染层与界面层**，所以纯 Node 里能跑 |
| **desktop** | `desktop/main.mjs`（Electron 主进程） | 只做"窗口 + 安全默认值 + 起服务器"，游戏逻辑一行不重复 |

为什么桌面模式要起一个服务器再加载 `http://127.0.0.1:…`：本作是真 ES 模块，
Chromium 在 `file://` 下会因 CORS 拒绝执行 module 脚本 —— 直接
`loadFile('dist/index.html')` 得到的是一个白窗口。所以 `desktop/shell.mjs` 与
`pnpm run serve` **共用同一个 `server/static.mjs`**。

服务器那一层是按"能被公网碰"的标准写的（虽然默认只回环）：路径穿越被显式拒绝
（`..`、`%2e%2e`、反斜杠、盘符、NUL 都有测试，并且用**裸 socket** 验证过 —— 因为
`fetch` 与浏览器会在客户端先把 `/../` 规范化掉，用它们测等于没测）、只允许 GET/HEAD、
带 `X-Content-Type-Options: nosniff`、带 hash 的产物长缓存而 html 用 `no-cache`。

> `dist/` 里是 ES 模块，**必须用 HTTP 打开**（`pnpm run serve` / `pnpm run preview` / 桌面外壳都行）。
> 直接双击 `dist/index.html` 会被浏览器的模块 CORS 策略拦下 —— 这是 ES 模块的规矩，不是配置问题。
> 开发期用 `pnpm run dev` 就没这个问题。

> Electron 的二进制不在包里，首次安装会从 GitHub 下载约 100MB。受限网络下它会因为
> 往 `%LOCALAPPDATA%\electron` 写缓存而失败（实测 `EPERM`，npm 时代一样），可以给镜像与缓存目录：
> `$env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"`、`$env:ELECTRON_CACHE="$PWD\.electron-cache"`。
> 没装成时 `pnpm run desktop` 会直接告诉你怎么办，而不是抛一个栈。

## 操作

**两种战斗模式**（设置里切，`设置 → 战斗模式`）—— 这是同一套模拟层的两条输入路径，
不是两个玩法：切换只影响"谁来瞄准、谁来决定何时开火"，伤害与数值一个字节都不变。

| 模式 | 武器 | 技能 |
| --- | --- | --- |
| `auto`（默认） | 自动锁定最近敌人开火 | 冷却好了**自动**朝自动选的目标放 |
| `manual` | 玩家自己瞄准 + 自己按开火 | 玩家自己瞄准 + 自己按键放 |

| 按键 | 作用 |
| --- | --- |
| `W A S D` / 方向键 | 八向移动 |
| `Shift` | 按住慢走，用于微操走位 |
| `空格` | **手动模式**：开火（自动模式下无作用） |
| `1` `2` | 释放技能槽 1 / 2 |
| 鼠标 | **手动模式**：准星即朝向（只取方向，离角色多远都一样） |
| 右摇杆 | **手动模式**：手柄瞄准（左摇杆移动） |
| `空格` / `P` / `ESC` | 暂停菜单 |
| `F` | 切换 1x / 2x 游戏速度 |
| `1` `2` `3` `4` | 升级界面快速选卡（选卡时不跑模拟，所以技能不会同时放出来） |
| `Enter` / `N` | 商店界面直接进入下一波 |

> ⚠ 手动模式**不改时序**、不加任何"手感补偿"：它只是不再替你扣扳机。
> 技能读的是**按键边沿**（按一下放一次），开火读的是**按住** ——
> 按住连放会让冷却与能量失去意义，那等于把自动模式换个名字。
> 于是"自动模式下的行为指纹"这条硬判据仍然成立（见下文「当前状态」）。

鼠标点击即可操作全部 UI（选角、购买、卖出、刷新、锁定）。

## 玩法循环

1. **波次战斗** —— 每波 20~60 秒。怪物从战场边缘涌入，撑满时间即过关；
   时间到后场上剩余怪物清完才结算（HUD 显示"清场"）。
2. **材料 = 经验 + 货币** —— 击杀掉落材料，靠近自动吸附。材料既升级也当钱花。
3. **升级选属性** —— 每次升级从 4 张卡中选 1 项（20 种属性方向）。
4. **波间商店** —— 用材料买**武器**与**道具**，可刷新、可锁定商店、可半价卖出武器。
   货架上每一件都带**词条**（前缀 / 后缀，按品级 1~3 条），所以"这件值不值这个价"
   是能看出来的（详见 [`docs/history/03`](docs/history/03-体系化与数值曲线.md) 的「词条系统」）。
5. **随机道具包** —— 花钱赌一件随机道具。价格 = 概率表期望值 × 折扣，
   普通包赌中低层、高级包赌高层（T4 专属）；**幸运**既提高开出品质、又让实际折扣变优。
6. **武器上限 6 把** —— 全部自动开火，同屏满配 6 把才是完整形态（还原原作核心特色）。
   同名同档两把可**合成**一把更高的（品级 T1–T5），合成时两把的词条**各取更好的那条**。
7. **技能与技能构筑** —— 每个角色有自己的技能表与技能树（见下方「技能」一段）。
   技能不是"多一把武器"：它有**能量**（每帧回充、施法扣除），所以"这一发火球还是留着放大招"
   是一个真取舍，不是自动化的一部分。

**轴外循环**（长线部分，设计与实测详见 [`docs/history/01`](docs/history/01-长线化与三角.md)）：

> 这里的"局内 / 局外"**不是屏幕或分屏**，而是**同一场游戏里的不同场景**：
> "局内"= 战斗那条轴（`Game.STATES` 里的战场 / 升级 / 商店 / 营地），
> "局外"= 另外两条轴（**养成** / **经营**）的场景。三者**平级、不互相嵌合** ——
> 战斗产出材料，材料被玩家**自己拿去打造**装备，装备再回到战斗，闭环靠"打 → 造 → 再打"。

> **模块 ≠ 系统**：**模块**是用户**定义游戏机制与玩法**的方式（战斗 / 经营 / 养成），
> **系统**是**全局都生效**的能力层 —— 技能 / 角色 / 天赋 / 装备 / 武器 / 道具 / 能力 / 属性 / 时装 / 状态。
> 两条轴不互相代替：不存在"技能模块"，也不存在"战斗系统"这个说法。定义与需求账在
> [`docs/requirements.md`](docs/requirements.md) 的 §一「术语约定」与 R50。

- **局内营地** —— 波次之间可以去建/升级设施，花的是本局材料，结算清零。
- **跨局据点** —— 用**孢子**（局外货币）买永久设施，给的是**功能**而不是纯数值：
  多一个营地设施位、营地更便宜、多一个货架位、每波白送刷新、开局带材料、孢子产出更高。
  其中"营地 +位子"与"营地更便宜"是**两条循环的连接线**（自检里没有它们就直接报错）。
- **角色天赋树** —— 每角色一棵，四级节点（微点 / 显著点 / **同类互斥的精通** / **唯一的基石**），
  产物**只是开局条件**，绝不进模拟层。
- **难度阶梯 10 级 + 通关条件** —— 撑到第 20 波并清场 = 通关；打赢第 N 级解锁 N+1（每角色独立）。
- **每日 / 每周挑战** —— 共享种子（UTC 日期键 / ISO 周键），成绩出**可离线复算的成绩码**，
  不需要服务器也不需要信任提交者。挑战**不接天赋与据点**（全体同条件）。
- **离线产出** —— 买了据点里的「菌床」之后才开：10 分钟起算、单次封顶 8 小时、满级约 86 孢子
  （一局通关约 93）。**结算即前进**，所以刷新页面刷不出来。

**Boss 波**：每 5 波出现「荒原暴君」，扇形弹幕 + 高血量，掉落大量材料。

## 内容规模

- **9 个角色**：全能人 / 狂战士 / 元素法师 / 工程师 / 受虐狂 / 角斗士 / 收藏家 / 疾行者 / 掘进者（隐藏）
  （各有独立初始属性、起始武器与专属机制，如受虐狂低血增伤、工程师炮塔）
- **24 把武器**：近战 10 把（匕首、长剑、长矛、战斧、雷霆战锤、裂地锤、火把、电击棒、等离子刃、触手）
  + 远程 14 把（手枪、冲锋枪、霰弹枪、狙击枪、激光枪、火箭筒、喷火器、磁轨炮、十字弩、弹弓、哨戒机枪、变异手枪、转轮机枪、元素法球）
  含穿透、散射、爆炸溅射、链式电弧、灼烧、无限穿透光束等差异化机制
- **29 个道具**：T1~T4 四个品级，从咖啡到外骨骼，含"便携炮塔""克隆装置"等特殊效果
- **19 条词条**（前缀 9 / 后缀 10）：按品级滚 1~3 条落在**这一件**武器或道具上，
  档位跟着品级走（T1 只能滚 T1 词条）；槽位分五类（武器 / 护具 / 饰品 / 工具 / 补给），
  并有 `weapon:近战`、`armor:重型` 这类细分（"重型护甲 +闪避"这种噪音搭配不会出现）
- **随机道具包**：普通包 / 高级包两种赌注，价格由概率表期望值反推，幸运提高开出品质
- **20 个技能 / 15 个符文 / 9 张技能树**（每个角色一张）：技能拆成
  **形**（6 种：弹丸 / 扇形 / 环 / 直线 / 装置 / 自身）× **效**（8 种：伤害 / 灼烧 / 电弧 / 减速 / 定身 / 击退 / 治疗 / 吸血）× **符文**（15 个改造器），
  所以"同一个火球改成三连发"是换一个符文，不是新写一个技能（详见下文「技能」一段）
- **两种战斗模式**：`auto`（默认，武器与技能都自动）／`manual`（自己瞄准、自己按开火与技能）
- **13 种怪物** + 精英化变体：异形幼虫、尖刺兽、酸液喷射者、重装巨块、分裂粘体、粘体碎块、浮游之眼、
  爆裂菌、孢子牧者、掘地者、母巢、钟摆、荒原暴君（追击 / 远程 / 环形弹幕 / 自爆 / 分裂 / 治疗光环 / 掘地 / 召唤 / 摆锤 / Boss）
- **战场**：外星荒漠（红棕 + 土黄平涂地块、抖动过渡、深色岩石碎石、白骨残骸、地面裂纹）

## 技能（**形 × 效 × 符文** + 每角色一棵技能树 + 两种战斗模式）

需求原话是"每个角色技能和技能构筑都不一样"。要满足它，**不能**靠写 9 套代码 ——
那会在第 3 个角色就变成一条 `if (char === 'mage')` 的长链。所以技能被拆成**三张正交的表**：

| 表 | 它回答什么 | 内容 |
| --- | --- | --- |
| **形** `FORMS` | 怎么把效果送出去 | `bolt` 弹丸 / `cone` 扇形 / `nova` 环 / `beam` 直线 / `summon` 装置 / `buff` 自身 |
| **效** `PAYLOADS` | 打中了做什么 | `damage` / `burn` 灼烧 / `shock` 电弧 / `slow` 减速 / `stun` 定身 / `knock` 击退 / `heal` 治疗 / `leech` 吸血 |
| **符文** `RUNES` | 同一个技能怎么长 | 15 个（8 个通用 + 7 个角色专属），改的是**参数**不是种类 |

20 个技能 = **9 个角色各 2 个专属** + 2 个通用（`过载弹` / `冲击环`）。
拆成三张表的理由很具体：**"同一个形状换一种效果"必须表达得出来** ——
它是构筑的来源。于是"同一个火球改成三连发"只是换一个符文，不是新写一个技能。

### 每个角色一棵树，两张卡

技能树按**技能表自己的扇区**生成（`ch` 字段），**不遍历角色表** ——
遍历角色表就要 `import data_chars.ts`，而 `profile.ts`（meta 层）读技能模块，
那一行会构成一条**向上的依赖边**（低层认识高层），架构门会红。
角色名与定位由调用方**注入**（`Skills.make({ chars })`）。代价是"漏掉一个角色"这里看不出来，
所以 `audit()` 拿注入的角色清单做覆盖判据。

| 卡 | 选什么 | 候选 |
| --- | --- | --- |
| ① 战斗方式 | 这一局主用哪一个技能 | 自己的 2 个专属 + 1 个通用（三选一） |
| ② 改造 | 给主技能挂一个符文 | 自己的专属符文排第一 + 通用符文（三选一） |

3 × 3 = **9 种构筑/角色**。候选里**不含别的角色的技能**：角色的身份靠"你能挑的技能"体现，
如果人人都能挑火球，法师就只剩数值差异了。一张卡**只能打一次**（打完就定下来，这才是"构筑"）；
`Skills.canPick` 是**唯一**的校验实现，模拟层与档案层共用它。
**重打免费** —— 构筑管的是"这一局怎么打"，与数值成长无关，收钱只会让玩家不敢试。

### 技能不是"多一把武器"：能量

技能有冷却**也有能量**（0~100，满条约 12 秒回满，施法按 `cost` 扣）。
为什么不用冷却就够：只有冷却时"两个技能谁先放"没有取舍；
有能量之后"这一发火球还是留着放大招"变成真选择。
能量**不是新货币** —— 它不进钱包、不参与结算，只是这一局里的一条资源。

### 两种战斗模式（设置里切，`设置 → 战斗模式`）

| 模式 | 武器 | 技能 |
| --- | --- | --- |
| `auto`（**默认**） | 自动锁定最近敌人开火 | 冷却好了**自动**朝自动选的目标放 |
| `manual` | 玩家自己瞄准 + 自己按开火 | 玩家自己瞄准 + 自己按键放 |

**这是同一套模拟层的两条输入路径，不是两个玩法**：切换只影响"谁来瞄准、谁来决定何时开火"。
同一个技能在两种模式下是同一个技能，唯一的区别是"方向从哪来"
（`target:'aim'` 的技能在 `auto` 下用最近目标的方向，在 `manual` 下用玩家的方向）。
伤害、冷却、能量、时序**一个字节都不变**。

实现上有两条硬约束，都是为了不把上面那句话变成谎话：

1. **输入必须打包成纯数据再过界** —— `src/input.ts` 的 `Input.manualInput()` 产出
   `{aimX, aimY, fire, cast, slot}`，模拟层不认识 DOM、不认识鼠标。
   于是**录制回放天然支持手动模式**：`record.ts` 记的就是这个对象，重放时不需要真有一只鼠标。
2. **技能读边沿，开火读按住** —— 按住连放会让冷却与能量失去意义（那等于把自动模式换个名字）；
   而连射武器按住即连发是玩家的期待，所以开火是按住。

### 守卫（`test/skill.mjs`，六节）

| 节 | 判据 |
| --- | --- |
| 表有效性 | 形/效/符文的参数与默认值齐备、**每个角色 ≥2 个专属技能**、**没有两个角色的技能集相同**、每张卡 ≥1 个专属技能 |
| 折叠正确性 | 逐符文比对折叠结果的参数与修正（**符文改的是 mods 还是 params 要分别验**） |
| 模拟行为 | 自动模式会放 / 手动模式不会自己放 / 手动模式按了会放 / 伤害真的落到了怪身上 |
| 默认档不变 | 空构筑 + `auto` 时，行为与"没有技能系统"逐位相同 |
| 档案层 | 打过的卡只读一次即生效、非法选项被拒、重置后回到空构筑 |
| 接线形状 | 源码里 `Skills.make` 必须排在 `skillsRef.audit()` 之前（启动顺序是**静态检查**，不是靠跑一遍碰运气） |

## 美术宪法（写进代码里的硬约束）

这套视觉规范不是"尽量做到"，而是**架构层面强制**：

1. **唯一外轮廓色** —— 所有实体一律 `#100d0c` 纯黑描边（3px 基线），没有第二种描边色。
2. **纯色平涂** —— `draw2d.ts` **不提供**任何渐变 / 阴影 / 模糊 / 贴图 API（有意为之）。
   体积感靠"同色系压暗的硬边色块"表现，而非光影过渡。
3. **低饱和复古调色板** —— 全部颜色集中在 `utils.ts` 的 `PAL` 里，禁止散落硬编码。
4. **地面用有序抖动（dither）** 做色带过渡，属于复古平涂语言，不是渐变。
5. **零 3D / 零写实 / 零景深** —— 没有光照模型、没有法线、没有金属反光、没有玻璃质感。
6. **热点特效克制** —— 命中白闪 / 挥击弧 / 爆炸环都是纯色块，不抢主体视线。

`test/render-check.mjs` 会在运行时**拦截渐变与阴影 API 调用**，一旦有人破坏宪法，测试直接失败。

### ESM 化：从 "IIFE + 挂 window" 到真正的模块

改造前每个文件都是 `(function (global) { ... })(window)`，模块之间靠 `global.Game` / `global.U`
互相找对方，`index.html` 里手写 16 个 `<script>` 决定加载顺序，测试用 `vm.runInThisContext`
逐个求值。问题是：依赖关系只能靠注释和自觉维持，顺序错了、名字拼错了都要等运行时才炸；
`tsconfig` 里还得用 `declare var U: UtilsApi` 把 16 个全局"假装"成变量，等于把类型检查也一起关掉了。

现在 16 个文件全部是 `import { X } from './x.ts'` / `export { X }`，换来四件事：

| | 改造前 | 改造后 |
| --- | --- | --- |
| 模块边界 | IIFE + `global.X`，靠加载顺序 | 真实 `import` / `export`，依赖写在文件头 |
| 类型来源 | `declare var`（16 个假的全局变量） | 从定义处推断，跨文件签名真实可查 |
| 运行源码 | 必须先 `tsc` 编译到 `js/` 才能跑 | 浏览器与 Node 都直接跑 `src/*.ts` |
| 测试加载 | `vm.runInThisContext` 手写文件列表 | `await import('../src/game.ts')`，Node 原生类型擦除 |

顺带修掉的三个真实问题：

1. **`declare var` 掩盖了色板类型**。`PAL` 之前被声明成带索引签名的 `Palette`，所以 `PAL.HP`、
   `PAL.CREAM`、`PAL.PAPER` 这些**根本没定义**的键能通过类型检查；改成从 `utils.ts` 导入后，
   必须显式给色表加 `var PAL: Palette` 标注才成立 —— 也就是说这三个键的存在性以前是没人管的。
2. **`global.` 批量改写会把"取短名"一起删掉**。`var w = global.innerWidth, h = global.innerHeight;`
   和 `var U = global.U;` 长得像，但前者是真实声明；第一版迁移脚本把它一起删了，
   `R.resize()` 直接报 `Cannot find name 'w'`。现在只有"左右同名"的别名才删。
3. **假导入会伪造循环依赖**。`sprites.ts` 里有个函数内局部变量叫 `R`（`var R = 26 * sc`），
   按字面扫描会误判成"渲染层的 R"，于是 `sprites → render → sprites` 成环。
   迁移脚本改成"文件里出现过 `var R` 就一律不导入"，宁可由 tsc 报错再补。

`test/ui-check.mjs` 现在会**解析整张 import 图**并断言：无环、模拟层不得依赖渲染层/界面层、
造型库不得依赖玩法、绘制原语层只能依赖 `utils`、`main.ts` 不被任何模块导入。
这类"分层塌陷"以前只能靠人自觉，现在改坏了测试直接红。

> `tools/*.cjs` 是迁移期留下的一次性脚本（IIFE→ESM、CJS 测试→ESM、早期 JS→TS 标注）。
> 工作已经做完，留在这里是为了让"当时到底怎么改的"可复查，不是运行期依赖。

### 组件式组合：所有对象都由组件拼出来

改造前每种对象都是手写对象字面量，而且存在"用到才挂上去"的字段：

| 症状 | 后果 |
| --- | --- |
| `w.dup` 只在一局里有多把同名武器时才赋值；`e._spr` / `e._fl` 首次绘制才挂上 | 同类型的对象在运行期长出不同形状（V8 隐藏类分叉），属性访问退化到慢路径 |
| `addStain` 先 `d = {}` 再逐个赋值 | 同上 |
| 字段齐不齐只能靠人读代码 | `weapon` 少写一个 `cd`，要等跑到 `checkWeapon` 才炸 |

现在所有游戏对象都是 `Comp.archetype(原型, [组件...])` 组合出来的：

```js
Comp.define('Cooldown', { cd: 0 });
Comp.archetype('weapon', ['WeaponCore', 'Cooldown', 'Seat'], { list: 'weapons' });
const w = Comp.spawn('weapon', { id: 'sword', def: def });
```

- **35 个组件 / 11 个原型**：player、enemy、bullet、ebullet、particle、pickup、decal、turret、weapon、item、offer。
- 造出来的对象**字段齐全、形状一致**；数组默认值按对象复制，不会两个对象共用一个数组。
- `Comp.assign` 写一个原型没声明的字段**直接抛错** —— 这是"漏声明组件"的主要入口。
- `Comp.query(sess, 'enemy')` 取集合，`Comp.run('particleStep', list, dt)` 跑系统；
  系统声明自己需要哪些组件，首次运行时校验集合里的原型确实具备（`particleStep` 声明 `Lifetime + Motion`）。
- `Comp.audit(obj)` 找游离字段。`test/comp.mjs` 会打一场真实对局，把场上**每一个对象**都审一遍：
  原型正确、无游离字段、无缺字段、同类对象形状一致。
- `Comp.selfCheck()` 把**工厂裸产物**与模板逐字段 `Object.is` 比对（`NaN` / `-0` / 科学计数法 /
  字符串转义都在这一条上），另外检查数组默认值不共享。它用裸产物而不是 `spawn` 产物是有原因的：
  `onSpawn` 钩子本来就会改写字段（`player.rig` 模板里是 `null`，出生时由钩子搭骨架），
  拿钩子之后的对象去比是误报。

实测（都是量出来的，不是估计）：

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 真实波次截尾均值 | 0.172ms/步 | 0.175ms/步（噪声内） |
| 300 怪压力场景截尾均值 | 0.637ms/步 | 0.643ms/步（噪声内） |
| `Comp.spawn('bullet')` vs 手写字面量 | — | 79ns vs 18ns（**4.4×**，两侧都取三次最小值） |

前两行是同一台机器上前后对照测的；跨运行波动约 ±10%（后续一次复测是 0.186 / 0.677ms），
所以"噪声内"是真的噪声内，不是挑了个好看的数字。

第三行值得展开：这个数字改过三代实现，每一代都是被测试当场打回去的：

| 代 | 做法 | 实测 |
| --- | --- | --- |
| ① | 逐字段从模板拷贝（`Object.assign` 思路） | ~1650ns（**47×**）—— 模板是运行期逐个加属性建起来的字典模式对象，每次 spawn 都在做哈希查找 |
| ② | 按原型代码生成构造函数，值仍从模板读 | ~290ns（**15.8×**）—— 隐藏类与模板一致了，但每次 spawn 仍要读 24 个属性 |
| ③ | 代码生成 + 把原始值**内联进生成源码** | ~79ns（**4.4×**）—— 生成的函数体就是一句对象字面量，不读模板、不持有闭包上下文；剩下的倍率全是 `Comp.spawn` 自己的查表与判断（未注册原型 / 覆盖值 / `seedPrev` / 钩子） |

两个都是测试抓出来的、不是我先验就知道的坑：

- ②→③ 之前，参照组（手写字面量）**不逃逸**，V8 做了标量替换 + 常量折叠，
  量出来 **1.1ns/个**，于是比值假到 **248×**。现在参照组也把对象写进循环外的变量强制逃逸，
  并加了一条断言 `字面量 > 5ns` 守住"参照组是真的在分配对象"——参照物跑飞了比被测对象慢更隐蔽。
- 内联进源码的值写错（`NaN` / `-0` / 科学计数法 / 字符串转义）不会有语法错误，
  只会静默变成别的值。所以 `Comp.selfCheck()` 现在把**工厂裸产物**与模板逐字段 `Object.is` 比对
  （用裸产物而不是 `spawn` 产物：`onSpawn` 钩子本来就会改写字段，比如 `player.rig`
  模板里是 `null`、出生时由钩子搭骨架），`test/comp.mjs` 另外造了一个边角原型专门压这条。`

刻意**没有**做成原型的：升级词条（直接引用 `UPGRADE_POOL` 里的共享定义）、刷怪表
（`Enemies.buildWave` 的产物）、事件载荷与 `RunSummary`。它们是共享定义 / 每波一次的记录 /
跨层数据包，不是每帧实体；把它们克隆成组合对象只会改变共享语义，没有收益。这条边界也写在测试输出里。

### 骨架系统：角色是"骨头 + 绑在骨头上的部件"

改造前角色是"把形状贴在坐标上"：手臂是一个从肩点画到 `(±armX*1.18, armY + ry*(0.42 ∓ swing*0.35))`
的胶囊，五官是相对 `(cx, cy+bob)` 的一堆魔数，武器挂点在 `game.ts` 与 `render.ts` 里**各抄了一份**同样的
三角函数。角色没有骨头，也就没有"转身带动手臂""挤压带动五官"这种结构。

`src/rig.ts` 是通用骨架运行时，`src/bronana.ts` 是豆豆这个骨架的具体定义：

```
anchor ← 角色摆位（世界坐标，scale 1）
 ├─ body   ← 躯干：缩放就是角色半径（尺寸 + 呼吸挤压都在这里）
 │   ├─ head   ← 五官挂点（眼线）
 │   ├─ armL   ← 左臂：肩在骨头原点，手在骨头末端
 │   └─ armR
 └─ w0…w5  ← 6 个武器挂点（挂在 anchor 而非 body：现有效果里武器不随呼吸起伏）
```

- **定义期就抛错**：骨头重名 / 父骨不存在 / 层级成环 / 两根骨头抢同一字段 / 部件绑到不存在的骨头 /
  两个部件抢同一层序 —— 全部在 `compile` / `parts` 阶段抛。`Skeleton` 作为组件挂在 `player` 原型上。
- **部件有声明式的绘制层序**（`Bronana.PAINT`：躯干 10 → 暗部 12 → 豆豆坑 14 → 手臂 30/32 → 五官 40 → 武器 50），
  层序就是执行顺序，测试断言它严格递增且与数组顺序一致。
- **姿态求值零分配**：每根骨头 14 个 `Float64Array`，`Rig.set/reach/update` 全程不产生垃圾；
  手臂用 `Rig.reach`（绕关节旋转 + 沿骨轴伸缩两自由度）让"手要落在这个点上"这类既有轨迹被**原样复现**。
- `Rig.stale(inst)` 暴露"写过姿态但没跑正向运动学"这个最典型的静默错误（画出来的东西永远慢一帧）。

两处刻意的设计决定，都写在 `rig.ts` 文件头：

1. **骨头带完整 TRS，父骨的缩放作用到子骨的平移**。所以"呼吸挤压"只改躯干骨一根，
   头与手臂的世界位置自动跟着走（测试断言了头相对躯干的位移随挤压变化）。
2. **`Rig.at` 只应用平移 + 旋转，刻意不应用缩放**。本作的美术宪法是"粗黑外轮廓统一 3px"，
   把缩放进 ctx 变换会把 3px 描边变成各向异性的椭圆描边。需要缩放几何的部件改用 `Rig.point`（完整矩阵）。

**几何等价是测出来的，不是我保证的**：`test/rig.mjs` 把改造前的闭式公式逐字抄进测试，
扫 1080 组（bob × 摆臂 × 挤压 × 朝向）参数逐一比对 ——

| 项 | 项数 | 最大误差 |
| --- | --- | --- |
| 躯干 / 双肩 / 双手 / 眼线 | 1080 | **0.00e+0**（逐位相同） |
| 武器座 / 枪口 / 子弹出生点（6 槽 × 5 个瞄准角） | 90 | 1.14e-13 |
| 五官位置（含朝向偏移与两个嘴位） | 9 | 1.14e-13 |

顺带消掉了那个隐患：武器挂点现在由模拟层与渲染层**调用同一根骨头上的同一个函数**
（`Bronana.seat`），`w.index` 与数组下标的一致性也进了测试（卖武器后重新编号）。

开销（`test/rig.mjs` 实测）：摆位 + 正向运动学 **0.80 µs/次**、武器挂点 **0.84 µs/次**；
模拟层整体截尾均值与骨架化之前同量级（噪声内）。

#### 骨架接上之后又清掉的东西（优化 pass）

骨架成了挂点的唯一来源之后，"为了挂点而存在的缓存"就全变成了死状态。这一轮按"没被读过就不留"
逐项清掉，并全部进了 `test/rig.mjs` 的回归断言：

| 项 | 之前 | 现在 | 依据 |
| --- | --- | --- | --- |
| `WeaponCore` 字段 | `id def swing swingDir flash index dup` | `id def swing dup` | `swingDir` 全仓库零读写；`flash` 只有"写 + 自减"、没有任何读取（枪口特效本来就由 `Emit.muzzle` 的粒子负责） |
| `Seat` 字段 | `wx wy ang` | `index` | 挂点坐标改由骨架按需算，缓存的 `wx/wy/ang` 只剩 `fire()` 里那一次写入，没人读；`index`（挂点槽位号）从 `WeaponCore` 挪到 `Seat` —— 槽位是挂点的事，不是武器核心的事 |
| 玩家骨架 | `newSession` 里再 `Comp.assign(p, { rig: Bronana.create() })` | `Comp.spawn('player')` 出生即带 | 新增 `Comp.onSpawn(原型, fn)` 生成钩子：对象/函数类型的默认值写不进组件，以前只能靠调用方记得补一次，忘了就是渲染期一个 TypeError。热路径上没有钩子的原型只多一次 falsy 判断 |
| 近战弧度 | `game.ts` 两遍（命中锥 + 挥击特效）+ `render.ts` 一遍 | `Bronana.meleeArc(def)` 一份 | 测试里加了静态断言：`game.ts` / `render.ts` 不再出现 `arc \|\| 90` |
| 缺骨架时 | `Rig` 里冒出的 `TypeError` | `bronana: 没有骨架实例 —— player 原型的 Skeleton 组件里 rig 为空` | 失败要指向原因，不指向现象 |

**明确没做**：把每帧 6 次武器挂点的正向运动学合并成一次。实测武器挂点 **0.84 µs/次**，
一帧 1 次摆位 + 6 次挂点 ≈ **6 µs**，占 16.6 ms 预算的 **0.036%** —— 为它引入"批量摆位 + 记得收尾
`update`"这层 API，等于用一个新陷阱换 0.036%。测量结果是"不值得"，所以没做。

### 骨架化过程中挖出来的渲染 bug（**画面有变化**）

老 `sprites.drawBronana` 里这段顺序是错的：

```js
x.save();
D.bronanaPath(x, rx, ry, s);      // 路径在这里就按"当前变换"映射到设备空间了
x.translate(cx, cy + bob);     // 之后再平移，不会移动已经建好的路径
x.clip();
```

Canvas2D 的路径在加入时就被当前变换固定，`translate` 不会移动它。于是裁剪区留在"变换原点"上：

- **游戏内**：变换原点是战场左上角，裁剪框离角色 **1050px**（zoom=1）→ 躯干的暗部与高光**被整块裁掉**，
  角色是平涂的；同时在战场原点被多填了一块 39×41 的豆豆形剪影（zoom=0.5 或宽窗口时**在视口内，肉眼可见**）。
- **UI 肖像**：变换原点就是角色中心，所以一直是对的 —— 也就是说**同一套代码在游戏里和角色卡上画出来的不是同一个豆豆**。

用带 CTM 追踪的桩（`test/_ctx.mjs`，能记录每次 clip / fill 落在设备空间的包围盒）测出并写进回归断言：

| | 改造前 | 改造后 |
| --- | --- | --- |
| 裁剪区离角色（zoom=1 / 0.5） | 1050px / 525px | **0.45px / 0.23px** |
| 战场原点那块游离剪影 | 有 | 无（断言全部绘制都在角色 3.2R 内） |
| 肖像路径 | 一直正确 | 仍然正确 |

骨架化之后这个 bug 在结构上写不出来了：路径建在躯干骨坐标系里，`translate` 没有地方可放错。

**⚠️ 这一条会改变画面**：暗部现在真的画出来了，而这段代码是"整个剪影先填一层暗色、再压一块高光"，
所以游戏内角色会从"浅色平涂"变成与**角色卡肖像完全一致**的样子（本色 tint[1] + 一块高光）。

同一个模式在 `sprites.ts` 的 blob 造型里也有（`D.bronanaPath` 之后才 `translate`），
裁剪同样落偏：贴图里偏 1.00R（26~78px，随体型）。修法一样（先 translate 再建路径，
椭圆坐标同步改成角色局部坐标），修完 blob 的裁剪偏移 **1.00R → 0.00px**。
顺带要说明一句我先前说错的话：我原本判断"按字面修会让所有 blob 变成一整块纯暗色，所以肯定是笔误"——
这个判断不成立。blob 的色阶是温和的一档（`#8f6fae → #6b5086`、`#b0603c → #83442a` 等），
而且 **jelly 分支本来就是"整个钟形压一层暗色"**，一直如此。所以 blob 现在与 jelly 得到同一种处理。

### 同一个坑的第三处：尖刺怪的星形画在了脚底（**画面有变化**）

`starPath` 在**局部原点**建路径，而 spiky 分支直接 `D.starPath(...)` 就填充 —— 没有先平移到身体中心。
于是星形被画在"脚底"上（比身体中心低 R）：下半截插进地面、上半截几乎没露出来，
看上去像"一颗圆球身上随便扎了几根刺"，而且顶部那几根还离得很远。
修法是同样的三步（`save` → `translate(cx, cy)` → 建路径 → 填充 → `restore`），
修完星形与身体圆同心，"尖刺兽"才是真的尖刺兽。
`test/rig.mjs [9]` 现在按**实测内容包围盒**断言：全部 10 种怪物贴图的内容都落在画布内、
上下留白有界、内容水平居中（改造前 spike / exploder 的星形有 8~10px 画在画布外）。

### 怪物贴图的"正方画布"（**画面有变化，改得最多的一处**）

`make()` 里有两个互相打架的"半个约定"：画布高写成宽（正方画布），
同时又按 `(w/2, h)` 平移原点；而 `enemySprite` 的回调里还有一次 `translate(0, up)`。
结果原点落到 `(w/2, 2·up + down)` —— **比画布底边还低**，内容的下半部分整块画不出来，
`drawEnemy` 再按"贴图底边 = 脚底"（`-spr.height - 4`）定位，于是怪物又被整体上移 6~10px。

实测（`test/rig.mjs` 的 CTM 桩量出来的包围盒）：grub 底部有 25px、giant 有 78px 画不出来。
也就是说**怪物一直只显示了上半截**：腿与触手全部丢失、身体被画布底边切平
（看上去像"贴在地上的半球"，所以一直没人觉得不对），而命中圈是按完整圆算的 ——
看得见的身体比命中圈小、还偏上，命中圈的下半部分完全在身体之外。

修法是把约定收敛成一个：`S.enemyBox(def)` 给出盒子（脚底以上 `up`、以下 `down`），
`make()` 只管画布尺寸、原点就是左上角，贴图自报 `bodyY`（身体中心在画布里的 y），
`drawEnemy` 把 `bodyY` 对准 `(ex, ey)`。于是：

| | 改造前 | 改造后 |
| --- | --- | --- |
| 可见身体高度（grub / giant） | ~31px / ~115px（下半截被切） | **53px / 159px**（完整） |
| 腿 / 触手 | 完全看不见 | 画出来了 |
| 身体中心相对敌人坐标 | 偏上 6~10px | **严格重合**（脚落在命中圈底部） |
| 精英光环 | 半径按命中圈（22×scale）算，Boss 身上会陷进身体里 | 按可见身体（26×scale）算，套在身体外 |
| 精英三角 | 挂在命中圈顶部 | 挂在可见头顶上方 |

**这一条会明显改变画面**：怪物比原来"高"约 40~70%（其实是原来被切掉了），
脚踩在地面上而不是浮着，命中圈与可见身体同心。可见身体半径仍是 26×scale、
命中圈仍是 22×scale（身体比命中圈大 18%），这是**刻意留的宽容度**，没有动。

## 拍板记录一：角色的暗部

修好裁剪之后，"整块剪影先填一层 `sh`"这一行就真的生效了。但它和紧随其后的腹部椭圆**用的是同一个颜色**，
而且它会把 `D.bronana` 画好的本色**整块盖住**——`skin.base` 只剩下轮廓描边的意义。三种改法：

| 方案 | 一行改动 | 画面结果 |
| --- | --- | --- |
| **A（已采用）** | 不动 | 整个身体 = 暗色 `tint[1]` + 一块高光。**游戏内与角色卡肖像完全一致**（角色卡一直就是这个样子，改之前只有游戏内角色是浅色平涂） |
| B | `bronana.ts` 的 `drawBelly` 里把整块剪影的填充色从 `skin.sh` 改成 `skin.base` | 本色身体 + 腹部暗块 + 高光。三色平涂（调色板本来就是 `SKIN / SKIN_SH / SKIN_HI` 三档），但 **8 张角色卡会一起变浅** |
| C | 删掉那一行整块填充 | 与 B 同色，但不动描边（B 会把 3px 黑边的内侧吃掉约 1.5px） |

选 A 的理由是它**不引入任何你还没见过的画面**：角色卡上的豆豆一直是 `tint[1]` + 高光，
游戏内的那个一直是浅色平涂，两者从来不是同一个东西；A 只是让它们统一到你已经看了很久的那一版。
连带的 blob 裁剪也按同一套（整个剪影压暗），与 jelly 分支对齐。想换成 B 说一声，两处各一行。

## 引擎与架构参考

> 为什么这个游戏是这么写的。下面每一条都是**先量、再定**，不是先立规矩。

### 碰撞体：弹丸的碰撞体是"线段 + 半径"，不是点

原本所有命中判定都是**落点法**：先 `b.x += b.vx*dt`，再看落点的圆有没有和怪重叠。
这在慢速弹上没问题，但最快武器 railgun 单步位移 36.7px，而判定阈值是 `子弹r + 6 + 怪r`：

```
两个采样点都要落在圆外才会漏 → 穿透带 = ( sqrt(阈值² - (步长/2)²) , 阈值 ]
```

实测（`tools` 里的探针，结论已进 `test/frames.mjs`）：

| 目标 | 阈值 | 老实现的穿透带 | 实测漏判区间 |
| --- | --- | --- | --- |
| grub（r22） | 33.0px | (27.4, 33.0]，宽 **5.6px** | d ∈ [28.5, 33] |
| 小怪（r15.4） | 26.4px | (19.0, 26.4]，宽 **7.4px** | d ∈ [20, 26] |
| 更小的怪（r12） | 23.0px | (13.9, 23.0]，宽 **9.1px** | d ∈ [15.5, 23] |

也就是说**擦边那一圈是打不中的**：子弹从怪身上穿过去、什么都不发生。

现在 `src/collide.ts` 提供形状与判定（纯数学，只依赖 `utils`），弹丸按**线段 × 圆**做扫掠：

```js
var x0 = b.x, y0 = b.y;
b.x += b.vx * dt; b.y += b.vy * dt;
var t = Col.segCircle(x0, y0, b.x, b.y, e.x, e.y, rad + e.r);   // 首次接触的插值位置
```

- 判定半径**保持原来的 `+6` 余量**（那是刻意的手感宽容度，不是误差补偿），所以扫掠只会
  把擦边那一圈补回来，**不会**把碰撞体撑大 —— 测试里两件事都断言了（带内全命中 + 阈值外不误判）。
- 候选按接触点的 `t` 升序结算，穿透（pierce）打到的第一只就是**最近**的那只（老实现是网格遍历顺序）。
- 敌弹对玩家同样走扫掠（阈值不变：`b.r + p.r - 4`），现在敌弹还慢，但改了速度不会突然漏判。
- 查询用 `Col.segBounds` 把线段退化成一次圆查询，候选缓冲是两个复用数组：**每步零分配**。

### 帧模型：逻辑帧固定，显示帧插值

改造前的问题不是"没有固定步长"（累积器一直有），而是**只有一份 1/60 写死在 main.ts 里**，
外加 8 个测试各自又写了一遍；更要命的是**逻辑帧和显示帧被绑成了一帧**——
144Hz 显示器上同一个逻辑帧会被画两遍，看起来是顿挫。

现在：

| | 做法 |
| --- | --- |
| 逻辑帧 / 物理帧 | `Game.cfg.fixedDt = 1/60`，**全项目唯一一份**；`maxSteps` / `maxFrameDt` 同样只在这里定义。main.ts 与 11 个测试套件都取它（测试里有静态断言防回退） |
| 一次逻辑帧做什么 | `step()` 里顺序固定：记录上一帧位置 → 刷怪 → 网格 → 玩家 → 武器 → 炮塔 → 怪 → 子弹 → 敌弹 → 掉落 → 粒子 → 清理。物理（积分 + 碰撞）就在同一个固定帧内跑完 |
| 显示帧 | main.ts 把累积器剩下的时间折算成 `R.alpha ∈ [0,1]`；渲染层用 `prev + (cur - prev) * alpha` 取位置 |
| 插值范围 | 玩家 / 怪 / 子弹 / 敌弹。**粒子与贴花不插值**：它们小而短命，给几百个粒子套变换换不来可见收益 |
| 位置来源 | `Transform` 组件带 `px/py`（上一逻辑帧位置）。`Comp.spawn` 对带这两个字段的原型**自动对齐** `px=x, py=y`，所以刚出生的对象不会被从 `(0,0)` 插过来（这是个真会发生的 bug：子弹与掉落都是在帧中间生成的） |

`R.alpha` 缺省是 **1**，也就是"直接画当前逻辑帧"—— 任何不设 alpha 的调用方（测试、`?still=1` 冻结截图）
行为与改造前逐像素一致，插值只在真正的显示循环里生效。

**代价（说清楚）**：插值意味着画面最多落后一个逻辑帧（16.7ms），这是固定步长 + 插值的固有代价；
换来的是高刷屏上的平滑。如果更在意输入延迟而不是平滑，把 `R.alpha` 固定成 1 就退回旧行为。

实测开销（`test/perf.mjs`，各跑 3 次）：扫掠 + 记录上一帧位置让模拟层**每步多约 0.01ms**
（真实波次 0.179~0.187ms，改造前 0.159~0.179ms；压力场景 0.664~0.673ms，改造前 0.608~0.697ms）——
即模拟层自身 +6% 左右，但模拟层只占 16.6ms 预算的 1.1%，换掉的是一整类漏判。

### 容器与对象管理：先量，再决定要不要管

体检方式是"跑满 3600 步（场上始终 300 只怪）+ 强制 GC 看堆底"，外加两个针对性场景
（六转轮机枪的弹幕、不打补丁连打 4 波）。两个问题分开看：**有没有泄漏**、**有没有失控增长**。

| 容器 | 上限 / 回收策略 | 实测峰值 | 结论 |
| --- | --- | --- | --- |
| `enemies` | `cfg.enemyCap` 300，超限回收最远的非 Boss | 300 | 有界 ✓ |
| `bullets` / `ebullets` | 无显式上限，靠 生命 / 出界 / 命中 自然回收 | 弹幕场景 **26**（6 转轮机枪 + 60 只贴脸怪） | 上界 = 射速 × 飞行时间，约几十；加 cap 无意义 ✓ |
| `pickups` | **无上限**，只在被拾取时移除（换波清空） | 实战 **22**；人为"只杀不捡"的跑步机场景 **862** | 实战自限；862 时每步代价约 0.1% 预算。**没加 cap** —— 加 cap 等于悄悄吃掉玩家的掉落 ✓ |
| `decals` | 环形缓冲 90（`decalCursor` 轮转覆盖） | 90 | 有界 ✓ |
| `particles` | 池 + 上限 420（满员 O(1) 轮转覆盖） | 弹幕场景 102 / 420 | 有界 ✓ |
| `textParticles` | 池 + 上限 28（非优先满员即丢弃） | 28 | 有界 ✓ |
| `turrets` | 每波按"炮塔道具数"重建 | 0（本次没带该道具） | 上界 = 道具槽 ✓ |
| `spawnQueue` | 每波由 `Enemies.buildWave` 重建 | 当波刷怪表长度 | 每波重置 ✓ |
| `grid.map` | 68px 单元格，`startWave` 换新表，查表时复用单元格数组 | **447 格**（战场 25×19 的理论上限附近） | 常数 ✓ |

**没有泄漏**：每次采样前强制 GC 两次，`heapUsed` 从 9.9MB 走到 10.1MB 后停住（3600 步）；
粒子池的自由链表恰好等于峰值（98 峰 / 98 空闲），`Emit.audit()` 重复引用 0。

这一轮体检挖出并修掉的东西：

| 问题 | 证据 | 修法 |
| --- | --- | --- |
| **`?test=demo` 开发场景手写对象字面量 push 进容器** | 贴花少了 7 个形状字段（`seq/a1/a2/d1/d2/s1/s2`）→ 渲染这一帧往 canvas 送 **14 次 NaN 参数**（`arc(NaN,NaN,NaN…)`），贴花根本画不出来 | 舞台搭建从 `main.ts` 抽到 `demo.ts`（**可被测试覆盖**），掉落走 `Comp.spawn`、贴花走 `Game._internals.addStain` |
| **`?test=play\|demo\|levelup\|shop` 会卡死浏览器** | `while (Game.wave < wave) Game.nextWave();` —— `nextWave()` 要求当前在 `shop` 状态（状态机测试专门守着这条），而 stage 是在 `playing` 下调用的，于是它每次返回 false、`Game.wave` 永不前进 → **死循环**（wave 默认 8，所以默认参数就中招） | 直接 `Game._internals.startWave(wave)` 搭出第 N 波；测试断言"能跳到第 6 波" |
| **`Emit.spawn` 用裸 `for-in` 写字段** | 池对象上写一个原型没声明的字段不会报错，会**悄悄长出游离字段**（同原型对象形状分叉，而且只有那条配方会中招） | 改走 `Comp.assign`：拼错的字段当场抛错 |
| **`cleanup()` 每步新建敌人数组** | 每步分配一个数组并拷贝最多 300 个引用，**即使这一帧没有任何怪死掉** | 改成就地交换删除（倒序遍历），零分配且保持数组身份不变 |

**量过但决定不改**：`updateBullets` / `updateEnemyBullets` / `updatePickups` 每步各建一个 `out` 数组
（3 个/步 = 180 个/秒）。堆底在 3600 步里是平的，说明这些短命数组连一次 GC 都没逼出来 ——
和当初"实测 193 次/秒的实体分配不值得上对象池"是同一个结论，为它改写成原地删除只是换个写法，
不换来任何东西。

### 关键架构决策：模拟层与渲染层严格分离

`game.ts` **完全不碰 DOM 和 canvas**，`render.ts` **只读世界状态、不做任何模拟**。
带来的好处是游戏核心可以在 Node 里以无头方式跑完整对局，于是：

```bash
node test/smoke.mjs        # 自动打多波、验证 23 把武器都能开火、10 种怪物行为正常
node test/rig.mjs          # 骨架：编译期校验 / 几何等价（1080 项）/ 暗部裁剪回归
node test/frames.mjs       # 碰撞体扫掠判定 + 逻辑帧常数 + 显示帧插值
node test/modes.mjs        # 零 DOM 加载 / 静态服务器 / CLI / 桌面外壳逻辑
node test/states.mjs       # 状态机：转换表 / 唯一入口 / 动作守卫 / 跳波回归
node test/signals.mjs      # 信号总线：异常隔离 / 重入保护 / 快照语义 / 死订阅
node test/particles.mjs    # 粒子池：一致性 / 上限 / 复用残留 / 回收泄漏
node test/packs.mjs        # 随机道具包：定价恒等式 / 概率分布 / 幸运收益 / 可复现
node test/render-check.mjs # 桩 canvas 跑 240 帧真实渲染，抓 NaN、违禁 API、贴图裁切、绘制预算
node test/cache.mjs        # 缓存：命中 / 倍率 / 失效路径 / 条目与内存账目 / 长局不重建
node test/ui-check.mjs     # 元素/CSS/data-act 契约 + 模块图 + 状态屏幕映射 + DOM 写入量
node test/perf.mjs         # 模拟层性能基准（帧耗时 / 帧预算占用）
node test/ai.mjs           # 怪物行为/弹幕模式：注册表校验 + 假 ctx 单测 + 真实对局冒烟
node test/depth.mjs        # Z 深度：层带表 / 排序确定性 / 槽位复用 / 真实一帧的层带先后
node test/registry.mjs     # 扩展点总账：27 个家族 / 跨表引用 / 跨文件静态契约
node test/containers.mjs   # 容器与对象管理：声明 / 统一回收 / 上限策略 / 长局不变量

pnpm run fingerprint       # 打印行为指纹（纯结构重构前后比对）
pnpm run probe             # 不变量随机探针：随机操作跑多局，每帧查会话不变量（找 bug 用）
pnpm test                  # 全部一起跑
```

`ui-check.mjs` / `render-check.mjs` 还会做几项**无需浏览器**的契约与预算检查，专治"只有打开浏览器才发现"的问题：

- **CSS ↔ HTML 契约**：`styles.css` 里的每个 id / 类选择器都必须能在 `index.html`（或动态类名白名单）里匹配到元素。
  历史上 HTML 从 `class="weapon-strip"` 改成 `id="weapon-strip"` 后 CSS 没跟着改，导致整条样式静默失效、武器槽跑到画面正中。
- **`drawImage` 参数类型**：首参必须是真 canvas。历史上精灵函数改为返回 `{canvas,width,height}` 后，
  有两处忘了取 `.canvas`，一处让角色选择抛异常并**中断了整个 UI 初始化**（所有按钮失效），一处让商店道具图标不显示。
- **入口契约**：`index.html` 必须只有一个 `<script type="module" src="/src/main.ts">`，
  且该文件存在 —— 手写 16 个 `<script>` 的时代已经结束。

体检一共改了四件事，都是**先量出来再做**的：

**1. 怪物 AI 抽成注册表模块（`src/ai.ts`，232 行）**
改造前行为与弹幕模式都是 `game.ts` 里的 if/else 链。问题不在分支多，而在**默认值会吞掉错误**：
`behavior` 写错一个字母，怪物会照常移动（走 else 分支）却**永远不造成接触伤害**；
`pattern` 写错则静默退化成单发 —— 10 种怪 4 种模式全靠人眼核对。现在：

```js
AI.behaviour('ranged', { note: '停在 keepDist 外环绕射击', move(e, ctx) {…} });
AI.pattern('fan', { big: true }, (def, base) => […]);   // 未知名字当场抛错
```

依赖倒置的收益是**可测性**：`ai.ts` 只依赖 `utils.ts`，要什么能力都由 `AiCtx` 注入
（查询 / 伤害 / 击杀 / 开火 / 夹取 / 随机数），于是 `test/ai.mjs` 能给一个假 ctx 直接断言
"该逼近还是该保持距离、该不该开火、光环该不该回血"，不必跑整局游戏。
`game.ts` 从 1612 行降到 1517 行，字符串分支 41 → 33。

**2. 行为指纹：纯结构重构不许改变对局（`tools/fingerprint.mjs`）**
抽模块最怕的不是报错，而是"没报错但怪物走位变了"。指纹用固定种子跑三段固定长度的对局
（ranger/1800 帧、gladiator/1800、engineer/1200），把位置/血量/等级/材料/场上各对象清单压成哈希。
它对**随机数消费顺序**极其敏感 —— 把一次 `rnd()` 挪到别处同样会被抓到。
`test/smoke.mjs` 里钉着基线：抽 `ai.ts` 前后指纹**逐位相同**（`5f763627` / `ac2a349e` / `b1d751da`）。
后来做「容器统一回收」时 gladiator 那条从 `ac2a349e` 变成了 `a00dad64` —— 子弹/掉落物从
"每步重建数组（保序）"改成"就地交换删除（不保序）"，遍历顺序变了，同帧多段命中的结算顺序与
分离力的浮点累加顺序就跟着变。这是**有意接受**的（交换删除 O(1)，保序删除要 O(n) 搬移，
引擎通用做法就是前者），基线已更新并在 `smoke.mjs` 里写明原因；另外两条没变，
说明差异只出现在"同一帧内有多个对象被移除"的情形 —— 这正是指纹该有的分辨力。

**3. 死接口清零。** 体检查出 30 个"全仓库零引用"的成员，逐个核对后删掉：
`U.pick/shuffle/PI/pct/fmtTime/mergeInto`（其中 `pick`/`shuffle` 的 `rnd` 参数缺省时退化成
`Math.random`，这种"默认值破坏可复现性"的助手留在公共 API 里迟早被误用）、
`S.maxScale/reset/drawParticle/drawArc`、`D.shade/polyPath/blobPath` 的转发别名、
`Comp` 的 7 个命名别名、`Settings.reset/FIELDS_DEF`、`Save/Storage.clearError`、
`Scene.states`、`R.toWorld`、`Sfx.hit/coin`。
公开面随之收窄：`CompApi` 25 → 18、`SpritesApi` 24 → 22、`DrawApi` 22 → 19、`UtilsApi` 22 → 19。

**4. 体检工具自己也被修过三次**（这些坑都写在工具注释里）：
注释里的名字被当成引用（本工具注释里就写着 `U.pick`）、
`\b` 对 `U.$$` 这种以 `$` 结尾的名字永远匹配不上（把活代码判成死的）、
`X.name =` 的定义行被算成一次引用（于是"全是内部使用"）。
—— 测量工具本身出错比不测更糟：它会给出**看起来很确定**的错误结论。

> **没做的（以及为什么）**：`game.ts` 仍有 1517 行，`Session` 有 43 个字段 —— 它们是同一个
> "一局游戏的状态"与"一局的推进逻辑"，按职责硬切会让大多数函数要么接收一个巨大的 ctx、
> 要么改成互相调用，收益不明确而回归面很大。要继续切的话，下一个最自然的缝是
> **子弹/开火路径**（`def.kind === 'orb'/'rocket'/'flame'` 这几处分派 + `updateBullets` 的特例），
> 做法与 `ai.ts` 完全一样（注册表 + ctx + 指纹比对）。同理，接口隔离在本项目里主要是类型可读性
> （单一命名空间对象，运行时零成本），拆分会让所有调用点改签名，收益/代价不划算 —— 记录在案。

### Z 深度：分层带 + 层内 y 排序（`depth.ts`）

改造前**没有深度系统**，只有"代码顺序"：拾取物 → 炮塔 → 怪（怪内部按 y 排）→ 玩家 → 弹幕 → 粒子。
两个后果一眼可见：

- **玩家永远压在所有怪之上**：y 更大的怪（更靠镜头、本该挡住玩家）会被玩家盖住；
- **拾取物与炮塔永远压在所有怪之下**：与 y 无关，材料掉在怪脚下时看不见；
- 影子跟实体画在同一遍里：A 影子 → A 身体 → B 影子 → B 身体，于是 **B 的影子会压在 A 身上**。

现在借的是成熟引擎里最通用、也最经得起时间检验的那套组合，没有自创概念：

| 来源 | 借鉴的东西 | 在本项目里的落点 |
| --- | --- | --- |
| **Unity** | `sortingLayer`（具名层）+ `sortingOrder`（层内整数序） | 具名层带 + 层号 |
| **Godot** | 节点 `z_index`（稀疏整数）+ `y_sort_enabled`（同层按 y 排） | 层号留空位 + 层内 y 排序 |
| **Bevy / 一般 ECS** | `ZIndex(i32)`，同值时按实体 id 保证确定性 | `(band, y, id)` 三元组 + 自增 `seq` 兜底 |
| **2D 俯视游戏惯例** | 地面/贴花/影子/实体/弹幕/特效/飘字/UI 各自成层 | 13 个层带 |

```
z=   0  ground      地面与静态装饰（烘焙成一张图，每帧一次 blit）
z= 100  decal       血迹贴花
z= 200  prop        岩石与白骨
z= 300  bounds      战场围墙
z= 400  shadow      影子（单独一遍）
z= 450  marker      地面标记（拾取范围圈）
z= 500  actor       站在地上的实体：拾取物 / 炮塔 / 怪 / 玩家 —— **同带内按 y 排**
z= 600  air         （预留）悬浮实体
z= 700  projectile  子弹与敌弹
z= 800  fx          命中粒子
z= 850  swing       挥击弧与冲击环
z= 900  text        伤害飘字
z=1000  screen      屏幕层（危险边框 / 横幅 / 调试叠层）
```

三件工程上的硬要求：

1. **层是数据**：层号稀疏、带说明、名字写错**直接抛错**（引擎里层名错是配置错误，
   不该静默画错层次）。新增一层不用重排已有层号。
2. **排序必须可复现**：比较器是 `(band → y → id → seq)` 的字典序，与**入队顺序无关**，
   也不依赖 `Array.prototype.sort` 是否稳定 —— 录屏对比、行为复现、回归基线都靠这条。
3. **零分配**：`push` 从槽位池取对象，`flush` 复用同一个 live 数组。
   一帧 300+ 实体不产生数组/对象垃圾（`render-check` 的"每帧分配 < 60"仍在守着）。

**注册表而不是 switch**：`Depth.actor('enemy', { band, y, id, draw })` ——
新增一类可视实体 = 一次注册，主渲染循环不动。注册项自己给出"用哪个 y、怎么画"，
所以 **sim 层完全不知道深度这件事**（`depth.ts` 只 `import utils`，
测试里有一条断言守着"它不认识 Game/会话"）。层内 y 取的是**插值后**的渲染 y，排序与画面一致。

**调试叠层**（借引擎的 debug view 思路）：`?z=1` 除了帧率面板再叠一张深度报告 ——
每个层带这一帧画了多少个、槽位池复用情况。没有它，层带只是代码里的数字，肉眼无法验证。

> **画面变化（都会看到）**：① 怪按 y 与玩家前后遮挡（怪走到玩家下方时会挡住玩家）；
> ② 拾取物与炮塔也参与同一套 y 排序；③ 影子独立成层，拥挤时不再互相压在身上；
> ④ 拾取范围圈从"跟玩家一起画"改成地面标记层（压在实体之下，不再盖住怪物）。
> 其余层的相对顺序与改造前**完全一致**，只是从"代码顺序"变成了显式声明的层带。

### 扩展点总账：所有"家族"在一处声明、一次校验（`registry.ts`）

前面每一节都在讲"某个东西是数据驱动的"：组件、场景、设置、粒子、AI 行为、深度层带、武器/道具/怪物表……
但它们是**七个各自为政的注册表**，每个有自己的校验方式和报错风格；表与表之间的引用没人管 ——
`Enemies.LIST[].behavior` 有没有实现、`item.icon` 有没有画法、`char.startWeapons` 里的武器 id 存不存在、
`def.shape` / `def.legs` 写错会不会静默换形状，全靠人眼。**那不是一套系统，是一堆零件。**

现在有一层总账，机制只有一份：

```js
// 在拥有数据的那个模块里自注册（避免"总账反过来依赖所有模块"的循环）
Registry.family('enemy', {
  note: '怪物图鉴（数据表）', owner: 'enemies.ts',
  entries: () => Enemies.LIST.map(d => ({
    id: d.id,
    refs: [
      { field: 'behavior', value: d.behavior || 'chase', family: 'aiBehaviour' },
      { field: 'shape',    value: d.shape    || 'blob',  family: 'enemyShape' },
      …
    ]
  }))
});

Registry.audit();   // 一次跑完全部家族：id 唯一 + 所有跨表引用都存在
```

当前 **46 个家族**（测试里还会再注册一个 `event` 家族，所以运行时是 47）：
组件 35 · 原型 11 · 武器 23（22 种武器类 / 2 个武器型）· 道具 29（图标 21 / 品级 4）· 角色 8（标签 8）·
怪物 10 · 行为 3 · 弹幕 3 · 弹丸 13 · 粒子 7 · 掉落 2 · 造型/腿/嘴/眼 4/4/6/7 ·
层带 13 · 可视实体 4 · 场景 14 · **状态 14** · 覆盖层 13 · 按键组 9 · **设置 13** · 事件 22（代码里 emit/on 的字面量）。

长线化四步往总账里加的家族，一个都不少：
难度 10 级 + **13 个修正键** · 局内营地 **5 种设施**（+效果键 +等级数）· 跨局据点 **6 种设施**（+**7 个修正键**）·
天赋 **40 个节点**（4 个扇区 / 4 种分级）· 挑战 **26 条 / 5 组 / 30 个指标** ·
档案 **9 个分区** · 图鉴 3 态 · 每日字段 11 · 每周字段 10 · 离线速率 3 · 成绩码字段 10。

除了**运行期**的家族审计，几条**静态契约**也收在这同一处（`test/registry.mjs`）——
它们跨文件、跨语言，正是最容易悄悄断掉的地方：

| 契约 | 断了会怎样 |
| --- | --- |
| 覆盖层家族 ↔ `index.html` 的 `scr-*` | 界面**静默不显示**（`q('scr-x')` 返回 null，没人报错） |
| 状态 ↔ 场景 ↔ 覆盖层一一对应 | 切到某个阶段没有界面，或界面停在上一屏 |
| 每个设置项都有 `applySetting` 分支 | 设置改了但**不生效** |
| 代码里 `emit/on` 的事件名都在总账里 | 订阅了永不触发的事件（或发了没人收） |
| `char.startWeapons` 的 id 都在武器表里 | 开局没武器 |
| 每个可视实体的层带、剔除余量都在注册项里 | 深度/剔除退化成散在循环里的魔法数字 |

**审计本身也要被测**：测试会往怪物表里塞一条 `behavior: 'teleport'` 的假怪，
断言审计确实报出来 —— 一个抓不到错的审计等于装饰。

> 这是"机制"而不是"又一份清单"：新增一个家族 = 在数据所在模块写一次 `Registry.family(...)`，
> 之后引用它的表与上面那些契约都会自动纳入（`test/registry.mjs` 有一条
> "新增家族只需一次声明，审计自动纳入"的断言）。`Registry.describe()` 能把总账打印成人话。

### 实测瓶颈与修复（不是猜的，是量出来的）

最初跑起来"卡卡的"，**根因不是帧率被限制**（主循环用 `requestAnimationFrame`，跑满显示器刷新率），
而是我把静态地面每帧重画了一遍：

`drawGround()` 对整张 1680×1260 战场做抖动填色，5 条色带 × 每带 (252/4)×(1700/4) 次循环，
**每帧约 45,000 次 `fillRect` + 133,000 次随机数调用**。60fps 只有 16.6ms 预算，这根本跑不完。

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 每帧绘制调用 | **49,966 次** | **1,838 次**（↓27 倍） |
| 静态地面 | 每帧重绘约 4.5 万次填充 | 换波时烘焙一次，每帧 1 次 `drawImage` |
| HUD 空转 120 帧 DOM 写入 | 约 1,080 次 | **0 次**（变化检测） |
| 模拟层每步耗时（300 怪） | — | 平均 0.64ms / P95 0.95ms（占预算 3.9%） |
| 模拟层每步耗时（真实波次） | — | 平均 0.17ms / P95 0.31ms（占预算 1.0%） |

结论：**模拟层只占 1~4% 的帧预算，瓶颈完全在渲染**。同批一并修掉的还有：

- **伤害飘字并发上限 26 条** —— 转轮机枪 ×6 每秒上百次命中，无节制飘字会让 canvas 文字渲染成为新瓶颈。
- **粒子超限惰性淘汰** —— 去掉 `Array.shift()` 的 O(n) 搬移。
- **空间网格复用单元格数组** —— 不再每帧重建上百个小数组。
- **怪物排序复用缓冲** —— 去掉每帧 `slice()` 产生的数组垃圾。
- **HUD 变化检测** —— 只写真正改变的字段，避免每帧触发布局重算。

这些都有测试守着：`render-check.ts` 断言每帧绘制调用 < 2500、每帧选项对象分配 < 60，
`perf.ts` 断言帧耗时占预算比例，`ui-check.ts` 断言 HUD 空转不写 DOM。改坏了会直接红。

#### 基准怎么测才不会被机器噪声带着走

这台机器是**共享的**：同一份代码连跑三次，截尾均值出现过 0.186 / 0.245 / 0.288ms
（压力场景 0.677 / 1.497 / 0.824ms），还出现过 37.97ms 的单步尖峰 —— 别的进程在抢 CPU。
所以我先前报的"性能抖动"不是代码问题，而是**测量方法问题**。现在 `perf.mjs` 的规则是：

1. **每个场景跑三轮，每轮重建同样的场景**（`Game.newRun` + 同一波次 + 同一套武器），轮间才可比；
2. **三轮全部打印**（截尾均值 / 中位 / P95 / P99 / 最差 / 离群点个数），不藏坏数据；
3. **断言取最好的一轮**：被测的是"这份代码跑一步要多久"，别的进程抢走的时间不属于这份代码，
   取最小值是"这台机器能给的最好条件"—— 真实的性能回归会把它抬高，噪声不会；
4. **另外断言轮间抖动 < 6×**：抖动爆掉说明这次测量本身不可信（数字全都不看），而不是代码慢。

最近一次（同一台机器、`node test/perf.mjs`）：

| 场景 | 三轮截尾均值 | 取最好一轮 | 轮间抖动 | 占 60fps 预算 |
| --- | --- | --- | --- | --- |
| 真实波次（第 10 波，满配 6 武器） | 0.198 / 0.167 / 0.151ms | **0.151ms** | 1.31× | **0.9%** |
| 300 怪压力（引擎上限） | 0.632 / 0.618 / 0.599ms | **0.599ms** | 1.05× | **3.6%** |
| 弹幕（转轮机枪 ×6，200 怪） | 0.583 / 0.649 / 0.546ms | **0.546ms** | 1.19× | **3.3%** |

对照：同一份代码在**整套测试连着跑**时（机器更热）测到的是 0.205 / 0.742 / 0.630ms
（抖动 1.41× / 1.39× / 1.14×）。两边的差距就是机器负载，不是代码 —— 所以 README 里
这类数字我都写成"同一次运行内可比"，不跨运行比。

### 关于对象池：实测结论是"不需要"，所以没做

先量再决定，而不是照着 checklist 加东西。测量方式：`perf_hooks` 的 GC 观测器
（先用主动制造 200 万对象的**阳性对照**确认观测器本身有效，避免测出假的 0）：

| 项目 | 实测 |
| --- | --- |
| 模拟层新增实体对象 | 约 193 个/秒（子弹/敌弹/掉落/粒子） |
| 30 秒实战（250+ 怪物）触发的 GC | **0 次**，GC 暂停 0ms |
| 渲染层选项对象分配（改造前） | **150 个/帧 ≈ 9,010 次/秒** |
| 渲染层选项对象分配（改造后） | **1.4 个/帧 ≈ 82 次/秒**（↓99%） |
| 渲染层选项对象分配（骨架化把角色那几个字面量也收掉之后） | **0.4 个/帧 ≈ 26 次/秒** |

结论：**池化实体对象最多省掉 193 次/秒的分配，而且它一次 GC 都没触发过** ——
那是为了"看起来在做优化"而加复杂度。真正的垃圾在渲染层：
`D.circle(x, y, r, color, { outlineWidth: 0 })` 这种字面量每次调用都新建一个对象。
统一改用 `draw2d.ts` 里的共享只读常量 `D.O.*` 后，每帧分配从 150 个降到 1.4 个；
骨架化时把角色绘制里剩下的几个字面量（`D.bronana` 的 skin 选项、受击闪白的选项）也换成模块级复用对象，
再降到 **0.4 个/帧**（剩下的全是 `D.text`）。

**编码约定**：`D.O.*` 是只读的，任何代码不得修改；
每帧都会走到的绘制路径里不要写选项字面量，改用 `D.O` 里的常量。

已经做掉的"复用"（比对象池更对症）：静态地面烘焙、怪物/道具贴图缓存、
空间网格单元格数组复用、怪物排序缓冲复用、粒子超限惰性淘汰。

什么时候才该上对象池：实体数量级上到几千，或者 profiler 显示 major GC 造成可见卡顿。
到那时 `render-check.ts` 的每帧分配指标会先报警。

### 绘制通用化与加速策略

加速不是靠猜，而是先加**分层统计**（`R.phase`）找出钱花在哪，再逐项验证。第一轮量出来的结果很反直觉：

| 层 | 次/帧 | 占比 |
| --- | --- | --- |
| **岩石 + 白骨** | **898** | **48%** |
| player（Bronana + 6 武器） | 385 | 20% |
| 怪物 | 175 | 9% |
| 其余（地面/敌弹/拾取/粒子/贴花…） | ~400 | 23% |

**岩石白骨每帧 898 次绘制，而它们每波完全静态。** 于是做了四件事：

| 策略 | 做法 | 效果（典型场景中位） |
| --- | --- | --- |
| ① 静态层烘焙 | 岩石+白骨与地面一样烘焙进离屏 canvas，每帧 1 次 `drawImage`；与地面分两层以保持"地面→血迹→岩石"叠放顺序 | 898 → **1**（占总量的 48% 直接消失） |
| ② 视口剔除 | `R.inView()` 只画视野内实体；余量 90px；每层的剔除半径由其种类注册表给出 | 密集场景 **−21%**；300 只怪只画 260 张 |
| ③ 原语 save/restore 条件化 | 只有需要 alpha 时才 `save/restore`（原来每个原语无条件 2 次，纯浪费） | 典型 **628 → 532**；密集 **5,479 → 4,200**（−23%） |
| ④ 小实体贴图缓存 | 拾取物形状固定，烘焙后 1:1 贴出（坐标取整，不重采样） | 每个拾取物 **11 次 → 1 次**；密集 870 → 58 |

**累计效果**：典型场景每帧绘制调用中位 **~1,800 → 490（−73%）**；
密集场景（300 怪 + 80 拾取 + 80 贴花 + 120 粒子）**6,923 → 3,403（−51%）**。

### 绘制函数通用化

`sprites.ts` 里加了一个**种类注册表**，把"画法"和"剔除半径"放在一起：

```js
S.register('ring', {
  cullR: 140,                    // 该形状的剔除余量
  draw: function (x, p) { /* ... */ }
});

S.drawObj(x, obj);               // 渲染循环只做派发，不再写 switch
S.cullRadius(obj);               // 剔除半径由注册表提供，不散落魔法数字
```

收益：新增一种特效/弹药 = **一次 `register()`**，不用改任何渲染代码；
每帧循环里也不再出现 `p.kind === 'blast' ? 130 : 16` 这类写死在渲染层的数字。
子弹的剔除半径同样收进 `S.bulletCullR()`。

### 明确没做的三件事（以及原因）

1. **武器贴图缓存** —— 把武器烘焙成图片后，旋转时 `drawImage` 会重采样，
   **粗黑轮廓会发虚**。这与"线条边缘锐利无模糊"的美术规范直接冲突，所以武器保持矢量绘制。
   代价是 player 层约 318 次/帧，但 6 把武器是硬上限，不会随局势膨胀。
2. **怪物影子 / 血迹贴花批处理** —— 这是剩下最大的一块（密集场景约 1,600 次/帧），
   做法是把同色纯填充形状合成一条路径、一次 `fill()`。
   但它会改变半透明形状重叠时的合成结果（不再重复压暗）以及层内叠放次序，
   属于**肉眼可见的美术变化**，在没有实际看过画面的前提下我不擅自改。
   需要的话这是一处集中改动（`drawEnemies` 的影子 + `drawDecals`）。
3. **全量命令缓冲批处理** —— 同色形状合成一条路径会让**重叠处的黑色外轮廓合并消失**，
   直接破坏本作最核心的美术特征。所以批处理只对"纯填充、无描边"的形状成立。

### 新增的测试护栏

- **分层绘制统计**：每帧打印各层开销，优化不再靠猜。
- **save/restore 栈平衡**：帧末栈深必须为 0，且不允许出现多余 `restore`
  （这条立刻抓出了我自己引入的两个 bug：`D.arcRing` 条件 save 配无条件 restore，
  会把调用方的 alpha/变换弹掉；`D.bronana` 引用了未声明的变量）。
- **剔除效果与精度**：确定性种子 + 固定布局做 A/B（关闭/开启剔除），
  并校验"视野内 5 只怪恰好画 5 张、视野外 5 只一张不画"，防止过度剔除变成视觉 bug。
- **`Game.newRun(charId, seed)`**：可复现的随机种子，基准与 bug 复现都靠它。
- **基准用截尾均值断言**：均值会被单次 OS 级停顿（进程被挂起，实测出现过一次 8.6 秒）
  彻底带偏，导致基准随机变红。现在断言用"去掉最差 1% 的截尾均值"+ 中位数 + P95，
  离群点单独报出来 —— 真正的性能回归仍然会让 P95/中位数变红。
- **性能基准跑三轮取最好一轮 + 打印抖动**（`test/perf.mjs`）：共享机器上单次测量能差 2 倍，
  所以每轮重建场景、三轮全打印、断言取最好一轮，并另外断言轮间抖动 < 6×
  （抖动爆掉说明这次测量不可信，而不是代码慢）。详见「基准怎么测才不会被机器噪声带着走」。
- **微基准的参照组也要防优化**（`test/comp.mjs`）：手写字面量造对象时如果对象**不逃逸**，
  V8 会做标量替换 + 常量折叠，量出来 1.1ns/个，比值假到 248×。现在两侧都强制逃逸，
  并断言"参照组 > 5ns"——参照物跑飞了比被测对象慢更隐蔽。
- **缓存账目**（`test/cache.mjs`）：条目数、像素、字节都要能报出来，并守住"长局之后同一张贴图
  还是同一个对象"（没有被反复重建）与"两层烘焙不超过显存预算"。缓存失控是那种能连跑几小时
  都不报错、只在玩家机器上慢慢吃掉内存的问题。
- **贴图几何用实测包围盒断言**（`test/rig.mjs [9]`）：CTM 桩能报出每次 fill/stroke 在画布里的
  包围盒，于是"内容有没有被画布切掉"是可测的（改成正向断言之后立刻抓出 spiky 的星形画偏了）。

### 粒子发生器（`emit.ts`）

粒子系统原本是把 `spawnParticle({...})` 内联在玩法代码里：**12 个发射点 + 5 个飘字点散落在
伤害/击杀/AI 逻辑中**，改一个特效要动战斗代码。现在改成命名配方 + 对象池：

| 关注点 | 做法 |
| --- | --- |
| 特效定义 | 集中在 `emit.ts`，玩法代码只写 `Emit.deathSparks(e)` / `Emit.bulletExplosion(...)` |
| 对象复用 | 自由链表，运行期零分配；过期对象按 O(1) 交换移除归还池 |
| 满员处理 | 轮转覆盖（O(1)），不再线性扫描找"最旧的一个" |
| 复用安全 | 取用前 `resetVis` / `resetText` **逐字段重置**，杜绝上一条粒子的残留字段 |
| 分层限流 | 视觉粒子 420、伤害飘字 28 分开限流（文字渲染贵得多） |
| 每帧数组 | 不再重建数组（原来的 `var out = []` + 重新赋值已删除） |

**注意：这次改造的性能收益基本为零**（改造前后每步耗时都在噪声内，约 0.63ms）。
它换来的是**架构与可测性**：特效定义集中、玩法代码不再关心粒子构造、满员路径 O(1)、
以及一套能守住池正确性的测试 —— `particles.ts` 会检查重复引用（同一对象同时在活跃列表和
自由链表）、复用残留字段、回收泄漏、上限突破。

这也解释了粒子为什么池化、而怪物/子弹不池化：粒子的**改造动机是架构**，
顺带拿到池的好处；而给实体加池纯粹是为不存在的 GC 问题付复杂度。

### 角色呼吸律动

旧实现把走路和待机写成两套公式在模拟层直接切换：

```js
p.bob = moving ? Math.abs(Math.sin(p.step)) * -3.2 : Math.sin(p.step * 0.5) * -1.2;
p.armSwing = moving ? Math.sin(p.step) * 0.9 : 0;
```

实测出的问题：

| 问题 | 数据 |
| --- | --- |
| 松手瞬间幅度与相位同时跳变 | bob 单帧跳 **1.19px**（走路时正常每帧只变 0.357px） |
| 手臂硬切归零 | 单帧从 −0.641 直接变 0 |
| 待机只有上下平移、没有形变 | bob −0.79~1.20px，**完全没有挤压拉伸** → 像"漂浮"不像"呼吸" |
| 待机手臂完全静止 | 0.000 ~ 0.000 |

现在拆成"模拟层给状态、渲染层求曲线"：

```js
// 模拟层（game.ts）：只维护两个连续量
p.moveBlend = U.approach(p.moveBlend, moving ? 1 : 0, dt * 8);   // 约 0.13 秒平滑混合
p.animT += dt * (1 + 0.55 * p.moveBlend);                        // 统一相位，永不重置

// 渲染层（render.ts）
R.playerAnim(p) → { bob, sx, sy, armSwing }
```

- **呼吸 = 体积守恒的挤压拉伸 + 小幅浮动**：`sy = 1 ± 2.4%`，`sx = 1/sy`（只鼓不胖）。
- **待机手臂有轻微摆动**（±0.22），不再是死的。
- **走路 = 弹跳 + 摆臂**（bob ±3.2px、arm ±0.9），经 `moveBlend` 与呼吸交叉淡入淡出。
- 相位共用且永不重置 → 无相位跳变；曲线是 `animT` 的纯函数 → 确定性、与刷新率无关。
- 参数集中在 `render.ts` 顶部：`BREATH_HZ=2.6`（周期约 2.4 秒）、`BREATH_BOB=1.15`、
  `BREATH_SQUASH=0.024`、`WALK_HZ=5.2`、`WALK_BOB=3.2`、`WALK_ARM=0.9`。

测试（12 项）：曲线连续性（1/600 秒步长扫描无跳变）、待机呼吸幅度与形变存在、
体积守恒 `sx·sy≡1`、呼吸周期 2.5 秒落在 1.5~3.5 秒区间、走路时不做呼吸形变、
松手不突跳（最大单帧 0.589px vs 均值 0.257px）、手臂过渡摊到 14 帧而非一帧硬切、
混合权重单调趋近、同相位输出一致、相位持续推进。

### 随机道具包

商店里两种赌注：**普通道具包**（便宜，赌中低层）与**高级道具包**（贵，赌高层，T4 专属）。
三条设计约束：

1. **价格由期望值反推，不是拍数字**：
   `售价 = 基准期望值 × 0.62`（`I.packPrice`），所以改了概率表价格自动跟着变，
   标价与概率永远自洽。基准折扣实测 59%，概率表与实测频率吻合（T3+ 频率误差 < 2%）。
2. **幸运只吃一次收益**：最初的写法里价格额外乘了一次幸运折扣，
   导致同一属性既抬高期望值又压低价格，**实际折扣从 62% 掉到 43%**（测试当场抓到）。
   现在价格与幸运无关，幸运只把权重往高层搬 —— 第 10 波普通包：
   幸运 0 是 `T1 62% / T2 31% / T3 8%`，幸运 60 变成 `T1 47% / T2 38% / T3 15%`，
   实际折扣从 59% 优化到 51%。**"幸运"这个属性第一次有了硬收益。**
3. **层级上限跟随波次**：第 1 波只出 T1，不会开出神装。
   另外高级包的基础权重是 `[0,3,6,2]`，截断到"本波只出 T1"后权重全为 0 ——
   最初会导致概率显示为空、售价退化成最低价、抽卡兜底给最便宜道具。
   现在有退化分支（只出本波最高可用层级），并且**第 1~2 波直接不卖高级包**（显示"第 3 波解锁"）。

开包会提示赚了还是亏了（`道具包开出：浓缩咖啡 T3 稀有（赚 13）`），
结算界面统计开包次数与总花费。

测试（`test/packs.mjs`，6 组）：定价恒等式与单调性、概率表全量性（任何波次/包种都非空）、
统计分布与理论权重一致、幸运显著抬高品质、购买/拒绝/扣钱/属性生效、
连续开包、同种子可复现、特殊道具（炮塔）开出后下一波真的部署、与刷新/锁定共存。

顺带补了一条 **`data-act` 契约检查**：index.html 里每个按钮动作都必须有对应的
`case` 分支，反之亦然 —— 防止"按钮画了但点了没反应"。

### 血迹贴花（攻击与击杀）

旧实现是一行 `if (S.decals.length < 90) push(...)` —— **贴花满了就永久停止添加**。实测：

| 指标 | 修复前 |
| --- | --- |
| 一波 391 次击杀，实际留下血迹 | **90 次** |
| 没有任何血迹的击杀 | **301 次（77%）** |
| 贴花缓冲处于写满状态的帧占比 | 67% |

另外三个问题：**攻击命中完全不留血迹**（只有击杀留）；三个溅射圆的偏移写死，
每个血迹形状一模一样；`seed` 字段存了却从没被渲染用过（死数据）。

修复：

| 改动 | 做法 |
| --- | --- |
| 环形缓冲 | 写满后覆盖最旧的一条 → **每一次击杀都留痕**，血迹永远反映最近的战斗 |
| 新旧浓度梯度 | 透明度按新旧排名 0→0.55，最旧的一条淡到 0 后才被覆盖 → **覆盖时无跳变** |
| 命中溅血 | 未致死的命中留小片血迹，受每秒 8 次预算限制（否则每秒上百次命中会把地面铺满） |
| 玩家出血 | 玩家受伤也留血迹，用 `PAL.BLOOD`（怪物用各自本色，便于看出"这里死的是什么"） |
| 形状随机 | 角度/距离/半径系数在**生成时**随机一次 → 每个血迹不同，渲染时零随机数开销 |
| 跳过看不见的 | 透明度 < 0.03 的不参与绘制 |

实测（60 秒 / 第 14 波）：击杀 206 次 → 贴花写入 576 次（含命中溅血），
**漏掉 0 次**，缓冲稳定在 90，其中 488 次写入发生在缓冲写满之后（证明环形覆盖有效）。
命中溅血实测约 9.6 条/秒，落在预算内。

测试（8 项模拟侧 + 9 项渲染侧）：每次击杀都留痕、缓冲不超容量、命中溅血受预算限制、
玩家出血用血迹色、换波清空、最新最浓/最旧为 0、褪色贴花跳过绘制、每个形状都不同、
视野外不绘制。

### 状态机（转换表 + 唯一入口）

改造前 `state` 是裸字符串，**15 处写入散在 4 个文件里，没有任何校验**。实测出的三个真故障：

| 故障 | 证据 |
| --- | --- |
| `nextWave()` 在非商店状态会**跳掉一整波** | 从第 1 波连调两次 → 直接到第 3 波（"下一波"按钮连点就中招），而怪物血量/数量按波次成长，等于白送难度 |
| `buyOffer()` 在战斗状态下**能买走商店货** | 残留点击即可购买（`buyPack`/`reroll`/`sellWeapon` 同样没有守卫） |
| `UI.refresh()` 缺 `howto` 分支 | 用 `else` 兜底成 playing → 帮助浮层消失、但游戏并没有恢复 |
| `_prevState` 单槽 | 暂停来处只存一个字符串，容易被后续状态变化弄脏 |

现在：

```js
Game.TRANSITIONS = { title: ['chars','howto'], chars: ['title','howto'], playing: [...], ... };
Game.setState(to);        // 唯一入口：校验 + 发 stateChange
```

- **转换表是唯一事实来源**：8 个状态、32 条合法转换。非法转换被拒绝并发 `stateDenied`，
  **不抛异常**（一次残留点击不该让游戏崩），同时给出可见告警。
- **`chars → playing` 被特意禁止**：那样会进入"playing 却没有会话"的状态，模拟层访问 `S` 会崩；
  进入对局必须走 `newRun()`（它建好会话后强制切换）。`step()` 也加了无会话防御。
- **动作前置校验**：`nextWave` / `buyOffer` / `buyPack` / `reroll` / `toggleLock` / `sellWeapon`
  只在 `shop` 可用，`chooseLevelCard` 只在 `levelup` 可用，被拒绝时零副作用。
- **暂停记录来处**由 `setState` 统一维护，恢复时校验来处仍可达。
- 静态检查守着"唯一入口"：**除 `game.ts` 的 `setState` 内部外，全项目不得出现 `Game.state =`**。

### 场景系统（`scene.ts`）：一个阶段"是什么"只声明一次

状态机管的是**能不能去**；但"处在这个状态时，界面各自该怎样"原本散在 4 个模块、9 处比较里：

| 位置 | 原先硬编码的策略 |
| --- | --- |
| `ui.ts` `SCREEN_FOR` | 状态 → 覆盖层（8 条） |
| `ui.ts` `UI.show` | `inGame = playing\|pause`（HUD 可见）、`inRun = playing\|pause\|levelup\|shop`（武器条） |
| `ui.ts` `UI.refresh` | 只有 `shop`/`levelup` 要重画内容 |
| `main.ts` | `state !== 'playing'` 才推进模拟、`!== title/chars` 才画世界、`playing\|levelup` 才刷 HUD、5 处按键分支 |

于是"加一个场景"要同时改 4 个文件，漏掉任何一处都不会报错 —— 只会在某个界面上表现为
"HUD 不刷了""按键没反应"这类难查的现象。现在每个阶段在 `scene.ts` 里一行：

```
场景        覆盖层    模拟  世界  HUD  武器条  按键
title      title      否   否   否   否    menu     标题页：待机背景 + 菜单
chars      chars      否   否   否   否    start    选人页：有且只有一条进对局的路
playing    —          是   是   是   是    battle   战斗中：唯一推进逻辑帧的场景
levelup    levelup    否   是   否   是    cards    升级选卡：模拟暂停，世界继续画
shop       shop       否   是   否   是    shop     波间商店：武器条可见（可以卖）
paused     pause      否   是   是   是    pause    暂停：HUD 保持可见，值是冻结的
howto      howto      否   是   否   否    none     帮助浮层：从哪进来就回哪去
end        end        否   是   否   否    none     结算：世界当背景
```

- **定义期校验**：状态漏了场景 / 场景不在状态机里 / 两个场景抢同一个覆盖层 / 按键组没定义，
  都在模块加载时抛错。
- **`main.ts` 与 `ui.ts` 里已经没有任何 `Game.state ===` 比较**（有静态断言守着），
  闸门与可见性全部读表；按键按 `keys` 分组派发。
- **表里不放函数**：`refresh` 是字符串、按键处理留在 `main.ts` 按组分发，
  所以 `scene.ts` 是纯数据（只依赖 `game.ts` 取状态清单），能被直接对照与静态检查。
- **最值钱的是那条行为断言**：`sim` 列与实测逐一对照 —— 每个状态真的跑一步，
  看会话时间是否前进，必须与表里声明一致。改表时忘了改代码（或反过来）会当场红。
  另外 `ui-check` 会把每个状态**实际**显示出的覆盖层 / HUD / 武器条与表对照
  （写这套断言时它立刻抓出我自己的一个回归：`paused` 的覆盖层是 `pause`，两者名字不同）。

### 全局状态、常量、设置与存档

**全局状态有多少，是被测出来的**：`test/persist.mjs` 扫描 `src/*.ts` 的顶层 `var`，
先判定"声明之后还被赋值吗"把常量与状态分开，再把状态逐个对照白名单。
当前结果是 **46 个模块级可变状态 / 142 个常量自动豁免**
（写这几行时是 6 / 74 —— 长线化四步一共加了 40 个状态，每一个都是显式登记的）：

| 类别 | 例子 | 说明 |
| --- | --- | --- |
| 会话 | `game.ts:S`、`emit.ts:S` | 唯一的会话指针（`emit` 那份是同源引用，便于粒子池解绑） |
| 复用缓冲 | `_cand/_candT/_candRaw/_segQ`、`sortBuf`、`_bronanaOpt` 等 | 每帧复用，零分配 |
| 缓存 | `sprites.cache`（贴图）、`draw2d.segsCache`、`ui.el` | 可重建 |
| 适配器/监听 | `storage.current`、`settings.values/listeners` | 持久化层内部 |
| 跨局档案 | `profile.ts:data`（孢子 / 解锁 / 图鉴 / 天赋 / 据点 / 挑战记录 / 上次见面） | 有测试守着它"只增不减"与坏档防线 |
| 接线层标记 | `main.ts:challenge`（"这一局是挑战局"）、`lastDaily`、`runPeaks` | 属于接线层：模拟层不认识挑战，也不认识天赋 |

新增一个可变状态必须**显式登记**，否则测试红 —— 逼着回答"它属于设置 / 会话 / 缓存 / 复用缓冲 哪一类"。
同时断言**没有任何模块往 `window`/`globalThis` 上挂东西**（ESM 化之后只留宿主注入的 `__still`/`__diag`）。

**常量**：可调数值集中三处 —— `Game.cfg`（帧模型 + 容量 + 刷怪预算）、各子系统的具名常量
（`SHAKE_*` / `BREATH_*` / `WALK_*` / `VIS_CAP` / `SEAT_*` …，就近声明并注明来源）、
`PAL` 色表。跨模块一致性由测试守着（`Bronana.SEATS === Game.cfg.maxWeapons`、
`main.ts` 不得再写死 `1/60`/`0.25`/`6` —— 这条断言当场抓出 still 截图那条路径里两处残留的 `1 / 60`）。

**设置系统**（`settings.ts`）：设置是一张声明表（键 / 类型 / 默认值 / 范围 / 中文名），
值经校验后存进 storage；本模块**不 import 渲染层或玩法层**，
"把值应用到具体模块"由 `main.ts` 通过 `onChange` 做 —— 所以 CLI 与无头测试也能读写设置，
而不会因为 import 链把 canvas 拉进来。五条防御都有测试：越界夹回、非法值拒绝、
未知键丢弃、缺失键补默认、**写入失败（配额满/无痕模式）不影响本次会话内的生效**。
面板在暂停界面里（控件写死在 HTML，值是静态 id 契约，`ui-check` 会核对两边）。

**存档系统**（`save.ts` + `storage.ts`）：三个槽位分开存，互不牵连 ——
设置（settings 自己管）、进行中的一局（`bronana.run`）、战绩记录（`bronana.records`）。

- **一局存档存的是进度，不是场上实体**：角色 / 种子 / 波次 / 等级 / 经验 / 生命 / 材料 /
  加点 / 武器与道具 id / 累计统计；怪、子弹、粒子、贴花都是派生状态，读档时由 `startWave` 重新铺开。
  **代价说清楚**：随机数流不会接着原来的走 —— 恢复的是进度，不是"同一局的未来"（那需要整局重放）。
- **信封 + 版本**：`{ v, at, kind, data }`，版本不符 / 类型不符 / 非 JSON 一律拒绝并说明原因，
  **绝不抛异常**（坏档不该让游戏起不来）。
- **能修的修，不能修的拒**：未知角色或非法波次 → 拒绝（标题页不显示"继续"）；
  未知武器/未知道具/未知加点键 → 丢掉那几条，其余照常恢复；越界生命与材料夹回合法范围。
- **自动存档点**：换波（`waveClear`）与进入商店（`shopOpen`）；`runStart` 让旧档作废；
  `gameOver` 把这一局并入记录并清掉"可继续"。
- **可继续的一局**体现在标题页多出的那个按钮（`Save.peekRun()` 只读校验，坏档不显示按钮）。
- 存储是**适配器**：浏览器传 `window.localStorage`，无头测试与 CLI 用内存适配器，
  桌面外壳将来可以换成文件 —— 三个使用方共用一套代码。


### 事件驱动 + 信号机制

界面刷新、特效、音效、结算全部由 `Game.events` 驱动。审计出总线本身的四个问题：

| 问题 | 后果 |
| --- | --- |
| 处理器抛错会向外传播 | **中断整帧模拟**，并且后续监听器不再执行（一个坏界面处理器就能卡住游戏） |
| 重入没有深度保护 | 自触发信号直接把调用栈打爆（`RangeError`） |
| 派发中增删监听器行为依赖下标 | 不可预测 |
| 没有 `once`/`clear`/计数，`init` 不幂等 | 重复 init 订阅翻倍（全项目 `off` 使用 0 次） |

补齐后（`U.Bus`）：**异常隔离 + 重入深度上限（32）+ 快照语义 + once/clear/计数与诊断**。
`UI.init()` 与订阅改成幂等；`levelCards` 事件负责"连续升级时状态不变也要重画卡面"。

**界面不再手动刷新**：`stateChange` 是唯一驱动源（`UI.refresh` 由事件调用），
`SCREEN_FOR` 是**全映射**（8 个状态一个不漏），未知状态不会错误地显示成游戏界面。

诊断入口：`Game.events.stats()` 给出派发/调用/异常/拒绝次数与订阅数；
`Game.events.events()` 列出当前订阅。`test/signals.mjs` 还会检查**死订阅**
（订阅了但没有任何代码发射的事件）。

### 摄像机抖动（trauma 模型）

旧实现有两个**实测出来**的问题：

| 问题 | 证据 |
| --- | --- |
| 偏移每帧用 `Math.random()` 重采样 → **抖动频率 = 刷新率** | 同幅度下"每秒位移总量"：60Hz 65px/s，144Hz **238px/s**（碎 2.4 倍）——手感随显示器变 |
| 用 `Math.random()` | 破坏可复现性（基准、截图、复现 bug 全受影响） |

现在改成标准 trauma 模型：

```js
R.addTrauma(0.5);      // 或由模拟层发事件：Game.events.emit('shake', 0.5)
```

- **幅度 = trauma²** —— 收尾干净，不像线性那样拖尾。
- **位移用确定性平滑噪声**（一维值噪声，固定 26Hz 采样）—— 与刷新率无关，
  60Hz 与 144Hz 每秒位移总量比值 **1.10**（旧实现 2.4）。
- **幅度以屏幕像素定义**，再按 `zoom` 折算成世界单位 —— 缩放时观感一致。
- **`max` 语义而非累加** —— 火箭筒这类高频爆炸如果累加，trauma 会长期顶到 1 变成永久晃动。
- **衰减在渲染时间**（不在模拟步里）—— 不再和粒子系统耦合，2x 速度下时长依然正确。
- 触发点：玩家受击 0.50、子弹爆炸 0.20（暴击 0.34）、自爆怪死亡 0.30、**Boss 倒下 0.90**。
- 三个手感参数集中在 `render.ts` 顶部：`SHAKE_MAX_PX=16` / `SHAKE_FREQ=26` / `SHAKE_DECAY=2.4`。

模拟层与渲染层仍然分离：模拟层只发 `'shake'` 事件声明"冲击有多大"，
**具体怎么抖完全由渲染层决定**，所以模拟层测试可以独立验证"何时请求、请求多大"。

测试覆盖（9 项渲染侧 + 5 项模拟侧）：无 trauma 时偏移严格为 0、确定性、
与刷新率无关、幅度不超上限、zoom 一致性、按时衰减归零、**抖动结束后摄像机精确回到玩家
位置（无漂移）**、高频小冲击不累加顶满、平静时不请求抖动、Boss 抖动显著更强。

## 缓存机制：四类缓存，一张倍率

"生成一次、之后复用"的东西有四类，各自解决不同的开销。共同点是：**全是位图或纯数据，
没有一类会随运行时间无限增长**（这一点由 `test/cache.mjs` 用账目守住，不靠读代码）。

| 缓存 | 位置 | 键 | 何时失效 | 实测规模 |
| --- | --- | --- | --- | --- |
| 离屏贴图 | `sprites.ts` 的 `cache` | 图案 + 尺寸 | 倍率变化 / `S.reset()` | 22 条 · **1.07MB**（跑满 1500 帧的稳态） |
| 静态层烘焙 | `render.ts` 的 `R.ground` / `R.props` | 战场波次 | 换波 / 倍率变化 / `R.invalidateBakes()` | 1× 每层 9.0MB，2× 每层 **36.0MB** |
| 每实例记忆 | `e._spr` / `e._fl`（`SpriteCache` 组件） | 敌人实例 | 倍率变化（贴图对象自带 `scale`，不匹配就重取） | — |
| DOM 脏检查 | `ui.ts` 的 `el._hud` / `slot.dataset.wid` | HUD 字段名 / 武器 id | 值真的变了 | 空转 120 帧 **0 次** DOM 写入 |

（粒子自由链表、子弹候选数组属于"复用缓冲"不是缓存，见「关于对象池」。）

三件容易做错、现在都有测试守着的事：

**1. 倍率 —— 这次补上的。** 缓存层是位图，而世界变换里带着 `dpr`。1× 烘焙的贴图在 2× 屏上
会被放大 2 倍：画面内 `drawImage` 的 `imageSmoothingEnabled` 默认开着，于是描边发虚 ——
而同一帧里**矢量绘制**的角色、子弹、粒子是清楚的，一虚一实很显眼。现在贴图与两层烘焙都按
`dpr`（上限 2）烘焙，但 `Sprite.width/height` 仍是**逻辑尺寸**，渲染层照逻辑尺寸贴：
**倍率变化不移动任何东西**，同一位置只是分辨率更高。界面上直接塞进 DOM 的画布
（角色肖像 / 武器与道具图标 / HUD 武器槽）同理，现在是"属性尺寸 = 逻辑 × 倍率、CSS 尺寸 = 逻辑"——
因为 `styles.css` 给它们写了 `image-rendering:pixelated`，只写属性不写 CSS，浏览器会用最近邻
把 1× 画布放大成胖像素。这件事由 `S.domCanvas()` 统一负责，`ui-check.mjs` 逐张核对（当前 125 张）。

**2. 失效路径。** 作废入口只有两个：`S.setScale()`（换倍率）与 `R.invalidateBakes()`（换倍率 /
换战场尺寸），`R.resize()` 在 dpr 真的变化时调它们 —— 拖到另一块显示器上不会继续用旧倍率的位图。
在此之前 `S.reset()` 是个**没有任何调用点**的 API，换句话说缓存根本没有失效路径。

**3. 可测量的账。** `S.cacheStats()` / `R.bakeStats()` 给出条数、像素、字节。测试用它守住三条：
条目数恰好是"每种怪本体 + 白闪 + 两种掉落"（没有多余的键）、长局之后同一个 def 拿到的还是
**同一个对象**（说明没有反复重建 = 没有每帧重画）、烘焙层不超显存预算。

**显存预算怎么定的**：烘焙层是"战场大小 × 倍率"的位图 —— 1760×1340 逻辑像素，2× 时每层
9.43M 设备像素 ≈ **36MB，两层 72MB**，比主画布还大。所以预算设的是"两层加起来 ≤ 76.3MB"
（`BAKE_MAX_TOTAL_PX`），超了**整体退回 1×**：宁可背景糊一点，也不要为了背景把显存吃光
（角色贴图是小块，单独按倍率走，不受这条影响）。实测 2× 正好在预算内，所以 2× 屏上背景与角色都是清楚的。

> 缓存的核心 `make()` 里曾经有两个 bug（画布高用了宽、原点按"底边 = 脚底"平移），
> 它们与倍率改造共用同一个函数。现在这条线是干净的：**画布尺寸只由 w/h 决定、原点就是左上角**，
> 贴图自报 `bodyY` / `foot` 让渲染层对位。改动与画面变化见「怪物贴图的"正方画布"」一节。

## 拍板记录二：血迹贴花

三件事都"可以改"，但每一件都有代价。决定和依据留在这里，而不是留在聊天记录里。

### 1. 褪色 —— 保留

现在是环形缓冲 90 条，透明度按"新旧排名"从 0.55 线性淡到 0：最旧的正好淡到 0 时才被覆盖，
所以环形覆盖看不出跳变。代价是**褪色速度由击杀速度决定，而不是时间**：

- 密集对局实测约 64 次贴花写入/秒 → 整个窗口 90/64 ≈ **1.4 秒**换一遍。
- 换波时清空（"进入新一波时血迹清空"），所以观感是"这一波最近 90 次击杀的血"。

改成常数透明度（原版 Bronana：血迹不褪）能拿到永久血迹，但容量一到**就会有一条突然消失**；
要不跳变就只能不设上限，那样贴花层在密集场景会无限增长 —— 而 80 条时它已经是第二大开销。

把容量从 90 提到 140 只能延长约 55% 的留存，代价是贴花层每帧调用从 ~497 涨到约 940（+90%）。
**用 +90% 的绘制调用换 0.8 秒留存，不划算，拒绝。**

### 2. 颜色 —— 保留本色

怪物用各自本色（绿怪绿血、紫怪紫汁），玩家用 `PAL.BLOOD`。这是可读性设计：
一眼看出刚打死的是哪一类怪，也符合"异形"设定与低饱和平涂的美术宪法。**这是设定，不是遗漏。**

### 3. 贴花烘焙层 —— 不做，理由是可算的

"每帧 1 次 drawImage"看着很美，但它和现行的褪色规则**在数学上不兼容**。四条路都算过：

| 方案 | 每帧调用（密集场景） | 代价 |
| --- | --- | --- |
| 现状：逐条褪色 | **497** | — |
| 常数透明度 + 烘焙层 | ~2 | 容量一到就"啪"地消失一条血迹 |
| 烘焙层 + 每帧整层重烤 | ~165 | 密集对局几乎每帧都有击杀 → 重烤 = 每帧重画全部贴花，只快 3 倍，还多一块 **9.0MB** 的战场大小离屏画布（现有地面 / 岩石两层已经占了 18.0MB；2× 屏上是每层 36MB，见「缓存机制」） |
| 按透明度分桶烘焙 | ~8 | 需要**每个桶一块战场大小的画布**：6 桶约 **54MB**，且褪色变成 6 级台阶（可见色阶） |

根因一句话：**透明度是"排名"的函数，任何一次击杀都会改变所有贴花的透明度**，
整层永远处于"刚失效"状态，缓存无从谈起。

所以保持现状，只做了**零视觉代价**的那部分：把每个贴花各自的 `save/restore` 改成整个循环共用一次。
密集场景贴花层 **605 → 497 次/帧（−18%）**，总调用 3370 → 3262，像素完全一致。
`render-check.mjs` 加了这条断言守着（>560 就红）。

> 真要上烘焙层，得先把"逐条褪色"换成"整层淡出"（新旧血同浓度），或者再拆一层"新鲜层 / 陈旧层"。
> 那是肉眼可见的手感变化，而我看不到画面，所以不擅自做 —— 改动集中在一个函数里，你说一声就动。

## 绘制批处理实测与更正

> 从"批处理是绝对优化项"这个前提出发量出来的结果，以及两处被实测推翻的判断。

### 绘制批处理：姿态图集（实测 −32% 绘制调用）

上一轮我给的结论是"半透明与描边没法合批"，那只是**合并路径**这一种做法。真正的引擎做法是
**预渲染成贴图/图集**：把一帧里重复画很多笔的东西烘成一张图，之后一次 `drawImage`。
先从最大头下手 —— 用 `tools/draw-census.mjs` 量出来一帧的调用是这样的：

| 场景 | 角色 | 怪 | 贴花 | 粒子 | 敌弹 | 合计中位 |
| --- | --- | --- | --- | --- | --- | --- |
| 典型（第 5 波，20~60 怪） | **327** | 55 | 16 | 7 | 25 | **511~547** |
| 密集（300 怪 + 贴花 + 粒子） | 176 | 1300 | 497 | 440 | — | 3403 |

**一个角色占掉一帧的一半以上**（躯干轮廓、暗部裁剪、斑点、眼、嘴、高光…），因为它是矢量画的。

做法（`S.playerBodySprite` + `S.warmPlayerAtlas`）：把**不随动作变化的部分**
（躯干 / 暗部 / 斑点 / 五官）烘成一张贴图，每帧一次 `blit`；手臂与武器仍逐帧矢量
（它们每帧都在转，烘不了）。两个决定成败的细节：

1. **呼吸形变是连续的**（`sx·sy≡1`），只烘一张会导致绘制时缩放 → 重采样发虚。
   把 `sy` 量化到 **0.002 一档**（±0.1%，肉眼不可见）并**逐档各烘一张**：
   贴图就是在那一档的形状下画的，绘制时不缩放 → 不重采样。
2. **预热**：不预热的话，游戏里每跨过一档（一次呼吸约 25 档）都要在那一帧现烘一张，
   那一帧会多出 ~300 次调用。`?` 进场第一帧一次烘完 26 张（约 7ms，一次性）。

实测（同一台机器、同一场景，`render-check.mjs`）：

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 典型帧绘制调用（中位） | 511~547 | **200~216**（武器图集 + 贴花 LOD 之后） |
| 密集场景角色层 | 176 | **16** |
| 角色身体 | ~300 笔/帧 | **1 次 drawImage** |
| 图集内存 | — | 56 张 ≈ **0.57MB**（倍率 1） |

**第二批（本轮）**：武器是刚体、只绕握把旋转 → 烘成贴图 + `rotate`（每把 1 次 drawImage，形状随挥舞变的 `tentacle` 按档各烘一张，这个"哪些武器形状随 swing 变"是声明出来的）；贴花做 **LOD**：淡到 <0.35 的旧血迹只画主圆（那个浓度下两笔溅射肉眼不可见），密集贴花层 497 → **299** 笔，新血迹仍是完整 3 笔（`render-check` 里有一条按规则算期望值的断言守着）。表格里的典型帧从 −32% 变成 **−60%**。

**还没批的、以及为什么**（用同一个普查工具量的，不含糊）：
- **贴花（密集 497 次）**：每条 = 3 个**半透明**圆且互相重叠，现在靠"每笔各乘一次 alpha"得到
  深浅不一的中心；烘成一张再整体乘 alpha 会让重叠处**变浅**。要批就得改血迹观感（或整层淡出），
  属于美术决定，没动。
- **粒子（密集 440 次）**：多数粒子的尺寸与透明度都随生命连续变化，烘一张就要缩放/调 alpha，
  同样会重采样 —— 可以按"尺寸档 + 全 alpha 贴图 + 绘制时给 alpha"做，收益中等。
- **武器（典型约 90 次）**：刚体旋转，正是"贴图 + rotate"的适用场景；代价是旋转会重采样，
  描边会略软。下一步做这个，预计典型帧再降 ~20%。

工具留在仓库里：`node tools/draw-census.mjs [帧数]` 会按**调用来源函数**与**分层**打印单帧调用账目，
以后要判断"该批哪一层"不用猜。

### 命令缓冲批处理 —— 更正与结论

上一轮我说过"纯填充批处理只在『同色 + 无描边 + **不重叠**』时严格成立"。
**这句话错了一半**，而且错的那一半正是让这个方向显得值得做的原因。

**更正 1：『不重叠』这个条件是多余的。** 只要填充**不透明**且同色，重叠与否都逐像素等价 ——
两次同色不透明填充，重叠处的颜色还是那个颜色；合成一条路径填一次，重叠处也还是那个颜色。
连抗锯齿边缘都等价，因为两者算的是同一个覆盖率：设两次覆盖率 α、β，
分开画得到 `(α+β−αβ)·C + (1−α)(1−β)·bg`，合并画得到同一个式子。
规则应当写作：**不透明 → 随便合并；alpha < 1 → 一律不合并**。

**更正 2（这条才致命）：合并路径并不减少绘制调用。** 每个子路径（`rect` / `arc` / `ellipse`）
**本身就是一次 canvas 调用**。把 9,100 个 `fillRect` 换成 9,100 个 `rect` + 1 个 `fill`，
调用数是 **9,101 而不是 1** —— 省掉的是"每笔各自走一趟光栅化"，不是调用次数。
而 `render-check.mjs` 记录、我一直在引用的那个指标，恰恰就是调用次数。

把规则套回三个候选：

| 候选 | 同色 | 无描边 | 能合并 | 调用数变化 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 地面抖动（每波烘焙 4.5 万次 `fillRect`） | 是 | 是 | 是（不透明） | **9,100 → 9,101（没省）** | 放弃 |
| 豆豆斑点 `D.dots` | 是 | 是 | 是（不透明） | 18 → 8 次/帧 | 能做，但只值 ~2% |
| 贴花 3 个圆 | 是 | 是 | **否**（alpha 0.03~0.55） | — | 不能碰 |

要动"每波一次的 4.9 万次调用尖峰"，唯一真正的办法是**改画法**：要么降低抖动密度（视觉变化），
要么改用 `createImageData` / `putImageData` 把整块地面按像素写出来
（8.5MB 缓冲 + 210 万次 JS 迭代，多半是把 4.5 万次 canvas 调用换成 210 万次 JS 循环，不是净赚）。
两个都不划算，**保持现状**。

`render-check.mjs` 现在会把换波那一帧单独测出来并给出分层明细。密集场景下实测
**51,096 次调用，其中 ground（抖动）47,835 次，占 93.6%** —— 这就是全游戏最重的单帧，
且基本全是抖动。这是**已知且接受**的每波一次尖峰。
测试同时守住它的上下限 —— 上界 60000，有人在静态层里加重活就会红。

**三个候选的最终结论**：贴花烘焙层不做（透明度的"排名"语义让整层永远处于刚失效状态，
每次击杀都要整层重烤，只快 3 倍还多一块 9.0MB 画布，而现有两层已占 18.0MB）；纯填充批处理不做（省不了调用次数）；
豆豆斑点能做但只值 2%，为它引入一个有状态的批处理 API、外加"忘了 `end` 就静默画错"的陷阱，
不划算。**批处理这条线到此为止**，除非换成 WebGL/离屏合成重写渲染层。
（⚠ **换成 WebGL 已经是决定，不是"哪天"** —— 用户拍板："shader 是一定要的……
canvas 不适合再承载我未来的游戏引擎的开发工作了"。七阶段施工见
[`docs/techstack-upgrade-decision.md`](docs/techstack-upgrade-decision.md)。
上面这句原文保留，是因为它记录的**批处理那条线的结论**仍然成立：
在接口做出来之前，合并路径并不减少调用数。）

## 实现要点

- **固定步长模拟** —— 1/60s 累积器；2x 速度是一次跑两步，不改变物理表现。
- **空间哈希网格** —— 子弹 / 近战范围 / 怪物分离力都走网格查询，同屏 300 怪物不掉帧。
- **静态地面烘焙** —— 换波时把色带 / 色斑 / 碎石 / 裂纹画进离屏 canvas，每帧只 blit 一次。
- **怪物贴图缓存** —— 每种怪物只在首次出现时绘制一次到离屏 canvas，之后仅做位移 + 挤压。
- **受击白闪** —— 预生成纯白剪影图层（`source-in`），叠加时是平涂色块，不是发光。
- **击退模型** —— 冲量封顶 520 + 指数衰减，避免多段命中把怪物打飞出地图（实测修复过这个 bug）。
- **收益递减** —— 收获按平方根递减（上限 3x）、移速与攻速有硬上限，防止后期数值爆炸。
- **敌人上限回收** —— 超过 300 时回收最远的非 Boss 怪物，保证性能可控。

### 确定性风险（**只有联机才有**）

模拟层用了 `Math.atan2 / sin / cos / pow`（`game.ts` 约 15 处、`ai.ts:136`、`stats.ts:120`；
`collide.ts` 只有 `sqrt`）。**`Math.sqrt` 是 IEEE 精确的，三角函数与 `pow` 不是规范精确的** ——
同浏览器双端实践上稳，Chrome ↔ Firefox ↔ Safari 混着来可能 1 ulp 漂移。

- **本地同屏、幽灵回放完全不受这条影响**（同一进程、同一个 JS 引擎）。
- 真漂移了 `tools/fingerprint.mjs` 会当场抓住，这是现成的护栏。

### 三条路，以及顺序

**路 A · 幽灵回放（异步多人）—— 最小可用。** 复用 `record.ts`：录带子 → 存 → 在别人的局里
当半透明幽灵叠着放。要写的是带子序列化 / 校验、时间轴对齐、幽灵渲染一层。
**完全不碰上面 7 个阻塞点中的任何一个。**

**路 B · 本地同屏 2~4 人 —— 类型正确的主力。** 依据：Brotato 本体就是**本地同屏最多 4 人**，
联机靠社区 mod（[Steam 讨论](https://steamcommunity.com/app/1942280/discussions/0/4634860269337666778)、
[BrotatoOnline](https://github.com/xx666zz/BrotatoOnline)）。这两页正文抓取被网络挡了，
所以机制细节不作断言 —— 而搜索结果里反复出现的正是 "Co-op and how items work"、
"What multiplayer changes?" 这类标题，说明"材料 / 道具共享与否"恰恰是这个模式最需要拍板的轴，
不是代码问题。改动集中在三块：

- `S.player` → `S.players[]` + `S.me`；`S.stats` 改为每玩家一份、`recalcStats(p)` 收参数。
  31 处引用逐个替换，**机械但量大**，这是主要工作量。
- 输入源抽象（`moveVec(playerIndex)`）+ 新手柄模块。P1 键鼠、P2 手柄最省事。
- 分屏：两个相机 + `clip`，`Depth` 与 `R.view` 按相机各算一份。

**零网络、零确定性风险。**

**路 C · 联机 co-op —— 周级，不是天级。** 地基在了，缺的是：

- `server/` 目前只有 `static.mjs`（纯静态），要新增一个 WebSocket 房间服务（Node 标准库够写，保持零依赖）。
- 延迟方案二选一：delay-based（简单，手感糊）或 rollback（手感好，但要"状态快照 + 回滚重算"；
  本作是 60Hz 纯函数式推进，理论可行，工作量约是路 B 的 2~3 倍）。
- 确定性加固：三角函数定点化 / 查表，或服务器权威 + 状态校验。
- 断线重连、房间、开局种子交换。

**推荐顺序：A → B → C。** 因为 A 能以极小代价验证一条决定性假设：**"带子能不能跨进程 / 跨机器
逐位重放"**。这条成立，C 才成立；不成立，C 直接否掉，省下几周。而 B 顺手把
`S.player → S.players[]` 这个重构做掉 —— C 也需要它。顺序反过来（先做 C）会把两个未验证的假设
叠在一起，出问题时分不清是网络还是模拟。

### 第一步：先验证假设，不写玩法

录取一局 → 导出带子文件 → **在另一个 node 进程里重放** → 比对指纹是否逐位一致。
不需要幽灵渲染，几十行 + 现有工具，跑完就能给出明确的"联机可行 / 不可行"。

### 待拍板的设计问题（决定手感，不是代码问题）

- 材料 / 金币共享还是各算？商店一起逛还是各逛各的？
- 升级卡各选各的？选卡时另一个人能不能继续动（关系到暂停语义）？
- 敌人数量按人数放大的系数？掉落归属？
- 死亡后是复活、观战，还是直接结束？
